# REod 言語設計書

**REod**（read と同じ発音。REod means just read）。PraTeX の埋め込みスクリプト言語。拡張子 `.reod`。

本書は現行の設計を述べる。個々の判断に至った経緯・撤回された案・却下理由は [decisions.md](decisions.md)（D-1〜D-42）にある。**却下理由は捨てないこと**——同じ結論に誤った理由で戻ることを防ぐため。

---

## 0. 位置づけ

> **REod は、TeX からの移行コストの低さを重視した、埋め込み向けスクリプト言語である。**

この一文が設計判断の優先順位を決める。汎用言語なら瑣末な事柄——`%` がコメント専用であること、`\write16` と fd の対応、`#[immediate]` と `\immediate` の一致——が、この位置づけでは中心的な要件になる。

- ホストは PraTeX（TeX を Rust で再実装し、TRIP テストの組版出力テスト以外に完全互換することを目標とするプロジェクト）。
- 役割は LuaTeX における Lua に相当する。PraTeX の拡張機構にはサンドボックス化された WASM ABI 経由の拡張と、内部 API を直接公開する経路の2種類があり、REod は ABI を跨ぐオーバーヘッドが無視できない処理のために後者を担う。

## 1. 設計思想

### 1.1 4つの制約

1. **素朴な実装でオーバーヘッドがなく、それが構文上明白であること。** 明示的な例外を認める（1.3節）。TeX に前例のある性能特性の階調であれば同様に認められる、開かれた基準として扱う。

2. **ほぼ完全な逐次実行だが、評価戦略は非純粋な遅延評価であること。** 束縛はデフォルトで遅延評価される（memoizing thunk）。

   thunk は環境を捕捉しない（クロージャ不採用）ので、自由名は強制の時点で引き直される。**それ自体は機能である**（4.6節）。しかし thunk を**関数の引数として渡すと**、自由名が呼ばれた側の局所束縛——仮引数や本体の `let`——で引き直されてしまう。呼ばれた側の局所束縛は呼出側から見えないし、**見えるべきでもない**（それは関数のインタフェースではない）。したがって引数は強制される。

   強制が起きる地点は 4.10節に尽きる。

3. **万能（チューリング完全）だが汎用ではないこと。** クロージャなし・ADT なし・一般 IO なし・多相なしという文法上の欠落によって構造的に絞り込む。ただし演算の豊富さは制限しない（1.8節）。

4. **単純素朴であって、単純明快ではないこと。** 実装の単純さと読解の分かりやすさを意図的に切り離す。

### 1.2 4制約の根拠

「TeX では読み取りと実行が同時に進行する」という一点から、4制約すべてが派生する。

### 1.3 制約1に例外はない

以前ここには「レジスタ層の 0–255 と 256–65535 でコスト特性が変わることを、e-TeX の前例に基づく明示的な例外として許容する」と書かれていた。**撤回した。**

65536 という数は e-TeX がそうだったからであり、導出ではない。**権威に従っただけの数字が、四つの制約の唯一の明示的例外を要求していた。** レジスタ層を 0–255 に限れば一様に安い経路しかなく、例外そのものが不要になる（3.7節）。

### 1.4 名前と意味の単射性（ビールジョッキ思想）

「意味と記号（名前）は、名前から意味への単射であってほしい」という原則。構文上の名称は、実際の計算上の意味から乖離させない。

これに加えて、**もう一段の検査**を課す：

> **その名前は、この言語が別のところで持っている機構を連想させないか。**

単射性だけでは、意味が違うのに同じ語を使ってしまう型の誤りを捕まえられない。実際にこの検査で3件が改名された：

| 改名前 | 改名後 | 連想させていたもの |
|---|---|---|
| `cfor` | `nfor` | C-style for |
| `match` | `switch` | パターンマッチ（ADT を持たないので存在しない） |
| `op` | `flow` | 演算子宣言機構（1.7節） |

#### 単射性はどこに掛かるか

単射性の要求は**意味論を固定したうえで**のものである。正確には:

> **同じ意味論を採用するなら、構文は意味に単射しなければならない。構文論の意味論は一意でなくてよい。**

REod は少なくとも二つの意味論を持つ——実行経路（インタプリタ）と道具経路（パーサ・ハイライタ・LSP）。同じ構文がこの二つで違う意味を持つことは、単射性の違反ではない。単射性が禁じているのは、**一つの意味論の内側で** 一つの構文が二つの意味を持つことである。

現に効いている例が無名標準ライブラリのブロックコメントである（D-69）。

| | 構文 | 意味 |
|---|---|---|
| 実行経路 | `comment; … label _comment_;` | `#[flat] goto` による読み飛ばし |
| 道具経路 | 同じ | 解析されない領域。コメントとして表示する |

どちらの意味論の内側でも、この構文の意味は一つしかない。したがって単射性は保たれている。

#### 言語間の単射性は放棄している

もう一つ、単射性が**掛かっていない**方向がある。

> その記法は、**他の言語で**持っている意味を連想させないか。

`:=` は他言語では正格な代入だが、REod では遅延サンクの束縛である。この検査は掛けていない——**意図的に放棄している**（D-70）。理由と、放棄に伴ってドキュメントが負う義務は D-70 に書いた。

`sfor`（strict for）も一度採ったが、禁止事項を撤回した結果「厳格」の根拠が消えたので `nfor`（number for）に落ち着いた。残る名前は「反復子を作らずに数値を回す」という実際の動作を言っている。

### 1.5 読み取り時検査と、道具経路の不完全性

**REod は通常の意味で静的型付けの言語ではない。** §4.3 が「`goto` で読み飛ばされる区間は解析されなくてよい」を保証している以上、実行されない区間の型エラーは永遠に見つからない。「well-typed なら実行時に壊れない」という保証は成立しない。

正確には **読み取り時検査**（check-on-read）である。読んだ範囲が、読んだ時点で検査される。

経路は2つに分かれる：

| | 何をするか | 完全性 |
|---|---|---|
| **実行経路** | インタプリタ。遅延、事前解析なし | プログラムの意味を定義する |
| **道具経路** | プリプロセッサ・LSP。先回りして検査する | **原理的に不完全** |

道具経路が不完全なのは欠陥ではなく §4.3 の裏返しである。**そう書くこと**が要求であって、完全性を装うことは許されない。

#### 静的解析の範囲

静的に意味を持つ要素（`let`/`fn`/`flow`/`typ`/`if`/`switch`/`nfor`/`ifor`/`while`/`loop`、`goto` の前方着地、領域の値の個数、paradox の検出）は通常の静的解析の対象にできる。

対象外：

- `comefrom` の名前解決（実行履歴に依存する）
- 演算子宣言（動的スコープによる復元対象、1.7節）
- **`$repeat` に動的な段数を渡した作用素式**——作用素の種類は静的に分かるが、「この文がいくつのブロックを抜けるか」が静的に決まらない。値がどの領域に着地するかも決まらないので、その下流の型検査と paradox 検出も実行時に落ちる（3.9節）

#### プリプロセッサ

多相を持たない以上、`u8 array` 用と `i64 array` 用の同じ処理は別々に書くことになる。これを埋めるのがプリプロセッサである。

**インタプリタがディスパッチしてはならない**のであって、**あらかじめ愚直に構成すること**は妨げられない。インタプリタが見るのは単相に展開しきったコードだけなので、4.7節の原則は保たれる。

条件は3つ：

- **展開結果を見せられること。** 見せられないなら隠蔽になる
- **解決しないこと。** 型リストは書き手が明示的に書く。推論も選択もしない
- **エラー位置がテンプレート側を指すこと。** 書いていないコードのエラーを見せてはならない

**生成できるのはメンバ関数だけである。** 自由関数として生成すると引数の型で区別することになり、4.7節が禁じたものになる。レシーバの型による解決は許されているので、メンバ関数としてなら通る。

#### コンパイル可能性について

制御はすべてフレーム局所である（3.9節）ため、各関数の制御フローグラフは閉じる。動的に見える量——`$repeat` の段数、`label` の跳び先——はいずれもフレームで区切られた有限領域の上を動くので、有限の分岐にコンパイルできる。thunk が環境を捕捉しないこともあり、遅延評価の言語としては珍しくコンパイラに優しい。

**ただしこれは目標ではなく帰結である。** 制約1の基準は素朴な実装であり、コンパイル可能性が設計判断を駆動し始めればその基準は侵食される。「コンパイラの都合で構文を制約する」ことはしない。

### 1.6 2層構造と、撃つ自由・組む自由

**デフォルト層**（静的型検査・IDE 支援を提供）と**マクロ層**（C 以上の表現力を持つ生のトークン展開機構。支援は保証されない）の2層。「足元を撃つ自由」だけでなく「胸元まで撃ち抜く自由」を意図して両方与える。

そして同時に、**規律を組む自由**を同じ機構で与える。

> 「胸元まで撃ち抜く自由」だけを与えて規律を組む手段を与えないなら、それは自由ではなく放置である。**危険にだけでなく、安全にも自由がなければならない。**

`return` は言語の組み込みではない。作用素式（3.9節）と作用素の別名（3.3節）で書かれた、無名標準ライブラリの1行である：

```
flow return = $repeat(break, getdepth());
```

同じ機構で、抜ける段数を名前の裏に隠す別名も書ける。`return` が安全なのは `getdepth()` がちょうど正しい数を返すからであって、機構が安全だからではない。言語はどちらを作るかを代行しない。

### 1.7 演算子宣言機構

ほとんどの文字を、現在の識別子の文脈に依存して演算子として扱える汎用的な宣言機構（Prolog の `op/3` に近い形——優先順位・結合則・引数の数を書き手が宣言できる）。静的解析の対象から外れ、処理系のコンテキストスイッチ機構の一つとして動的スコープによる復元対象になる（4.8節）。`global` は認めない。

制御構文（`break` / `continue` / `goto`）はここに置かない。置けば合成は無償で手に入るが、1.5節の静的解析の約束が崩れる——**制御フローの一般化と、制御フローの静的解析可能性は交換関係にある**。REod は後者を選ぶ。

### 1.8 通常演算のリッチさと CPU 命令の露出

「万能だが汎用ではない」は演算の豊富さを制限しない。CPU（x86・x87・SSE/SSE2 を含む）にある命令は積極的にプリミティブとして露出する。

`f80` を持つのはこの帰結であり、それ以上の意味がある。x87 は内部的に 80bit で計算する。`f64` しか提供しない言語は、**80bit で計算した結果を「64bit で計算した」と提示している**。実際とは異なるモデルを与えて理解したことにすることは許されない。

ネタ機能として、TRPG の NdM ダイスロール記法をネストできる2項演算子として持つ（`1d1d100` = `1d(1d100)`、右結合）。

### 1.9 作者の認知モデルとの適合

「グローバルステート＋命令列による介入＋後続がそれを読む」という認知モデル。「処理系がつっぱねる以上のことをしない」という評価軸は、ディスパッチ規則（4.7節）に直接反映されている。

### 1.10 中核仕様と無名標準ライブラリ

REod は**中核仕様**と、すべてのプログラムの前に無名で読み込まれる**標準ライブラリ**の2層に分かれる。標準ライブラリは REod で書かれている。

層構造そのものは問題を生まない。ただし条件がある：

- **脱糖を字句どおり仕様に書く。** 「存在する」だけでなく「書かれている」こと
- **層の境界を節として明示する。** 機能の一覧ではなく境界の宣言
- **中核の形をいつでも直接書けること**

> 抽象化を使う自由と、抽象化を剥がす自由の双方を人間に残すこと。

標準ライブラリにあるもの：`str`（= `u8 array`）、`return`、`printstr` / `printi32` 等（すべて `write` の糖衣、3.10節）。

## 2. 実行モデル

- コンパイル前提を持たない、逐次実行型のインタプリタを本義とする。
- TeX の読み取りサイクルとの統合を意図する。
- **プログラム全体の構文解析を先に行わない。** カーソルがトークン列を進み、読んだそばから実行する。通過していない区間は解析されていない——4.3節の「隠しコードの安全性」はこれに依る。
- `goto` は TeX の `\if` 偽分岐スキップと同型の「認識的スキップ」として実装される（波括弧の深さのみを認識）。

## 3. 構文仕様

### 3.1 コメント

コメントは字句の特別扱いではない。

> **`%` から改行までを、改行を含めて（閉区間で）飲む。**

飲まれた区間は何も産まない——4.9節の言葉で言えば akasha である。`;` が「値を作ってから潰す」のに対し、コメントは最初から何も無い。**到達点が同じで経路が違う**だけである。

`%` はコメント専用であり、剰余は `mod`（D-7）。TeX 互換を明示目的に据えている以上 `%` は譲れない。

#### 閉区間であることから導かれる3つ

**(1) 行末 `%` は行継続になる。** 改行を飲むので、改行が意味を持つ位置では次の行が続きとして読まれる。**TeX と同一機構**である。マクロ層（5節）が「継続は行末 `%`」を前提にしているのも、この一つの規則から出る。

**(2) アトリビュートの後にコメントを置けない。** アトリビュートは行末で終端する（3.3節）が、コメントがその改行を飲むので終端できない。

```
#[immediate]  % なぜ immediate が要るか      不正
x := x / 2;

% なぜ immediate が要るか                    正しい
#[immediate]
x := x / 2;
```

**規定ではなく帰結である。**

**(3) `%` が意味を持つのは、改行が意味を持つ場所だけ。** REod で改行が意味を持つのはアトリビュートと返り値型だけなので、影響範囲はそこに限られる。

> **半開区間**（改行を含めない）も選べる。その場合アトリビュート行に行末コメントを書けるが、行継続と TeX との一致を失う。§0 の位置づけ（TeX からの移行コストの低さ）を優先して閉区間を採る。

**行番号は物理行で数える。** エラー位置は書かれた行を指す。改行の意味（終端）にだけ論理行を使う。

### 3.2 型

**数値型**：`i64`, `u64`, `i32`, `u32`, `f32`, `f64`, `f80`, `u8`, `u16`

**組み込みパラメトリック型**：`array`, `pair`, `hashmap`。構文は後置形式に統一されている。

- `T array` — T の値を u64 キーで引く
- `T U hashmap` — T の値を U キーで引く。**`T array` ≡ `T u64 hashmap`** と読めば引数順が導出される
- `T U pair` — 第1要素 T、第2要素 U。写像ではなく直積なので、上の2つと引数順の読み方が違うのは当然である

この3つ以外にパラメトリックな型を書き手が新設することはできない。

**paradox 型** — 単位型。表示は `{}`。宣言や制御移動が返す型であり、**実在できず、記録もできない**（4.9節）。`{}`（空ブロック）がこの型の正準な式である。

- **読み取り時検査**（1.5節）＋型推論。推論は**関数内推論**に限定される（クロージャなしのため関数境界を越えない）。
- **多相（ジェネリクス）はユーザーが書けない。** 組み込みコンストラクタ（`Array.init` 等）は任意の要素型を返す必要があるため多相である。禁止されているのはユーザー定義の多相。
- **関数オーバーロードは許容**する（4.7節）。返り値の型だけで区別する。
- 代数的データ型（ADT）は提供しない。`switch` は数値など言語が直接比較できる値に限定する。

```
typ uf_tree {
    parent : i64 array;
    rank : i64 array;
};
```

### 3.3 束縛

REod は4つの束縛構文を持つ。**束縛演算子（`:=` / `&=` / `^=`）は thunk の作り方を区別するために存在する**ので、thunk を作らない構文には現れない。

| | 記号 | thunk を作るか | 本体をいつ読むか |
|---|---|---|---|
| `let x := E;` | 束縛演算子 | **作る** | 強制時に1回（メモ化） |
| `fn f (…) { … } -> T;` | なし | 作らない | 呼び出しごと（フレームを積む） |
| `typ T { … };` | なし | 作らない | — |
| `flow p = …;` | `=` | 作らない | **使用ごと**（メモ化しない、フレームを積まない） |

```
let a := E;   % 式 E から新しい thunk を生成する（既存の名前を必要としない根源的操作）
let b &= a;   % a が今指している thunk そのものを共有する
let c ^= a;   % a が今指している thunk の未評価の計算を、独立した新 thunk として複製する
```

新規導入には `let` が必要で、省略は不正。再束縛は `let` なしで書く。

`flow` は作用素式（3.9節）に名前を与える。`=` は定義であって束縛演算子ではない——`flow` は thunk を作らないため。`fn` と `typ` は名前の終わりが `(` と `{` で分かるので記号を要さないが、`flow` の本体は識別子で始まりうるので区切りが要る。

#### アトリビュート

```
#[global, immediate]
x := x / 2;
```

アトリビュートは「**次の行の評価方法・戦略を変更する**」の一つの意味を持つ。したがって：

- 複数指定はリストで書く
- **行末で終端する。** 修飾する文を同じ行に続けることはできない——続けられれば「次の行を修飾する」が嘘になる

| | 意味 |
|---|---|
| `#[immediate]` | 束縛の**前**に強制する。右辺に左辺の名前が現れても旧束縛を見る |
| `#[global]` | 書き込みを動的スコープの巻き戻しから除外する（4.8節） |
| `#[forward]` | 名前の存在チェックを抑止する（4.4節） |

`global` と `immediate` は**直交する2つの操作**であり、束ねない。同時に指定したければリストで明示的に書く。

**未解決**：`#[forward]` は不動点コンビネータではなく名前検査の抑止である。したがって再帰以外の用途（後述の「自由名をパラメータとして使う」形など）にも使われる。名前が意味から乖離しているので、改名の余地がある。

### 3.4 関数

```
fn getroot (uf : uf_tree, idx : u64) {
    if (uf.parent[idx] == idx) { idx }
    else {
        #[global]
        uf.parent[idx] := getroot(uf, uf.parent[idx]);
        uf.parent[idx]
    }
} -> u64;
```

- **返り値型は本体の後置矢印 `->` で記述する。** `->` は宣言位置でも呼出位置でも「返り値型を名指す」という同じ意味を持つ。
- **`;` で終端する。** 宣言は paradox 値を産むので、消さなければならない（4.9節）。
- **`->` の省略は本体からの推論であり、`-> {}` の糖衣ではない。** `fn f () { 5 };` の返り値型は i64 に推論される。以前ここには「省略は `-> {}` の糖衣」と書かれていたが、`{}` は paradox なので 5 を返せず、記述が誤っていた。撤回した。
- 引数の型も推論可能な場合は省略できる。**関数はクロージャを構成しない。**
- 関数は第一級ではない。`let g := f;` は不正。
- オーバーロードされた関数は返り値の型だけで区別され、引数の個数は常に一致することを要求する（4.7節）。呼出側は `式 -> 型` で解決先を指定する。

```
let uf := make(n) -> uf_tree;
```

- メンバ関数（`object.operation(args)` 形式）を持つ。ユーザーも定義できる。多相禁止により単相——`u8 array` 用と `i64 array` 用は別々に書く。機構は中核、個々のメソッドは標準ライブラリ。

REod は `main` を特別扱いしない。構造化プログラミングをしたければ自分で書けばよい：

```
fn main () {
    return 0;
};
main()
```

### 3.5 制御構造

すべて**式**である。4つは**反復回数を何が決めるか**だけで違う。それ以外に構文上の差はない。

| 構文 | 邦訳 | 反復回数を決めるもの | 完走時に領域を埋めるもの |
|---|---|---|---|
| `nfor (i in 0..n) { … }` | 数値原始再帰式 | **開始前に確定した範囲** | 最後の周回の末尾式（範囲が空なら paradox） |
| `ifor (x in it) { … } comp { … }` | 反復子循環式 | 反復子（有限とは限らない） | **なし**（出口が決める） |
| `loop { … }` | 無条件循環式 | `break` | **なし**（`break` が決める） |
| `while (cond) { … }` | μ再帰式 | 条件が 0 になるまで | **反復回数そのもの** |

計算論的な名前が残るのは `nfor` と `while` だけである。`ifor` の反復子は有限とは限らないので原始再帰的とは言えず、`loop` は上界を持たない。

**いずれの構文も本体の性格は制約しない。** `nfor` が保証するのは自分の反復が上に有界であることだけであり、本体に `while` を書けば全体は停止しない。

#### 各構文の値と `break` / `comp` の可否

「その構文自身が領域に何を置くか」を見れば、すべて決まる（4.9節の領域の規則から導出される）。

| 構文 | `break v` | `break;` | `comp` |
|---|---|---|---|
| loop | **必要**（唯一の値源） | 可 | 不可（到達しない） |
| while | 不可（二重） | 可 | 不可（二重） |
| nfor | 不可（二重） | 可 | 不可（二重） |
| ifor | 可 | 可 | **可（唯一）** |

`comp` が `ifor` だけに付くのは、**唯一「完走しうるのに、完走時に埋めるものがない」構文だから**である。`loop` は完走しないので comp が到達せず、`while` と `nfor` は既に埋まっているので二重になる。

`ifor` の2つの出口（`break v` と `comp`）は実行時には排他なので、領域に入る値は常にちょうど1つである。

**以前ここには `nfor` に対する `break`/`goto`/`comefrom`/`label` の全面禁止が書かれていた。撤回した。**

- `break;` — 「脱出を持てば原始再帰性が壊れる」は誤り。**上界のあるループからの早期脱出は依然として原始再帰的**である（回数が減るだけで上界は保たれる）。加えて本体に `while` を書くことは元から禁じられておらず、本体の性格は一度も制約されたことがなかった
- `goto`/`comefrom`/`label` — jump は depth 基準を跨げない（3.9節）ので、`nfor` の中で完結する限り問題がない。§4.1 にあった「`nfor` 内 jump でインタプリタがクラッシュする」規定も削除した

残るのは `break v` の禁止だけで、理由は**領域が二重になる**ことの一つである。

#### `while` は真の μ作用素である

`while` 式の値は**反復回数**である。μn. cond(n) = 0 となる最小の n そのもの。条件は各周回の前に評価されるので C の while と挙動は一致し、期待を裏切らない。しかし C が捨てている n を REod は返す。

**条件は任意の数値型を取る。** μ は「f(n) = 0 となる最小の n」として定義されるので、条件は述語ではなく数値でよく、0 が停止を意味する。C の「0 は偽」という慣習と一致するが、REod ではそれが**定義そのもの**である。§3.2 にブール型がないのはこのためで、必要がない。

```
fn collatz_steps (start : u64) {
    let x := start;
    while (x != 1) {
        #[immediate]
        x := if x mod 2 == 0 { x / 2 } else { 3 * x + 1 };
    }
} -> u64;
```

カウンタ変数が要らない。while の値がそのままステップ数である。

任意の値を返して while を抜けたければ、while の領域を跨げばよい：`$repeat(break, 2) v;`。while の領域は埋められないまま放棄されるので、二重は起きない。

#### `if` / `switch`

```
if (cond) { … } else { … }

switch kind {
    0 => union(uf, x, y);
    1 => write(1, $s, find(uf, x, y).to_str());
    _ => write(1, $s, "invalid command");
}
```

`&&` / `||` は短絡評価する。条件式の形に制限はない。

**`else` のない `if` は、偽のとき領域が埋まらない。** 値として使うならフォールバックが要る（4.9節）。文として使うなら `;` で潰す：

```
if c { n := 5; };                 文として
let x := if c { 5 } ?? 0;         値として。偽なら 0
```

これは**パターンマッチ式よりボイラープレートが小さい**。`_` の腕のない `switch` も同様である。

値を出す腕どうしは型が一致していなければならない（同じ領域に置かれるので）。ただし paradox を出す腕は注釈された型の既定値になるので、一致の要求から外れる。

ADT を持たないにもかかわらず網羅性に類する要求が出てくるのは、領域の規則からの帰結である。

#### `goto` / `label` / `comefrom`

```
goto skip_report;
ifor (x in uf.parent) { write(1, $s, x.to_str()); } comp { write(1, $s, "empty"); };
label skip_report;
```

意味論は4.1節に尽きる。

### 3.6 エラー処理

**エラーは値にならない。** ADT を持たないので error union は構成できない。処理系内部の失敗（`nfor` 内 label 到達、マクロ展開後の括弧不整合、配列範囲外等）はホストである TeX へ即座に伝播する。

ホストへ渡るものは2種類ある——**正常終了の値**（トップレベルの領域の値。exit code として扱う。解釈はホストに委ねる）と、**エラー**。

### 3.7 メモリモデル

```
countu64[i]             % レジスタ層オブジェクトへの添字アクセス（0–255、単一オブジェクト）
let a &= countu64[0];   % 参照（エイリアス）束縛
```

- **0–255**：型ごとに1つ確保される単一のレジスタ層オブジェクト。**一様に安い経路しかない**ので、制約1に例外は要らない（1.3節）。
- **256以上**：`Array.init(size, …)` 等による汎用ヒープ確保。
- 巻き戻しの規律は確保元によらず一様である（4.8節）。

### 3.8 演算

CPU 命令（x86・x87・SSE/SSE2 を含む）に対応する演算を積極的にプリミティブとして持つ。剰余は `mod`。ダイスロール演算子（`d`、右結合、ネスト可能）を含む、拡張可能な演算子宣言機構を持つ（1.7節）。

### 3.9 作用素式

**値でも関数でもマクロでもない第4の圏。**

```
作用素式 := 作用素* 終端
作用素   := 'break' | '$repeat(' 作用素 ',' 式 ')' | 別名
終端     := 式 | 制御文 | ε
制御文   := 'continue' | 'goto' L | 'comefrom' L | 'label' L
```

終端は列挙ではなく「式または制御文」である。

**意味論は1行**：

> `break X;` — このブロックを正常に終了し、続けて X を**外側の文脈で**行う。

領域の言葉で言えば、**`break X` は X を1段外の領域へ置く**。`$repeat(break, n)` は n 段外へ置く。

- X が**式**なら、その値がそのブロックの値になる
- X が**制御移動**なら、それが外側の文脈で行われる

`if` / `else` の本体は状態に対して透明（4.8節）なので、**`break` に対しても透明**——段数を消費せず素通しする。

#### `$` はモード切り替え

**`$` を読んだ時点で作用素の評価規則へ入る。** TeX の catcode 切り替えと同型。入ったあとは印を重ねない：

```
$repeat(break, getdepth())        % ○
$repeat($break, getdepth())       % × 同じものの2つ目の綴りになる
```

`$` は「他のものと読み違えられる構文」に付ける印である。`nest(…)` は関数呼び出しに見えるので要る。`break` は制御作用素以外に読みようがないので要らない。

#### `$repeat` の引数

第1引数は `break` / `continue` / 作用素の別名。`break` を重ねればブロックを n 段抜け、**`continue` を重ねれば反復を n 個進める**——`ifor` なら n 個消費、`nfor` なら n 個飛ばす、`while` なら条件を n 回試す。`loop` は進める状態がないので退化する。

`goto` は重ねられない。行き先がラベルで決まるので繰り返しても同じ場所に着く。

第2引数（段数）は**動的でよい**。作用素の種類は静的なのでディスパッチ原則（4.7節）には触れない。動的なのは段数だけであり、配列の添字が動的なのと同じ種類のことである。ただし1.5節の制限が掛かる。

#### 順序づけは並置。構成子は `$repeat` だけ

作用素を実行時の値で選ぶことはできない（4.7節）ので、順序づけの構成子の引数は常にリテラルにしかなりえない。ならば並置で足りる：

```
$repeat(break, n) continue;
```

#### `break goto` は規律のある跳躍

裸の `goto` は jump なので4.8節の一括巻き戻しを起こす。`break goto L` は**ブロックを正常に閉じてから跳ぶ**ので起こさない。ループ本体の journal は正常脱出で破棄・jump で適用されるため、この差は観測できる：

```
loop { acc += 1; goto done; }        % acc は巻き戻る
loop { acc += 1; break goto done; }  % acc は残る
```

#### 作用素は第一級ではない

`let f := break;` は不正。関数と同じ線である（3.4節）。制御移動が paradox 型を持ち、paradox は記録できない（4.9節）ことからも同じ結論が出る。

#### 別名

```
flow return = $repeat(break, getdepth());
flow skip_two = $repeat(break, 1) $repeat(continue, 2);
```

本体は**使用のたびに使用位置で読み直される**。フレームを積まないので、本体中の `getdepth()` は使用位置の深さを見る。

本体は終端を含んでよい——**インラインで書けるものは名前を付けられる**べきである。ただし作用素式は終端を高々1つしか持てない（終端の後には制御が戻らない）ので、別名が終端を持つなら使用位置に重ねられない。

#### `getdepth() -> u32`

現在のフレーム内で開いているブロックの数。すなわち、**この関数（トップレベルならプログラム）を抜けるのに `break` を何回重ねる必要があるか**。`break` が吸収されるレベルだけを数えるので、`if` / `else` の本体は入らない——`getdepth()` と `break` が同じものを数えなければ、この対は役に立たない。

#### `comefrom` 終端だけは実行が続く

`continue` と `goto` は制御が移るのでその後は何も起きないが、**`comefrom` は登録して終わり、実行が外側の文脈で続く**。唯一の「終わらない終端」である。

```
fn hoge () { { break comefrom T; }; write(1, $s, "草"); label T; 0 } -> i64;
```

`break` が内側のブロックを閉じ、`comefrom T` がその直後——`write(…)` の位置——を登録する。以後 `label T;` に来るたびそこへ戻るので、草が出続ける。**ループ構文を一つも使わない無限反復**であり、`comefrom`/`label` だけでチューリング完全であることの実演になっている。

`comefrom` は paradox 値を外側の領域に置くので、閉じられたブロックには `;` が要る。

#### depth 基準と、その越え方

**jump は depth 基準を跨げない。** より内側の基準の中も、より外側も**見えない**。

これはエラーではなく**隠蔽**である。§4.1-3 の「保存されている `comefrom` があればその直後へ飛び、**さもなくば何もしない**」がそのまま処理するので、新しいエラー条件を一つも足さない。`goto` だけは行き先が要るので、フレーム内に見つからなければエラーになる。

depth 基準はフレーム基底であり、**4つのものがこの一つの境界を共有する**：

| | 境界 |
|---|---|
| `getdepth()` の原点 | フレーム基底 |
| `break` が越えられない上限 | 同上 |
| jump の巻き戻しが降りられない下限 | 同上 |
| `goto` の前方走査の範囲 | 同上 |

**帰結：ラベル名はフレーム局所になる。** 名前空間もモジュールも持たない言語で、ラベルだけは自動的に閉じる。異なる関数が同じ `label retry` を持っても衝突しない。標準ライブラリや、後に載せるマクロ層で効く。

**depth 基準を跨ぐ唯一の手段は `break` である。** 偶然跨ぐことはできず、書かなければ跨げない。`break comefrom T` は「外側のフレームに登録を置く」という明示的な操作になる——制御がフレーム局所であることの唯一の例外であり、しかも構文的に特定できる。

#### 跳び先の生存期間

> **jump の跳び先は、それを含む構文が開いている間だけ生きる。**

これで**飛び込みの禁止**が出る：

| 登録した場所 | いつ死ぬか | 外から飛び込めるか |
|---|---|---|
| 関数本体 | 戻るとき | 不可 |
| ループ本体 | ループを抜けるとき | 不可 |
| 裸のブロック | 抜けるとき | 不可 |
| `if` の本体 | 透明なので囲む構文と同じ | 可（囲む構文が開いていれば） |

`if` が例外に見えるのは透明性（4.8節）の帰結である。取られなかった枝へ飛び込んでも `if` は状態を作らないので何も壊れない。**規則を書き足さずに正しい答えが出る。**

飛び出しは許される。`goto` の走査は相対深さ 0 以下でしか照合しないので、より深いブロックへは着地せず、浅い方へは出られる。

#### `$frame` — 呼び出しを伴わない depth 基準

```
let body := $frame {
    if c { return 0; }
    compute()
};
```

`$frame` がなければ、`return` の `getdepth()` は**強制した側**の深さを見るので、ブロックがどこで強制されたかによって「どこから抜けるか」が変わる。`$frame` があればブロック自身から抜ける。**thunk が環境を捕捉しないことの帰結を、制御についてだけ打ち消す**操作である。

depth 基準を張るとは、`getdepth()` の原点・`break` の上限・jump の下限を**同時に**決めることである。3つは同じものなので分離できない。裸のブロックにのみ付けられる。

#### 関数境界

`break` は関数境界を越えられない。越えると呼び出し式の評価途中への制御移動になる。黙って打ち止めにするのは嘘なのでエラーにする。

### 3.10 出力

中核が持つのは `write` だけである。

```
write(fd, 書式, 引数...)
```

- 第1引数は POSIX のファイルディスクリプタ（`\write16` ＝ 端末 ＝ fd 1）
- 第2引数は**レンダリング方針**。各引数は自分の静的型に応じてその方針でレンダリングされるので、型の混在した出力を1回で書ける
- 第3引数以降は結合される

```
write(1, $s, "count: ", n);
```

`$s` はテキスト表現（`u8 array` はそのまま、整数は10進）、`$x` は16進表現。方針は引数の型から導けないので、書式引数は実際に情報を運ぶ。

**書式トークンは文字列ではなく字句トークンである。** 文字列リテラルは値なので、`"%s"` を使えば実行時の値でディスパッチすることになり4.7節に反する。加えて `"%s"` は printf の見た目を借りるので、実際には行わない位置指定の埋め込みを示唆する。

**`write` は引数を左から順に評価しながら出力する。** 中間バッファを作らないので制約1を満たす。途中の引数の評価が失敗すれば、そこまでの出力は既にストリームへ出ている——隠すべき欠陥ではなく観測可能な事実である（TeX の `\write` と一致する）。

**`write` は値を返さない。** POSIX の `write(2)` は書けたバイト数を返すが、REod は 3.6節により失敗を値で表現しない。名前を借りている以上、返り値を持たないことを明記する。

`printstr` / `printi32` 等はすべて `write` の糖衣である（1.10節）。

## 4. 意味仕様

### 4.1 goto / label / comefrom の意味論

この3つの意味は次の3行に尽きる。

1. **`comefrom` は位置をコンテクストに保存する。** 名前ごとに1エントリを持つ可変マップへ、通過するたびに「戻り先＝この文の直後」を無条件で上書き登録する。
2. **`goto` は対応する `label` の直前まで読み飛ばす。** 走査はマクロを展開せず、波括弧の深さのみを認識する（認識的スキップ）。着地はカーソル移動以上の意味を持たない。
3. **`label` は保存されている `comefrom` があればその直後へ飛び、さもなくば何もしない。**

以前ここには「`nfor` 本体内で jump 関連の構文を見つけた場合インタプリタがクラッシュする」という例外があった。**削除した**（3.5節）。jump は depth 基準を跨げないので、`nfor` の中で完結する限り問題がない。

#### `#[flat]` — 走査から構造の認識を外す

規則2の走査は波括弧の深さを認識する。`#[flat]` はそれを外し、**最初に見つかった `label` に着地する**。

```
#[flat]
goto _comment_;
    ここは壊れていてよい { { {
    undefined( 1 2 3
label _comment_;
```

depth 基準（フレーム）の境界は越えない。そこは構造ではなく制御の境界である。

**これによりブロックコメントがほぼ導出される。** 上の区間は構文が壊れていても名前が未定義でも括弧が不均衡でも読み飛ばされる。

「ほぼ」なのは**字句解析だけは通る必要がある**ためである。未終端の文字列リテラルは字句の時点で失敗する。加えて**入れ子にならない**——最初の `label _comment_` で終わる。

`#[flat]` は構造からの明示的な離脱なので、**構造的に無効な位置へ着地しうる**。入っていないブロックの中へ着地すれば、その `}` に到達して実行時エラーになる。

> **却下**：「入っていないブロックの `}` は不活性とする」。「着地はカーソル移動以上の意味を持たない」からは自然に見えるが、`}` を無害な no-op にすると**本物の括弧不均衡が全域で黙って通る**。`#[flat]` の誤用は報告される方がよい。

`#[flat]` は静的解析の対象外である（1.5節）。

### 4.2 comefrom トリガーの無効化範囲（撤廃）

以前ここには「`let` の右辺・`ifor`・`while`・`loop`・関数本体の内部では `comefrom` トリガーを禁止する」と書かれていた。**撤廃した。**

禁止は不要だった。`comefrom` の登録は save stack の対象であり（4.8節）、**関数を抜けるときに巻き戻される**。つまり関数内で登録したものは、その呼び出しの中でしか効かない——禁止しなくてもそうなる。禁止は「危ないから止める」ではなく、**既に成立していることを重ねて言っていた**だけである。

同じことが depth 基準の規則（3.9節）からも出る。基準を跨いだ登録は見えず、見えなければ `label` は何もしない。

**ただし `break comefrom` は別である**（3.9節）。`break` が先にブロックを閉じるので、`comefrom` は**外側の文脈**で発火する。したがって関数本体に書いても、登録されるのは呼び出し側のフレームである。禁止に当たらないが、読み手は驚くのでここに明記する。戻り先は「その呼び出しの直後」として一意に定まるので、曖昧さはない。

### 4.3 マクロ展開と goto 走査の相互作用

走査中はマクロを展開しないため、TeX の `\iffalse … \fi` と同型の「隠しコードの安全性」を、`goto` による任意跳躍という形で一般化して持つ。マクロによる波括弧の不均衡は言語仕様として禁止しないが、`goto` 走査が実際にその区間を通過した時点で動的に検出され、"too many }'s" 相当のエラーとして TeX へ伝播する。

**この性質が、名前の存在チェックを関数本体に掛けられない理由である**（4.4節）。

### 4.4 静的型付けと名前検査の局所性

マクロ展開が確定した断片ごとに局所的に型を検査する。通常の関数呼び出しの型付けは常に関数の宣言だけで完結する（関数内推論、3.2節）。

**名前の存在チェックは `let` の右辺だけに適用する。** `let x := E;` は E の評価を遅延するので、未知の名前のエラーが「いつ強制されたか」に依存して現れる。エラーの出るタイミングを評価戦略から独立させるために、束縛の時点で検査する。`#[forward]` はこの検査だけを抑止する。

**`fn` の本体は検査しない。** 定義時に本体を検査すると、`goto` で読み飛ばされる区間に未定義の名前があってよいという性質（4.3節）と衝突する——どの `goto` が発火するかは静的に決まらないので、この衝突は回避できない。

したがって：

- 関数の自己再帰・相互再帰は `#[forward]` なしで動く
- `#[forward]` が要るのは相互参照する**値**の束縛だけ
- `#[forward]` を `fn` に付けるのはエラー（抑止するものがない）
- **`fn` 本体のタイプミスは呼び出し時まで見つからない**

検査の対象外とする識別子：予約語、アトリビュートの中身、`goto`/`label`/`comefrom` の直後のラベル名、`->` の直後の型名、走査中に `let` / `in` で導入された名前。

### 4.5 read() の意味論

`read()` は入力ストリームを消費する入力プリミティブで、その意味論は TeX の `\read` に対応する。行を読む。遅延評価される式に含まれる場合、入力の消費もその式の評価時点まで遅延する。

`read` は**返り値型オーバーロードの原型例**である。引数を取らないので引数による解決が原理的に不可能であり、4.7節が返り値型に絞った動機はここにある。

```
#[immediate]
let n := read() -> u64;
#[immediate]
let line := read() -> str;
```

### 4.6 束縛演算子の精密な意味論

- **`a := E;`** — E から新しい thunk を生成する。E が名前参照なら `thunk(a)`——**名前解決自体も強制の瞬間まで先送りされる**。
- **`b &= a;`** — a が現在指している thunk そのものを共有する。
- **`c ^= a;`** — a が現在保持している thunk の未評価の計算を複製する。複製対象の決定は `^=` の実行時点で即座に行われるが、中身の評価はなお遅延する。

#### 名前解決は常に解決時点の環境で行われる

thunk も関数本体も、**定義位置の環境を保持しない**。自由名は解決の瞬間の環境で引かれる。

```
let x := 1;
fn f () { x } -> i64;
{
    let x := 2;
    f()          % 2。宣言時の 1 ではない
}
```

**関数も動的スコープである。** クロージャを構成しないこと（§3.2）と同じ一点から出ており、thunk だけが特殊なのではない。

#### 「どの環境で強制するか」という問いは立たない

動的スコープと遅延評価を並べると、次の二択があるように見える——thunk の生成時点で環境を固定するのか、強制のたびに引き直すのか。実際に、この設計を読んだ4つの読み手のうち1つはここを**矛盾**だと判断した。

**どちらでもない。** メモ化により、**1つのセルは高々1回しか強制されない**。

| | |
|---|---|
| 生成時に環境を固定する | しない。それはクロージャである |
| 強制のたびに引き直す | 引き直す機会がない。強制は1回きり |

したがって「1セル = 1回の強制 = 1つの環境」であり、選ぶべき環境が複数現れない。`let` が再実行されれば**新しいセル**ができるので、関数を2回呼べば2つのセルが別々に強制される。

```
fn f () { let t := k + 1; t } -> i64;
fn g (k : i64) { f() } -> i64;
print(g(1));      % 2
print(g(10));     % 11
```

これは追加の規則ではなく、§4.6 の3つの性質（環境を捕捉しない・強制時に引く・強制後は値になる）から出る。

thunk についてはさらに次が出る：

```
let a := 5;
let b := a;
let c ^= a;

{
    let a := 999;
    write(1, $s, b.to_str());   % 999。b は名前 a を持つ
}
write(1, $s, c.to_str());       % 5。c は a の計算を持ち、名前から独立している
```

#### 無名関数が欲しくなる場面

クロージャは持たないが、用途別には次のように埋まっている：

| 用途 | 書き方 |
|---|---|
| 局所束縛（スコープ） | ブロック `{ … }`。ML の `let … in …` に相当し、構文の追加を要さない |
| 遅延（あとで計算） | `let` の thunk |
| パラメータ化・再利用 | `^=` + 自由名の遅延解決 |
| 高階（関数を渡す） | **できない**（制約3） |

3つ目は次の形になる。自由名が仮引数として振る舞う：

```
#[forward]
let template := n * 2;

let n := 5;
let a ^= template;
write(1, $s, a.to_str());       % 10

let n := 7;
let b ^= template;
write(1, $s, b.to_str());       % 14
```

### 4.7 ディスパッチは静的でなければならない

これが原則であり、以下はその帰結である。

**許される**

- **返り値型によるオーバーロード**（呼出側アノテーションで静的に決まる）。オーバーロードは返り値の型だけで区別し、引数の個数は常に一致することを要求する。解決とディスパッチは呼出側の責務であり、複数候補の比較なしに一意決定できなければならない（checking mode に完全に限定される）
- **レシーバの型によるメンバ関数の解決**（型が静的に決まる）

**禁じられる**

- **実行時の値によるディスパッチ**（文字列書式による分岐など）
- 関数境界を越える推論を必要とする解決（3.2節の関数内推論の制限）
- 候補を比較しないと決まらない解決

**期待型の伝播**：伝播元が非オーバーロードで一意に確定している場合にのみ許す。伝播元自体がオーバーロードされている場合はアノテーションなしを弾いてよい。

### 4.8 動的スコープ、ブロックとスコープの分離

#### ブロックとスコープは別物である

大半の言語はこの2つを同一視している。REod は分離する。

> `{ }` の意味は**1つ**——**値を産む文脈的領域（ブロック）**である。
> 巻き戻しの規律（スコープ）は、その括弧が**何に付いているか**が決める。

| 括弧が付いている先 | ブロックか | スコープの規律 |
|---|---|---|
| `if` / `else` | ○ | **付けない**（状態に対して透明。`break` に対しても透明） |
| `loop` / `while` / `ifor` | ○ | **チェックポイント**（下記） |
| `fn` | ○ | グループ（フレーム） |
| 何にも付いていない | ○ | グループ |

何も付いていない `{ }` がグルーピング構文であるという1点だけが規定である。TeX で `{ }` がグルーピング構文であることと同じで、恣意的ではない。

#### グループ

波括弧を抜ける際の巻き戻しは TeX のグルーピングと同型：**ブロック内で新たに行われた変更のみ**が対象。レジスタ層書き込みとヒープ書き込みに一様に適用される（**確保元によらず一様**）。

#### 状態には2種類ある

以前ここには「この規則は処理系のコンテキスト全般に統一して適用される」と書かれていた。**不正確だった。**

- **値の変更は蓄積する。** ループを回した結果はループの外で使う。だからチェックポイントの journal は正常脱出時に破棄され、変更が確定する（下記）
- **jump の跳び先は構造的である。** 開いていない構文の中を指す跳び先は、指す先が存在しないのと同じ。蓄積するものではない

したがって `comefrom` の登録だけは、チェックポイントを破棄するときにも**適用される**。3.9節の「跳び先は、それを含む構文が開いている間だけ生きる」はここから出る。

演算子宣言（1.7節）がどちら側かは未確定（5節）。

#### チェックポイント

ループ本体はスコープではない。**記録レベルを push するが pop しない。正常に抜けるときその journal は適用せず破棄する**——変更は確定する。jump が発火したときだけ適用される。

このレベルが存在する唯一の理由は、jump に巻き戻し先を与えることである。したがって：

- ループ内の非 global な蓄積はループを抜けても残る
- jump は依然としてループ本体の変更を巻き戻す
- **`continue` が巻き戻さないのは特別規則ではない**——そもそもブロックを抜けていない

#### `global`

`#[global]` でマークされた書き込みは最下層へ直接書き、**全 save level から当該セルの undo エントリを除去する**（TeX 方式）。したがって後続の pop は当該セルを復元しない。

**トップレベルのコードと global は区別しない**——トップレベルには巻き戻し先となる `{ }` が存在しないため、実質的に常に global 相当として扱われる。これは規定ではなく、レベルが1つしかないという条件からの帰結である。

#### jump の巻き戻し

`continue` 以外の jump（`goto`・`comefrom` による巻き戻り）は、実際に跨いだブロックの数に関わらず、発火するたびにその都度、非 global 状態をすべて一括で巻き戻す（単一チェックポイント方式）。journal を内側から適用して空にするが、**レベル構造そのものは pop しない**——「着地はカーソル移動以上の意味を持たない」ので、jump はブロック構造を変えず状態だけを戻す。

**降りられるのは現在の呼び出しフレームの底までである。** 関数の中のコードにとっての基準点は関数の入口である。ここより下まで戻すと引数束縛（フレームそのもの）が消える。

`break` は jump ではなく、この巻き戻しを引き起こさない。

### 4.9 値・領域・paradox

REod の中核。**規則は4行に尽きる。**

> 1. **領域はちょうど一つの値を持つ。** 内部に何も置かれていなければ、その値は **paradox** である
> 2. **`;`** は左の値を**評価してから**捨て、内部を空にする
> 3. **paradox は消さねばならない。** 消費するのは `;`、`??`、そして**ホスト**である

規範的な記述はこの3行で閉じている。この「空」に名前を与える必要はない。ただし**REod を正しく考えるための認知モデルには名前が要る**——付録A を参照。

規則1は式指向であることの帰結である。ブロックは式であり、式は値を持つ。したがって「値を持たない領域」は存在しない——内部が空なら、その値が paradox になる。

以下はこの3行の展開である。

#### 文脈的領域

領域は入れ子になる。被演算子の位置、ブロック、プログラム全体がそれぞれ領域である。ブロックより狭い。

```
[ [1] == [1] ]     左に1つ、右に1つ、全体に1つ
```

`==` は2つの領域を消費して自分の領域に1つ置く。値が2つ同時に見えても違反ではない——別の領域だからである。

```
{ [5] [6] }        1つの領域に2つ置かれる → 違反
{ [5;] [6] }       5 は潰されるので、置かれるのは1つ → 通る
```

被演算子の数は arity から、ブロックの項の数は `;` の有無から決まるので、**この規則は静的に検査できる**。

**丸括弧は領域を作らない。** 式をまとめるだけであり、項の列を持てない。`(1; 2)` は不正である。項の列を持てるのは波括弧だけである。

値は消費されなくてよい。消費されなければそのまま外側の領域の値になる。プログラム全体も1つの領域であり、その値がホストへ渡る（3.6節）。ソースが `1` だけのプログラムは `break 1;` と同じ結論を出す。

#### 空にすることは、何もしないことではない

`;` は**評価してから**捨てる。潰すには一度作らねばならない。

```
hoge()      何も起こさない
hoge();     hoge を呼ぶ
```

したがって `;` はこの言語の主要な強制点である（4.10節）。正格な言語では捨てることは意味論的に何も起こさないが、遅延評価の下では**捨てることが評価を起こす**。

**これが `;` を演算子にした理由である。** Rust のように「ブロックは末尾以外の項の値を捨てる」という規則にすれば `;` は区切り記号で済むが、遅延評価の下では**強制がブロックの暗黙の規則になる**。REod は強制点を字面に出す側を選ぶ。

副次的に、値が黙って消えることがなくなる（`1 2` はエラーになる）。

#### paradox

**paradox は値である。** 表示は `{}`。

出どころは2つ：

- 宣言（`let` / `fn` / `typ` / `flow`）と制御移動（`goto` / `continue`）が返す
- 内部に何も置かれていない領域の値として（規則1）

消費するのは3つ：

| | |
|---|---|
| `;` | 潰して内部を空にする |
| `??` | 代わりの値を置く（下記） |
| **ホスト** | プログラム全体の値として受け取り、「値なし」と解釈する |

**そのどれも起きないままその領域が使われればエラーである。**

ホストは領域ではないので、これは言語の例外ではなく**境界のプロトコル**である。`1; 2; 3;` だけのプログラムはトップレベル領域の値が paradox になり、ホストがそれを受け取って「何も返さなかった」と解釈する。

```
let x := 5        paradox が領域に残ったまま終わる → 不正
let x := 5;       akasha へ潰される → 正しい
```

**これが `;` の必然性である。**規定ではなく帰結である。

```
{ 5 }          値は 5
{ 5; }         中身は空 → 読まれる → paradox
{}             同上
```

**「記録できない」は独立した規則ではない。** 記録は値を領域の外へ持ち出すので、右辺の領域が終わる時点で paradox が残ることになる。同じ規則が全部を捕まえる：

```
let x := {};       右辺の領域が束縛の時点で終わる → 不正
f({})              引数の領域が呼び出しの時点で終わる → 不正
1 + {}             被演算子の領域が終わる → 不正
if {} { … }        条件の領域が終わる → 不正
```

> 以前ここには「paradox は実在できず、記録もできない」と書かれていた。**撤回した。** 実在できないものを一度作ってから型注釈で変換する、という説明は矛盾している。paradox は実在してよい。領域が終わる時点で残っていてはいけないだけである。

#### `{}` が paradox の表示である理由

akasha そのものは**何も書かれていないこと**である：

```

```

これを `{ }` で囲むと**領域になる**。領域は値を持つ（規則1）ので、内部が空なら値は paradox になる。

> **`{}` は、「内部が空の領域」を、そのまま字面にしたものである。**

型の表示に `{}` を使うのは記憶術ではない。paradox とは「内部に何も置かれていない領域の値」そのものであり、`{}` はその最小の書き方である。

#### `{ e1; e2 }` は「強制して捨て、次を返す」

`;` が強制を伴い、ブロックが領域の値を返すことから、次が出る。

```
{ e1; e2 }      e1 を強制して捨て、e2 の値を返す
```

Haskell の `seq` に相当する。式の位置で使える：

```
f({ side_effect(); 41 })
```

**専用の演算子は要らない。** 強制だけを行う機構が別に無いのは欠落ではなく、`;` とブロックの合成で得られるためである。

#### 文の位置のブロック式にも `;` が要る

規則4から出る。

```
if c { n := 5; };
loop { … };
while (c) { … };
```

`if` の枝が `;` で終われば枝の領域は空、それを波括弧が読むので paradox、それが囲む領域に置かれ、領域が終わる前に消さねばならない。

**ブロックを持つ式を文の位置で特別扱いしない。** 規則は「すべての項は値を残すか `;` で潰すか」の一つだけである。

これにより、今まで見えなかった区別が字面に出る：

```
fn f () { loop { … } } -> i64;      loop の値が返り値になる
fn f () { loop { … }; 0 } -> i64;   loop の値は捨てる
```

#### フォールバック演算子 `??`

paradox が生じたとき、代わりに置く値を書く。

```
E ?? F
```

E が paradox なら F、そうでなければ E。**F は必要なときだけ評価される**（`&&` / `||` と同じ短絡）。

```
d[k] ?? 0            キーが無ければ 0
d[k] ?? 0 - 1        キーが無ければ -1。**既定値でなくてよい**
if c { 5 } ?? 0      偽なら 0
nfor (i in 0..n) { … } ?? 0    範囲が空なら 0
{} ?? 0              0
```

優先順位は最低（`;` の直上）。E が paradox になりえない場合も書けるが、その F は到達しない。

> **撤回された設計**：「paradox に構文上書かれた型が付いていれば、その型の既定値になる」。
>
> これは型注釈に**値を生成する**という第2の仕事を負わせていた。`->` も `:` も本来「型を名指す／制約する」ためのものであり、無から値を作る操作ではない。§1.4 の単射原則に反していた。
>
> 加えて表現力が低い。既定値しか選べず、`-1` を返したい場合に書けなかった。
>
> `??` はこの2つを同時に解決する。**`->` と `:` は型を名指す仕事だけに戻る。**

**帰結**：`nfor` の `-> T` は「範囲が空のときの既定値を供給する」役割を失い、通常の型注釈になる（省略可）。D-9 の「範囲が空なら返り値型の既定値」も撤回され、`?? v` を書かなければ paradox のまま領域が終わる。

**帰結**：ハッシュマップの読み出しの推奨形が変わる。

```
let cur : i64 := d[ai];      欠損時に何が起きるか書かれていない → 不正
let cur := d[ai] ?? 0;       欠損時の値が書かれている
```

`?` は REod に null が無いことと衝突しうるが、この演算子が担うのは「値が無いときに何を置くか」であり、null 合体演算子と役割が一致する。

### 4.9.1 決まっているが暗黙だった規則

以下は実装が答えを持っていたが、仕様に書かれていなかったもの。

| | |
|---|---|
| **名前空間** | **1つ**。`let` / `fn` / `typ` / `flow` が同じ表を共有し、後の宣言が遮蔽する |
| **同名 `comefrom` の入れ子** | 内側の登録はブロック脱出で外側に復元される（save stack に載る） |
| **自己参照の検出** | 強制中フラグを持ち、循環を検出してエラーにする（`x := y; y := x;` など） |
| **`$repeat(op, 0)`** | 段数 0。終端をその場で実行する。負の段数はエラー |
| **`#[forward]` の範囲** | 名前の存在検査のみを抑止する。型解決には及ばない |
| **`$repeat(continue, n)`** | n 回 `continue` するのと同値。反復を n 個進める |

### 4.10 強制点

> 遅延が既定である。強制は**値が実在していなければならない地点**でのみ起きる。

| 強制点 | 実在が要る理由 |
|---|---|
| `;` | 潰すには一度作らねばならない |
| `#[immediate]` | 明示的な要求 |
| 関数の引数 | 呼ばれた側の局所束縛で自由名が引き直されてしまう |
| `+=` `-=` `*=` `/=` の左辺 | 現在値が要る |
| `break` の引数 | その時点の値でなければ意味が壊れる |

**虚無はこの双対である**——虚無が「実在の消去」なら、強制は「実在の要求」。

#### 複合代入は `:=` の糖衣ではない

```
x := x + 1;   % 発散する（自己参照 thunk）
x += 1;       % 動く
```

`+=` は左辺の現在値を即時強制してから演算する独立した演算子であり、`x := x + 1` への展開ではない。ほぼ全ての言語で `+=` は糖衣なので、この差異は明記しなければ裏切りになる。

「右辺に左辺の名前が現れたら強制する」という規則で統一すれば `+=` は本当に糖衣になるが、それは強制の起きる位置が書かれた記号ではなく名前の出現検査で決まることを意味する。処理順序を人間から隠蔽しないために、統一せず差異を明記する側を選ぶ。

## 5. 未解決・要確認事項

- **再束縛の糖衣**：`x := f(x)` は `#[immediate]` が要り、アトリビュートは行終端なので**1行の更新に2行**かかる。`+=` 族が埋めているのは「左辺の現在値を強制して合成」だけで、「右辺を強制して置換」が空いている。記号は未定——`:=` との関係が見え、かつ thunk を作らないとは示唆しない形であること。
- **演算子宣言はどちら側の状態か**：値のように蓄積するのか、jump の跳び先のように構造的なのか（4.8節）。ループ内で宣言した演算子がループの外で有効なままなのは、たぶん望ましくない。
- **`\def` 型の非メモ化オプションの要否**：TeX の `\def` が持つ「参照のたびに再評価する」性質に相当する束縛が必要か。`flow` が作用素についてはこれを提供している。
- **マクロ層**：当面仕様から外している。構想は「構文を自由にするための完全展開可能な TeX のサブセット」。定義は行頭 `\` から始まる行、改行終端（継続は行末 `%`）、呼び出しは任意位置。
- **演算子宣言の実装階層**：マクロ展開層の一部か、catcode のようにマクロ展開より手前（第3の層）か。
- **`f80` の実装**：Rust に f80 はない。ソフトフロートか x87 のインラインアセンブラが要る。`f32`/`f64` を先に入れて `f80` を後回しにすると 1.8節の理由が骨抜きになる。

## 付録A　akasha——「何もない」を対象として持つこと

本文の規則（4.9節）は「領域が空である」で閉じており、この付録は**規範ではない**。しかし **REod を正しく考えるための認知モデルには、これが要る**。

### REod は「何もない」を2種類区別する

| | REod | 例 |
|---|---|---|
| **値がない**（領域が空） | akasha | `5;` の後、`{}` の中身 |
| **値だが中身がない**（単位型） | **paradox** | 宣言が返すもの、空の領域が読まれたもの |

大半の言語はこの2つを1つに潰している。ML 系・Rust の `()` は「値がない」と「中身のない値」の両方を担う。

**潰したまま REod を読むと必ず外す。** 実際に、文脈を与えずに REod のコードを読ませた例では、`{ 5; }` も `{}` も `1; 2; 3;` も一律に「Unit/void」と読まれた。区別を持っていないので、`{ 5; }` を「無害な単位値」と解釈し、**「領域の終わりまでに消さねばならない」という規則に到達できなかった。**

したがって：

> 「何もない」を**対象として**扱えなければ、REod の規則は読めない。

規則を述べるのに名前は要らないが、**規則を理解するのに区別は要る**。

### akasha という名前

**akasha**（आकाश、アーカーシャ）。インド哲学の五大の一つで、**色を持たず形を持たない**もの。

| アーカーシャ | REod |
|---|---|
| 色を持たない | 型を持たない |
| 形を持たない | 値を持たない |

**含まれることがない**という性質も当たる。akasha は値ではないので、どこにも収まらない。収めようとすると——領域の値として見ようとすると——paradox になる。

以前は「akasha が残れるのはトップレベルだけ」という形でこの対応を述べていたが、規則が「領域はちょうど一つの値を持つ」に整理された結果、**例外なしの形になった**。名前は「色も形もない」を根拠に選ばれたが、この性質は独立に導かれたものであり、**名前が後から規則を予測した**ことになる。

神智学の Akashic records（起きたことすべてを記録する書庫）は語を借りただけの別概念であり、**保持**を指すので方向が逆になる。ここで借りているのは元の五大の一つの方で、「それ自身は何の質も持たない」という性格だけである。

`void` / `never` / `unit` / `nil` を採らないのは、いずれも既存言語で**型**の名前として使われており、akasha が型でないことと衝突するためである。`lethe`（忘却）も検討したが、あれは「存在したものが消される」という**操作**を指すので `;` と役割が重なる。名詞が要るのは行き先の状態の方である。

### 輪廻とカルマ

4.9節の規則は次のように言い換えられる。

| 段階 | REod |
|---|---|
| 値がある | 領域が値を持つ |
| 溶ける | `;` が内部を空（akasha）にする |
| 形なきものが形を要求される | 領域はちょうど一つの値を持たねばならない（式指向） |
| 業なき再生は成立しない | その値は **paradox**。消さねばならない |
| **カルマ**が色と形を決める | **`??`** が代わりの値を置く |

akasha は色（型）も形（値）も持たない。カルマを得て初めて色と形を持って再び現れる。

**`??` への変更で、この対応はむしろ正確になった。** カルマは元来**行為**であり、属性ではない。以前の「型注釈が暗黙に既定値を与える」は受動的すぎた。`??` は書き手が選んで置く行為であり、選んだものがそのまま結果になる。

なお**遷移は一つしかない**。`;` が内部を空にすることだけが出来事であり、領域の値が paradox になることはそこから**従う**——観測や相転移のような二つ目のイベントは無い。以前の版には「値位置で読まれると paradox が生じる」という第二の遷移があったが、その「読む位置」の一覧が恣意的だったため（なぜその4つなのかを説明できなかった）、4.9節の整理で消えた。

### この付録が目的としないこと

akasha を置く理由は、**この区別が実在し、既存の語では余計な荷物を持ち込まずに名指せない**ことである。

**読者を揺さぶることではない。** 異質な語で認知を強制する、という使い方は、名前を心理的効果のために用いることであり、「簡単に見せるために区別を消す」のと同じ範疇の操作である——向きが逆なだけで、どちらも名前を道具にしている。

この付録が付録であること自体が、その証拠になっている。異化が目的なら、規則の中心に置かねばならない。4.9節は akasha という語を用いずに閉じており、それで困らない。

### この付録の位置づけ

- **規則ではない。** 4.9節は akasha という語を用いずに閉じている
- **エラー表示にも現れない。** ユーザーが見る型は paradox（表示は `{}`）だけである
- **要るのは、規則がなぜそう組み合わさるかを一息に掴むときと、「何もない」が2種類あることを見落とさないためである**

## 付録B　Rust との関係

本書の読者は Rust を知っている可能性が高い。この付録は**優劣を立てるためではなく、Rust を基準に REod を速く読むため**にある。

REod は Rust の反対物ではない。**同じ問いに、違う制約の下で答えている**部分と、**同じ原則をより厳しく適用した**部分と、**Rust が払っていない代償を払っている**部分がある。順に。

### 共有しているもの

- **導入した概念を裏切らない。** REod の制約1・4はこの系譜にある
- **隠れた制御フローを増やさない。** どちらも例外機構を持たない
- **暗黙を嫌う。** 暗黙の変換も暗黙の複製も持たない

### 同じ原則から、違う答えになったもの

制約が違うので答えが違う。どちらかが間違っているのではない。

| 問い | Rust | REod | 制約の違い |
|---|---|---|---|
| 評価戦略 | 正格 | 遅延 | Rust は予測可能な性能が要る。REod のホストは読み取りと実行が同時に進む |
| 名前解決 | レキシカル | 動的 | Rust はクロージャと所有権のためにレキシカルが要る。REod は thunk が環境を捕捉しない（クロージャ不採用の帰結） |
| 「値がない」と「単位値」 | `()` に統一 | akasha と paradox に分離 | 正格なら区別が観測できない。**遅延の下では「作られなかった」と「作られたが空」が別の挙動になる** |

3行目が REod の最も Rust らしくない部分であり、しかも**遅延評価から導かれている**。順を追うと：遅延評価 → 捨てることが評価を起こす → `;` は区切りでなく演算子 → 領域という概念が要る → 「空」と「単位値」が別物になる。恣意的な形而上学ではない。

### REod の方が厳しいもの

**`;` に例外がない。** Rust は `if` / `match` / `loop` / ブロックを文の位置に置くとき `;` を要求しない（`ExpressionWithBlock`）。これは意図的な人間工学上の選択である。REod はこの例外を持たない——`;` が「評価して捨てる」という**観測可能な操作**である以上、省ける場所を作れない。

**脱出機構が少ない。** Rust は `return` / `break` / `break 'label` / `break value` / `continue` / `continue 'label` / `?` を持つ。REod は `break` の段数と `continue` だけで、`return` は標準ライブラリの1行に落ちる（1.6節）。

ただし**これは規律の差だけではない。** REod はエラーを値として扱わないので `?` に相当する必要がそもそも無い。少ないのは、必要が少ないからでもある。

### REod が払っている代償

Rust を好む読者が最も気にする点を、隠さずに挙げる。

**1. 隠れた制御フローを許している。** `comefrom` は「上から読んでも流れが追えない」構造であり、Rust なら決して入らない。REod はこれを**禁じる代わりに宣言する**——1.5節が「静的解析の対象外」と明記している。隠すことと、隠したと認識していることは別、という立場を採っている。しかし読み手にとって追いにくいことは変わらない。

**2.「コンパイルが通れば動く」が成立しない。** REod は**読み取り時検査**であり、`goto` で読み飛ばされた区間は永遠に検査されない（1.5節）。実行されない分岐の型エラーは本番まで残る。Rust の全体検査に慣れた目には最も落ち着かない点だと思う。

**3. エラーが値にならない。** ADT を持たないので `Result` に相当するものが構成できない。失敗は即座にホストへ伝播し、REod のコード内で回復できない（3.6節）。ホスト側の設計に負荷を寄せている。

**4. リファクタリングが安全でない。** 名前解決が動的なので、`let` を自由名の再束縛を跨いで移動すると結果が変わる。Rust のレキシカルスコープが与える「移しても意味が変わらない」保証は無い。

### 一つ、Rust の方が一貫している点

**`{ }` の扱い。** Rust のブロックは一様である。REod の `{ }` は3つのスコープ規律を持つ（`if` は透明、ループはチェックポイント、裸と関数はグループ。4.8節）。4.8節はこれを妥協として明記しているが、Rust に対する優位を語るならこの行も並べるべきである。

### まとめ

> REod は Rust の原則を受け継ぎ、Rust が受けていない制約の下で別の答えに至り、Rust が払っていない代償を払っている。

Rust の例外は、出荷可能なシステム言語であるための人間工学上の判断である。REod は埋め込み・小規模・狭い対象読者という条件の下にあり、その判断を必要としない。**条件が違うだけで、Rust の選択が誤りだったのではない。**
