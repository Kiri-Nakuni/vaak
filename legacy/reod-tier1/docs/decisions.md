# 設計判断ログ（設計書からの差分）

`言語設計書.md` / `コード例集.md` に対して確定した変更・補足。設計書本体を更新する際の差分元。

**言語名は REod**（read と同じ発音、"REod means just read"）。拡張子は `.reod`。設計書中の「言語名は未確定」を差し替えること。

## 確定した意味論

### D-1. スコープ（`{ }`）の生成規則は一様ではない

| 位置 | スコープを作るか |
|---|---|
| `if` / `else` の本体 | **作らない** |
| 裸の `{ }` | 作る |
| `loop` / `ifor` / `while` の本体 | 作らない（チェックポイントを作る、D-2r） |
| 関数本体 | 作る |

3つの挙動の詳細は D-23 の表を参照。

`if` が状態に対して透明であることは、§4.2 が comefrom トリガーを「トップレベルと `if` の中」に限って許している理由そのものになる。この2つは同じ規則の別の顔。

**帰結**：設計書 §3.5 の `comefrom retry` の例は、`retry_count += 1;` が `if` の中でもトップレベル扱いのままなので、jump 巻き戻しの影響を受けない。**例は正しく、修正不要**。

### ~~D-2~~（撤回）→ D-2r. ループ本体はスコープではなく**チェックポイント**

> **撤回された D-2**：「ループ本体のグループは入口で1回 push、`comp`／`break` 値の強制の後に pop」。
> これは設計書 例1（`ifor` で `total` を集計し `comp` で印字する）を壊しており、
> さらに関数層で致命的になった——関数内でループを回して集計すると脱出時に巻き戻り、
> `#[global]` で逃がすと関数の外へ漏れて再帰が壊れる。

正しい読みは §4.8 の「**実際に跨いだブロックの数に関わらず**…一括で巻き戻す（単一チェックポイント方式）」の方。ループ本体が作るのはスコープではない：

> ループ本体は記録レベルを push するが、**pop しない**。正常に抜けるときその journal は**適用せず破棄**する——変更は確定する。jump が発火したときだけ、全レベルの journal が適用される。

このレベルが存在する唯一の理由は、jump に巻き戻し先を与えること。

**帰結**：

- ループ内の非 global な蓄積はループを抜けても残る（例1 の `total`、関数内のカウンタ）
- jump は依然としてループ本体の変更を巻き戻す（例6 の `x`）
- §4.8 の「`continue` は巻き戻しの対象外」は特別規則ではなく、**そもそもグループを抜けていない**という自明な帰結になる
- ループ本体はスコープを作らないので、`let` はループの外へ漏れる（`if` と同じ、D-1）

### D-3. ヒープ書き込みも巻き戻しの対象

レジスタ層と同じ規則。`a[i] := v` の巻き戻し挙動は確保元によらず一様。

**帰結**：設計書 §3.4 の `getroot` はブロック内で経路圧縮しているため、`global uf.parent[idx] := ...` でなければ圧縮が消える。**コード例が誤り**。

### D-4. `global` は TeX 方式

`global` 書き込みは最下層へ直接書き、**全 save level から当該セルの undo エントリを除去する**。したがって後続の pop は当該セルを復元しない。

### D-5. jump の巻き戻しは全レベルを global 基準点まで適用するが、レベル構造は保存する

undo ジャーナルを内側から順に適用して空にするだけで、グループの入れ子自体は pop しない。§4.1 の「着地はカーソル移動以上の意味を持たない」——jump はブロック構造を変えず、状態だけを戻す。

### D-6. `#[forward]` は不動点コンビネータではない。ただし**不要ではない**

クロージャなしで Y コンビネータは構成できない（`f` を捕捉した関数値を作れないため）。自己適用による回避形も、関数を第一級の値として引数に渡せることと再帰的な関数型を要求するので通らない。

**しかし機構としては不要**。§4.6 の「名前解決は強制の瞬間まで先送りされる」により、関数本体が実行される時点では対象の束縛が存在するので、**再帰は動的機構なしで動く**。

> `#[forward]` は、**名前の存在チェックを抑止する属性**である。不動点コンビネータを生成するものではない。

**ここが重要**：`#[forward]` がなければ、未知の名前は即座にエラーになる（D-30）。「不動点コンビネータが不要」であることと「`#[forward]` が不要」であることは別。抑止する対象が動的機構ではなく静的検査だというだけで、抑止そのものは要る。

ただし D-30 で検査範囲を `let` の右辺だけに限定したので、**関数の再帰（自己・相互とも）には `#[forward]` は不要**になった。`#[forward]` が要るのは相互参照する**値**の束縛だけである——設計書 §3.3 が `#[forward]` を束縛の節に置き、値の例（`f := g; g := f;`）で説明しているのと一致する。

設計書 §3.3 の「不動点コンビネータを自動生成し」は誤り。§5 の未解決事項「クロージャなしでの不動点コンビネータの内部機構は未検討」は問題ごと消滅するが、`#[forward]` 自体は残る。

なお `#[forward]` を値の束縛に付けると本物の発散になりうる（`#[forward] let x := x + 1;` は検査を抜けたうえで自己参照 thunk になる）。設計書 §3.3 の例 `#[forward] f := g; g := f;` はこれに該当し、強制すると無限ループする。`fn` の相互再帰の例に差し替えること。

## 確定した構文変更

### D-7. 剰余は `mod`

`%` はコメント専用。TeX 互換を明示目的に据えている以上 `%` は譲れない。

### D-8. 呼出側の型アノテーションは `->`

```
let uf := make(n) -> uf_tree;
```

§4.7 でオーバーロード解決が返り値型だけ・checking mode 限定と確定しているので、呼出側が指定できるのは常に返り値型。宣言側の `-> u64` と意味が一致する。

> **`->` は返り値型を名指す。** 宣言位置でも呼出位置でも同じ意味。

これにより `:` の多義は「束縛子への型注釈」1つに減る（`parent : i64 array` / `size : u64`）。`typ counter : { ... }` の `:` は情報を運んでいないので**削除**し、`typ counter { ... }` とする。

文法上の曖昧さはない（`f(x) -> T + 1` の `T + 1` は型として読めないので `(f(x) -> T) + 1` に一意）。

### ~~D-9~~（一部撤回）. `nfor` の値は最後の周回の末尾式

値は**最後の周回の末尾式**。ここは有効。

> **撤回**：「範囲が空の場合は返り値型の既定値」。
>
> D-63 のフォールバック演算子により、`->` は既定値を供給しなくなった。範囲が空なら paradox のままであり、`?? v` を書かなければ領域の終わりでエラーになる。`nfor` の `-> T` は通常の型注釈（省略可）に戻る。

### D-10. `&=` / `^=` は `let` の省略が不正

新規導入（`let x &= y;`）と再束縛（`x &= y;`）を区別する。設計書 §3.3・§3.7 の `let` なしの記述は「再束縛」の例として読む。

### D-11. 標準形（CNF/DNF）制限を撤廃

意図は短絡評価の明示だったが、短絡は `&&`/`||` 自身の性質であり標準形とは独立。「`&&`/`||` は短絡評価する」と書けば足りる。`while` と `if` の非対称も同時に解消。

### D-12. 文字列は `u8 array` の構文糖

独立した型ではない。

### D-13. エラーは値にならない

§3.6 の「Zig のエラーモデルを参考」は誤解を招く。Zig の error union はタグ付き共用体であり、ADT を持たない本言語では構成できない。**エラー値は存在せず、即座にホスト（TeX）へ伝播する**、と積極的に書く。

### D-14. 多相禁止は「ユーザーが書けない」の意

`Array.init` 等の組み込みコンストラクタは任意の要素型を返す必要があるため多相。禁止されているのはユーザー定義の多相であることを明記する。

### D-15. `T U hashmap` の引数順は `T array` からの導出

`T array` が「u64 キーで T 値」なら `T U hashmap` が「U キーで T 値」なのは導出される。設計書に **`T array` ≡ `T u64 hashmap`** と書けば順序の理由が自明になる。`pair` は写像ではなく直積なので別カテゴリ——揃わないのが当然、という整理。

### D-16. マクロ層の字句規則

- **定義**は行頭 `\` から始まる行。改行で終端（継続は行末 `%`、TeX と同一機構）。
- **呼び出しは任意位置**。式の途中でも展開できる。
- 処理順は マクロ → アトリビュート。両者とも改行終端なので `#[...]` と `#1` は競合しない。

## 実装して初めて出てきた論点

### D-17. 左辺が右辺に現れる代入は、デフォルトでは書けない

`x := x / 2;` は「x を x/2 で更新する」ではなく、**`x / 2` というトークン列を指す thunk を `x` に束縛する**。§4.6 の「名前解決自体も強制の瞬間まで先送りされる」により、強制時に `x` を引き直して自分自身に到達し、発散する。

回避手段は2つ：

- `#[immediate] x := x / 2;` — 強制は束縛の**前**に起きるので、右辺の `x` はまだ旧束縛を指している。
- `x -= 3;` のような複合代入 — 現在値を先に強制してから演算する。

**複合代入（`+=` `-=` `*=` `/=`）が現在値を即時強制することは、この帰結を回避するために必須**であり、遅延にはできない。設計書 §3.3 は束縛演算子として `:=` `&=` `^=` しか挙げておらず、複合代入は例の中にしか現れていないので、正式に規定する必要がある。

なおこれは、設計書 §4.6 の意味論から機械的に導かれる帰結であって、追加の設計判断ではない。

### D-18r. アトリビュートはリストで書き、行末で終端し、**次の行**を修飾する

```
#[global, immediate]
x := x / 2;
```

`global` はキーワードではなくアトリビュート。`#[immediate]` と同じく「束縛のされ方」を修飾するものであり、TeX の `\global` プレフィックスに相当する枠に属する。`global` は予約語ではなくなる。

アトリビュートの意味論は「**次の行の評価方法・戦略を変更する**」の一つに単純化される。したがって：

- 複数指定はリスト（`#[global, immediate]`）で書く
- アトリビュートは**行末で終端**する。修飾する文を同じ行に続けることはできない——続けられると「次の行を修飾する」が嘘になるため（PHECL：Syntax は Semantic を誠実に示唆しなければならない）

### ~~D-19~~（撤回）. `global` は `immediate` を含まない

> **撤回された D-19**：「`global` は `immediate` を含む」。
> 根拠は「遅延したまま global にすると、強制側のスコープの状態で計算された値が
> メモ化されて全域に残る＝壊れている」だった。

**しかし設計書 §4.6 の例は、まさにその挙動を機能として提示している**——`b := a` がブロック内で 999 に強制される、あれである。scope-dependent な強制がそこでは特徴であるなら、global でだけそれを「壊れている」と判定するのは、設計者がユーザに代わって価値判断したことになる（PHECL 5・6）。

`global`（書き込みレベル）と `immediate`（評価時点）は**直交する2つの操作**であり、束ねない。同時に指定したければ `#[global, immediate]` と明示的に書く。戒1の例外条項——「ユーザ自身がその差異を同一視することを選択し、それを明示的に記述できるならば」——がこれに対応する。

D-2r 導入後は束ねる実利もほぼ消えている。`#[global]` が要るのは本物のスコープ（裸のブロック・関数本体）を越えるときだけで、`+=` は元から左辺を即時強制するため、実際に両方要るのは `#[global] x := <x を含む式>` の形だけ。

なお、トップレベルの束縛はレベルが1つしかないため元から global 相当（§4.8）。

### D-20. 関数の引数は呼出側で即時強制する

thunk は環境を捕捉しない（クロージャなし）ので、遅延したまま渡すと引数の式の自由名が**呼ばれた側の局所束縛**で引き直される。`f(x)` を `fn f (x : T)` に渡した時点で `x` が仮引数を指し、自己参照 thunk になって発散する。

**訂正**：当初これを「名前空間を跨ぐから」と説明したが、REod に名前空間は存在しない。「スコープを跨ぐから」でもない——§4.6 の例（ブロック内で `b` が 999 に強制される）はスコープを跨いでも強制せず、それが機能だからである。

正確な理由は**引数渡しに固有**である：

> 呼ばれた側の局所束縛（仮引数、本体の `let`）は、呼出側から見えないし**見えるべきでもない**——それは関数のインタフェースではない。遅延した引数はそれらを自由名の解決先として引き込むので、局所束縛が事実上インタフェースの一部になってしまう。

名前の衝突が実際に起きるかは呼ばれた側の内部に依存するので、遅延を許せば**仮引数を改名しただけで評価戦略が変わる**。一律に強制するしかない。

なお D-17（自己言及代入）は近いが別物である。あちらは同一スコープで、thunk の自由名と束縛先の名前が一致することによる。共通するのは「thunk が環境を捕捉しないことの帰結」という点だけで、機構は違う。

つまり **クロージャ不採用（§3.2）から引数の即時評価が導かれる**。

### D-21r. 関数定義は**改行**で終端する

```
fn add (a : i64, b : i64) { a + b } -> i64
```

返り値型は後置 `->` の後に型が並ぶが、型は後置形式（`i64 array`）で識別子の列なので、終端がなければ後続の文の先頭の識別子を型として吸い込む。

> **撤回された D-21**：`;` を要求する。
> これは PHECL 8（実行器の都合で、人間が使える構文を制約しないこと）違反だった——
> `;` が必要だった理由は「パーサが型の終端を決められないから」であり、
> 設計書 §3.4 の記法を実装の都合で変えたことになる。

改行で終端すれば型名表がなくても切れる。設計書 §3.4 の記法をそのまま使える。D-18r（アトリビュートの改行終端）と同じ規則であり、この言語が行志向であること——TeX の `%` による行継続と同じ系譜——の一部として一貫する。

### D-23. `{ }` は3つの意味を持つ（妥協として明示する）

| 位置 | レベルを push するか | 正常脱出時 | jump 時 |
|---|---|---|---|
| `if` / `else` の本体 | しない | — | 巻き戻さない |
| `loop` / `ifor` / `while` の本体 | する | **破棄**（変更は確定） | 適用 |
| 裸の `{ }` ・関数本体 | する | **適用**（TeX のグルーピング） | 適用 |

同じ `{ }` に3つの意味があり、差異は文脈から解決される。これは §1.4（ビールジョッキ思想）と PHECL 5・6 に反する。§1.4 が `label` について用いた解法——「単一の規則が参照する状態が文脈で変わるだけ」——はここでは使えない。**規則そのものが3つある。**

統一は試みたが不可能だった：`if` にチェックポイントを持たせると §3.5 の comefrom retry 例が無限ループになり（`retry_count` が巻き戻る）、`loop` からチェックポイントを取ると例6 が壊れる。3つは実質的に必要。

**これは妥協である。**記法で区別する（3種類の括弧を使う）方が原則には忠実だが、可読性の代償が大きいと判断した。PHECL は「隠蔽することと、隠蔽したことを認識していることは別」と言う。ここでは隠蔽しないことを選び、上の表を仕様の一部として明記する。

### D-24. `+=` は `:=` の糖衣ではない

```
x := x + 1;   % 発散する（自己参照 thunk、D-17）
x += 1;       % 動く
```

`+=` は**左辺の現在値を即時強制してから**演算する独立した演算子であり、`x := x + 1` への展開ではない。ほぼ全ての言語で `+=` は糖衣なので、この差異は明記しなければ確実に裏切りになる（PHECL 3、および「Syntax は Semantic を誠実に示唆しなければならない」）。

「右辺に左辺の名前が現れたら強制する」という規則で統一すれば `+=` は本当に糖衣になるが、それは PHECL 7（処理順序を人間から隠蔽しない）に反する——強制の起きる位置が、書かれた記号ではなく名前の出現検査で決まってしまう。よって統一せず、差異を明記する側を選ぶ。

設計書 §3.3 は束縛演算子として `:=` `&=` `^=` しか挙げておらず、複合代入は例の中にしか現れない。正式に規定すること。

### D-25. 制約2の書き方を修正する

現行：「束縛はデフォルトで遅延評価（memoizing thunk）される」。

しかし関数引数は即時強制される（D-20）。これを後から「例外」として提示するのは、「学習した事実は汎化されてよいが、嘘であってはならない」に反する。最初から正しく書く：

> 束縛はデフォルトで遅延評価される。ただし thunk は環境を捕捉しないので、関数の引数として渡すと自由名が呼ばれた側の局所束縛で引き直される。呼ばれた側の局所束縛は関数のインタフェースではないので、引数は強制される。

これは例外ではなくクロージャ不採用からの帰結なので、制約2の本文に組み込める。

### D-26. `return` は存在しない

§4.8 の「`break`/`return` は jump とは区別され」という記述は、存在しないものを導入している。`break` のみに直すこと。

`return` が要らない理由は「末尾式があるから」ではなく、**`break` がすでにその役割を果たすから**である（D-28）。

### D-28. `break` は**そのブロック**の値を正格に束縛し、ブロックを終了する

ループ専用の構文ではない。単一の意味論：

> `break E;` は、E を**正格に**評価してそのブロックの値とし、ブロックを終了する。

したがって：

| 位置 | 効果 |
|---|---|
| `loop` の本体 | ループ式の値になる |
| 関数本体 | **関数の返り値になる**（＝`return` の代わり） |
| 式としての裸の `{ }` | そのブロックの値になる |

`if` / `else` の本体は状態に対して透明（D-1）なので、**`break` に対しても透明**である——素通しして、その外側の本物のブロックが受け止める。逆に裸の `{ }` は本物のブロックなので、その中の `break` はそこで止まり、囲むループには届かない。

「正格に」の部分は §4.8 が既に書いている（「`break` の引数は自動的に強制評価される」）。D-28 はその適用範囲をループから全ブロックへ広げただけで、規則そのものは増えていない。

### D-29. `continue` は存在する。ただし巻き戻さない

`continue` はループの次の周回へ移る文である。jump ではあるが、**ブロックを出ないので**非 global 状態の巻き戻しは起きない。

D-2r 導入後、これは規則ではなく帰結になる——ループ本体のチェックポイントは `continue` では適用されない（そもそも抜けていない）。§4.8 の「`continue`（ループの暗黙の反復）以外の jump は…」という但し書きは、規則の除外項ではなく事実の確認として読める。

`goto` で同じ場所へ飛ぶと巻き戻るが、`continue` では巻き戻らない。この差は「ブロックを出たか」だけで決まる。

### D-31. jump の巻き戻しは呼び出しフレームの底で止まる

関数本体の中で jump が発火したとき、巻き戻しを level 0 まで降ろすと**引数束縛ごと消える**——関数のスコープレベルに記録されているため。フレームそのものが壊れる。

> 関数の中のコードにとっての「global な基準点」は、**関数の入口**である。

§4.2 は「`label` が `goto` の着地点として機能すること自体は禁止しない」と明言しており、関数内 `goto` は動くことを前提にしている。§4.8 は関数を考慮していないので、これは追加規定になる。

### D-32. `match` を `switch` に改名する

ADT を持たない（§3.2）以上、判定できるのは数値など言語が直接比較できる値だけであり、**これはパターンマッチではない**。`match` という名前は、存在しない destructuring や網羅性検査を示唆してしまう。

PHECL 3（構文上の名称や分類を、実際の計算上の意味から不必要に乖離させないこと）の直接の適用。`switch` は「値で分岐する」以上のことを約束しない。

### D-30. 名前の存在チェックは `let` の右辺だけに適用する

`let x := E;` は E の評価を遅延するので、未知の名前のエラーが「いつ強制されたか」に依存して現れる。**エラーの出るタイミングを評価戦略から独立させる**ため、束縛の時点で E 中の名前の存在を検査する（§3.3 の「通常は前方参照を認めない」）。

`#[forward]` はこの検査**だけ**を抑止する。

**`fn` の本体は検査しない。** 定義時に本体を検査すると、`goto` で読み飛ばされる区間に未定義の名前があってよい（§4.3、例4）という中心的な性質と衝突する——どの `goto` が発火するかは静的に決まらないので、この衝突は回避できない。

```
fn solve (n : u64) {
    if use_fast == 0 goto fallback;
    fast_module.accelerated_solve(n);   % 存在しなくてよい
    goto done;
    label fallback;
    naive_solve(n)
    label done;
} -> u64
```

**帰結**：

- 自己再帰・相互再帰は `#[forward]` なしで動く（本体が検査されないため）
- `#[forward]` が要るのは相互参照する**値**の束縛だけ——設計書 §3.3 が `#[forward]` を束縛の節に置き、値の例（`f := g; g := f;`）で説明しているのと一致する
- `#[forward]` を `fn` に付けるのはエラー。抑止するものがないので、受理すれば嘘になる
- `fn` 本体のタイプミスは呼び出し時まで見つからない。§1.5 が「`comefrom` の名前解決は実行履歴に依存するため静的解析の対象外」と既に宣言しているので方針としては一貫するが、**「`fn` 本体は静的に検査されない」と明記すること**

検査の対象外とする識別子：予約語、アトリビュート `#[...]` の中身、`goto`/`label`/`comefrom` の直後のラベル名、`->` の直後の型名、そして走査中に `let` / `in` で導入された名前。

### D-27. 関数定義は `let` ではなく `fn`

```
fn add (a : i64, b : i64) { a + b } -> i64
```

`let` による値の束縛と関数定義は、次の3点で別の操作である：

- **束縛種が違う**：関数は第一級ではない（`let g := f;` は不正）。値とは別の束縛種に入る
- **終端規則が違う**：`let` は `;`、関数定義は改行（D-21r）
- **評価戦略が違う**：`let` は thunk を作る（遅延）が、関数定義は本体のトークン範囲を記録するだけで thunk ではない

同じ `let` に載せることは、異なる操作を同一構文へ押し込んで差異を設計者が暗黙に解決することにあたる（PHECL 5・6）。`fn` に分けることで、D-21r で生じていた「同じ `let` が2つの終端規則を持つ」という非対称も同時に解消する。

### D-35. 出力は中核には `write` だけ。`print*` 系はすべて糖衣

```
write(fd, 書式, 引数...)
```

第1引数は POSIX のファイルディスクリプタ、第2引数は**レンダリング方針**、第3引数以降は結合される。

**書式引数は「型タグ」ではなく「レンダリング方針」**（読み方B）。各引数は**自分の静的型に応じて**その方針でレンダリングされるので、型の混在した出力を1回の呼び出しで書ける：

```
write(1, $s, "count: ", n);
```

`$s` はテキスト表現（`u8 array` はそのまま、整数は10進）、`$x` は16進表現。方針は引数の型から導けないので、書式引数は実際に情報を運ぶ——`.to_str()` との二重にはならない。`.to_str()` は「文字列を組み立てたいとき」の関数として役割が分かれる。

**書式トークンは文字列ではなく字句トークン**（`"%s"` ではなく `$s`）。文字列リテラルは `u8 array` の**値**なので、`"%s"` を使うと実行時の値でディスパッチすることになり、静的ディスパッチの原則（D-36）に反する。加えて `"%s"` は printf の見た目を借りるので、実際には行わない位置指定の埋め込みを示唆してしまう（PHECL：Syntax は Semantic を誠実に示唆しなければならない）。`$s` は何も示唆しないので自由に定義できる。

**`write` は引数を左から順に評価しながら出力する。** 中間バッファを作らないので制約1を満たす。途中の引数の評価が失敗すれば、そこまでの出力は既にストリームへ出ている——これは隠すべき欠陥ではなく観測可能な事実であり、PHECL 7（処理順序を人間から隠蔽しないこと）と TeX の `\write` の挙動に一致する。

**`write` は値を返さない。** POSIX の `write(2)` は書けたバイト数を返すが、REod は §3.6 により失敗を値で表現しない（ホストへ伝播する）。名前を借りている以上、**返り値を持たないことを仕様に明記する**。

TeX との対応表（§0 の目的のため）：`\write16` ＝ 端末 ＝ fd 1。

### D-36. 原則は「ディスパッチが静的であること」。§4.7 は書き換える

§4.7 の「オーバーロードは返り値の型**だけ**で区別する」は、原則の不誠実な定式化だった。本当の原則は：

> **ディスパッチは静的に決まらなければならない。**

これを原則として書き、規則をその帰結として並べる。

**許される**

- レシーバの型によるメンバ関数の解決（型が静的に決まるため）
- 返り値型によるオーバーロード（呼出側アノテーションで静的に決まるため）

**依然として禁じられる**

- **実行時の値によるディスパッチ**（`"%s"` のような文字列書式がここに落ちる）
- 関数境界を越える推論を必要とする解決（§3.2 の関数内推論の制限）
- 候補を比較しないと決まらない解決（checking mode 限定）

`read` は返り値型オーバーロードの**原型例**である。引数を取らないので引数による解決が原理的に不可能であり、§4.7 が返り値型に絞った動機はここにある。設計書にそう書けば規則が恣意的でなくなる。

### D-37. 中核仕様と標準ライブラリの層を分ける

`str` は `u8 array` の別名であり、**中核ではなく、無名で必ず読み込まれる標準ライブラリ**として定義される。`printstr` / `printi32` 等も同様に `write` の糖衣。

層構造そのものは PHECL と緊張しない。ただし PHECL が課す条件は具体的である：

- **脱糖を字句どおり仕様に書く。** 「存在する」だけでなく「書かれている」こと
- **層の境界を節として明示する。** 機能の一覧ではなく境界の宣言
- **中核の形を直接書けること。** `write` はいつでも自分で書ける

> 抽象化を使う自由と、抽象化を剥がす自由の双方を人間に残すこと。

**帰結：メンバ関数はユーザーも定義できなければならない。** `.lower()` が標準ライブラリなら、標準ライブラリはこの言語で書かれるので、言語がメンバ関数の定義構文を持つことになる。持っているならユーザーにも書ける。§3.2 の多相禁止により、メンバ関数も単相——`u8 array` 用と `i64 array` 用は別々に書く。

機構（メンバ関数のディスパッチ）は中核、個々のメソッドは標準ライブラリ。

**エラーメッセージは両方出す。** 別名である以上 `u8 array` が正確だが、書き手が `str` と書いたなら `str` と返す方が親切。`str (= u8 array)` の形で両方示す。

### D-33. `getdepth() -> u32`

現在のフレーム内で開いているブロックの数。すなわち、**この関数（トップレベルならプログラム）を抜けるのに `break` を何回重ねる必要があるか**。

`break` が吸収されるレベルだけを数えるので、`if` / `else` の本体は入らない（D-28 で本体が break に対して透明だと決めたため）。**`getdepth()` と `break` が同じものを数えなければ、この対は役に立たない。**

関数境界を越えないので、呼び出しの外側の深さは見えない。

### D-34. `break` は入れ子にできる

```
{
    {
        break break 2;
    }
}
```

`break E` が「E を値としてこのブロックを終える」なら、その `E` 自体が `break F` であることは、**もう一段外へ運ばれる値だ**ということ。重ねた回数だけブロックを抜ける。D-28 の意味論から自然に出るので、新しい規則ではない。

`if` / `else` の本体は透明なので段数を消費しない（D-28）。

**`break` は関数境界を越えられない。** 越えると呼び出し式の評価途中への制御移動になる（式の中の `loop` から `goto` できないのと同じ制約）。黙って打ち止めにするのは嘘なのでエラーにする。

**設計判断の根拠**：

> 「胸元まで撃ち抜く自由」だけを与えて規律を組む手段を与えないなら、それは自由ではなく放置である。**危険にだけでなく、安全にも自由がなければならない。**

`getdepth()` と `break` の入れ子があれば、ユーザーは望めば自分で `return` を書ける。言語がそれを組み込みで与えるのではなく、**組み立てられる材料を隠さない**という形で応える。§1.6 の「足元を撃つ自由」と対になる原則として記録する。

**未解決**：`break break E` の段数は**静的**である（`break` を書いた回数）。一般の `return`——「今いる深さがいくつであれ関数を抜ける」——を書くには段数が動的でなければならない。現状は、`getdepth()` が深さを**知る**手段を与え、書き手がその数だけ `break` を**書く**、という形になる。動的な段数指定（あるいはマクロ層による展開）を将来入れるかは未確定。

### D-38. 作用素式——値でも関数でもマクロでもない第4の圏

`break break x` が成立するのは「特殊文だから」ではなく、**`break E` が E を値として運び、その E 自体が `break F` ならもう一段外へ運ばれるから**である。ここから作用素という圏が立つ。

```
作用素式 := 作用素* 終端
作用素   := 'break' | '$repeat(' 作用素 ',' 式 ')' | 別名
終端     := 式 | 'continue' | 'goto' ラベル | ε
```

**意味論は1行**：

> `break X;` — このブロックを正常に終了し、続けて X を**外側の文脈で**行う。

- X が**式**なら、その値がこのブロックの値になる（D-28）
- X が**制御移動**なら、それが外側の文脈で行われる

`if` / `else` の本体は状態に対して透明（D-1）なので、**break に対しても透明**——段数を消費せず素通しする。

#### `$` はモード切り替え

**`$` を読んだ時点で作用素の評価規則へ入る。** TeX の catcode 切り替えと同型で、カーソルマシンにそのまま乗る。入ったあとは印を重ねない：

```
$repeat(break, getdepth())        % ○
$repeat($break, getdepth())       % × 同じものの2つ目の綴りになる
```

`nest(...)` は関数呼び出しに見えるので印が要るが、`break` は制御作用素以外に読みようがないので要らない。**`$` は「他のものと読み違えられる構文」に付ける印**である（`$s` も同じ理由、D-35）。

#### 作用素は第一級ではない

`let f := break;` は不正。値でも関数でもないので束縛に入れられない——**D-27（関数は第一級ではない）と同じ線が延びただけ**であり、新しい規則ではない。これを引かないと制御が高階化し、制約3（万能だが汎用ではない）が壊れる。

#### `$repeat` の第1引数は `break` か `continue`

`break` を重ねればブロックを n 段抜ける。**`continue` を重ねれば反復を n 個進める**——`ifor` なら n 個消費、`nfor` なら n 個飛ばす、`while` なら条件を n 回試す。`loop` は進める状態がないので退化するが、これは嘘ではなく `x * 1` と同じ種類の退化である。

`goto` は重ねられない。行き先がラベルで決まるので、繰り返しても同じ場所に着く。

#### `$repeat` だけが構成子。順序づけは並置

`fusion(a, b)` のような順序づけの構成子は要らない。並置がそれを書く：

```
$repeat(break, n) continue;       % fusion(nest(break,n), continue)
```

D-36 により作用素を実行時の値で選ぶことはできないので、順序づけの構成子の引数は常にリテラルにしかなりえない。ならば並置で足りる。

#### `$repeat` の段数は動的でよい

`$repeat(break, getdepth())` が成立する。**作用素の種類は静的**（`break` と書いてある）なので D-36 のディスパッチ原則には触れない。動的なのは段数だけであり、これは配列の添字が動的なのと同じ種類のことである。

#### `break goto` は規律のある跳躍

裸の `goto` は jump なので D-5 の一括巻き戻しを起こす。`break goto L` は**ブロックを正常に閉じてから跳ぶ**ので起こさない。D-2r によりループ本体の journal は正常脱出で破棄・jump で適用されるため、この差は観測できる：

```
loop { acc += 1; goto done; }        % acc は巻き戻る
loop { acc += 1; break goto done; }  % acc は残る
```

「危険にだけでなく、安全にも自由がなければならない」がここにも出る。同じ場所へ跳ぶのに、規律のある経路とない経路の両方が書ける。

#### 関数境界は越えられない

越えると呼び出し式の評価途中への制御移動になる（式の中の `loop` から `goto` できないのと同じ制約）。黙って打ち止めにするのは嘘なのでエラーにする。

#### §1.5 への追記が必要

> 段数がリテラルの `break` は静的解析の対象。`$repeat` に動的な段数を渡した場合は対象外。

作用素の種類は静的に分かるが、**「この文がいくつのブロックを抜けるか」は静的に決まらなくなる**。失うものを書いたうえで入れるなら PHECL 上の問題はない。書かずに入れるのが違反である。

### D-39. 作用素の別名——第3の評価規律

作用素式に名前を与える。`let`（値）・`fn`（関数）と並ぶ第3の束縛種。

```
flow return := $repeat(break, getdepth());
```

| | 本体 | いつ読むか | フレーム |
|---|---|---|---|
| `let` | 式のトークン範囲 | 強制時に1回（メモ化） | 積まない |
| `fn` | 本体のトークン範囲 | 呼び出しごと | **積む** |
| `flow` | 作用素式のトークン範囲 | **使用ごと**（メモ化しない） | 積まない |

**フレームを積まないことが本質**である。`getdepth()` が使用位置の深さを見なければ `return` にならない。定義時に評価しない点は `let` と同じだが、メモ化せず毎回読み直す点が違う。

**本体は終端を含んでよい。** `op skip := $repeat(break,1) $repeat(continue,2);` は正当である——**インラインで書けるものは名前を付けられる**べきであり、そうでなければ別名機構が導出されない理由で不自由になる（PHECL：抽象化を使う自由と、抽象化を剥がす自由の双方を人間に残すこと）。

ただし作用素式は**終端を高々1つしか持てない**（終端の後には制御が戻らないため）。別名が終端を持っているなら、使用位置に重ねることはできない：

```
flow done := $repeat(break, 1) continue;
done;      % ○
done 5;    % × 既に終端を持っている
```

本体に作用素でも終端でもないものが混ざっていればエラーにする——黙って無視すると定義の一部が消える。

#### 同じ機構が安全と首筋の両方を与える

```
flow return     := $repeat(break, getdepth());      % 安全。ちょうど関数を抜ける
flow leave_loop := $repeat(break, 1);               % 安全。段数が使用位置から自明
flow sneaky     := $repeat(break, getdepth() - 1);  % 首筋。何段抜けるか使用位置から見えない
```

**名前を付けられるということは、抜ける範囲を名前の裏に隠せるということ**である。`return` が安全なのは `getdepth()` がちょうど正しいからであって、機構が安全だからではない。

> §1.6 の「足元を撃つ自由」「胸元まで撃ち抜く自由」に対し、**規律を組む自由**を同じ機構で与える。言語がどちらかを代行することはしない。

### D-26r. `return` は組み込みではない（D-26 を改訂）

D-26 で `return` を削除したのは、§4.8 が §3 に存在しないものを参照していたという**文書の不整合**が理由であって、原理的な拒否ではなかった。作用素式（D-38）と別名（D-39）が入った今、正確に定義できる：

```
flow return := $repeat(break, getdepth());
```

**無名標準ライブラリに置く**（D-37）。中核ではない。脱糖は仕様に書かれており、中核の形をいつでも直接書ける。§4.8 の「`break`/`return` は jump とは区別され」は `break` のみに直したうえで、`return` は標準ライブラリの節に置く。

なお `continue` は D-29 のとおり中核に残る（`break` と違い、別名では書けない——終端だから）。

### D-40. `f80` を数値型に含める

`f32` / `f64` と並べて `f80` を持つ判断は §1.8（x87 を含む CPU 命令を積極的に露出する）の帰結だが、PHECL 的にはそれ以上の意味がある。

x87 は内部的に 80bit で計算する。`f64` しか提供しない言語は、**80bit で計算した結果を「64bit で計算した」と提示している**——これは PHECL が禁じる「実際とは異なるモデルを与えて理解したことにする」ことにあたる。`f80` を書けるようにするのは、起きていることを書けるようにするということである。

> 学習した事実は、後により一般化されてもよい。しかし、嘘であってはならない。

**実装上の注意**：Rust には f80 がない。ソフトフロートか x87 のインラインアセンブラが要る。Tier 2 以降で `f32`/`f64` を入れる際、`f80` を「後回し」にすると、上の理由が骨抜きになる点に注意すること。

### D-41. `cfor` を `nfor`（strict for）に改名

`cfor` は C-style for と読まれる。実際には数値範囲を反復するだけで、`break`/`goto`/`comefrom`/`label` を一切持たない——C の for とは似ても似つかない。PHECL 3（構文上の名称や分類を、実際の計算上の意味から不必要に乖離させないこと）の直接の適用であり、その原則が名指しで挙げている anti-C-style for そのものでもある。

**注意点**：この言語では「strict」が遅延評価の対語（`#[immediate]`）と衝突しうる。`nfor` が「本体が即時評価される」と読まれる余地は残る。C-style for との混同の方が実害が大きいと判断して `nfor` を採るが、記録しておく。

### D-42. `flow` の定義は `:=` ではなく `=`

```
flow return = $repeat(break, getdepth());
```

**束縛演算子（`:=` / `&=` / `^=`）は「thunk をどう作るか」を区別するために存在する**——新規生成／共有／未評価の計算の複製（§4.6）。ところが `flow` は thunk を作らない。本体はトークン範囲として保存され、使用のたびに読み直され、メモ化もされない（D-39）。`:=` を使うと、起きていない thunk 生成を構文が示唆することになる。

裏付け：**thunk を作らない `fn` と `typ` は元から束縛演算子を使っていない**（`fn add (a, b) { ... } -> i64`、`typ counter { ... }`）。`flow` だけが例外になっていた。

ではその2つに倣って並置にするか、というと `flow` は事情が違う。`fn` は `(`、`typ` は `{` が名前の終わりを示すが、`flow` の本体は識別子（別の別名）で始まりうるので区切りがない：

```
flow esc leave_loop;     % esc が名前か、それとも esc も本体の一部か
```

よって区切り記号が要る。`=` は REod でまだ何の意味も持っておらず（代入は `:=`、比較は `==`）、数学の定義的等号として「この名前はこれである」を意味する。示唆が正しい。

> 意味を示唆しない記号について、その対応を恣意的に定めることは妨げられない。

**規則として言うなら**：束縛演算子は thunk を作る構文にのみ現れる。`=` は評価を伴わない定義に現れる。

### D-22. マクロ層は当面仕様から外す

D-16（行頭 `\`、改行終端、呼び出しは任意位置）は保留。構文を自由にするための「完全展開可能な TeX のサブセット」という構想は生きているが、当面は仕様に含めない。

なお設計書 例5 の `\def\MarkRealVisit{...}` は、goto 走査が文を一切実行しない以上、生の `comefrom` と挙動が変わらない——マクロなしでそのまま成立する。

### D-43. §1.3（メモリモデルの明示的例外）を撤廃

> **撤回**：レジスタ層 0–65535 のうち 0–255 と 256–65535 でコスト特性が変わることを、e-TeX の前例に基づく明示的な例外として許容する。

65536 という数は e-TeX がそうだったからであり、導出ではない。**権威に従っただけの数字が、四つの制約の唯一の明示的例外を要求していた。** 0–255 に限れば例外そのものが不要になる。

### D-44. 「静的型付け」→「読み取り時検査」

§4.3 が「読み飛ばされる区間は解析されなくてよい」を保証している以上、「well-typed なら実行時に壊れない」は成立しない。名乗りが不正確だった。機能を減らすのではなく名前を正した。

道具経路（プリプロセッサ・LSP）の不完全性も同じ根から出るので、併せて明記した。

### D-45. `nfor` の jump / `break;` 禁止を撤回

> **撤回された根拠**：「脱出を持てば原始再帰性が壊れる」。

誤りだった。**上界のあるループからの早期脱出は依然として原始再帰的**である（回数が減るだけで上界は保たれる）。加えて本体に `while` を書くことは元から禁じられておらず、本体の計算論的性格は一度も制約されたことがなかった。

`nfor` が保証するのは**自分の反復が上に有界であること**だけである。残る禁止は `break v` のみで、根拠は領域の二重化ただ一つ。

### D-46. `sfor` → `nfor`

`cfor` は C-style for を連想させたので `sfor`（strict for）にしたが、禁止事項を撤回した結果「厳格」の根拠が消えた。残る違いは「反復子を作らずに数値を回す」だけなので `nfor`（number for）。

`ifor` からも「原始再帰」を外した——反復子は有限とは限らない。

### D-47. `op` → `flow`、`$nest` → `$repeat`

`op` は §1.7 の演算子宣言機構を連想させる（英語ではどちらも operator で、日本語の 演算子／作用素 の区別が構文に現れない）。`ctl` も検討したが、**面食らう機能なので見た目も違えた方が誠実**という判断で `flow`。

`$nest` は `break` については正確（ブロックの階層を n 段ネストする）だが、`$nest(continue, 2)` は反復子を2つ進めるのでネストしていない。`continue` を引数に許した時点で名前が追いつかなくなった。`$repeat` が両方を覆う。

### D-48. 命名の検査を §1.4 に追加

3件（`cfor`/`match`/`op`）が同じ形で引っかかったので、原則として書いた：

> その名前は、この言語が別のところで持っている機構を連想させないか。

単射性だけでは、意味が違うのに同じ語を使ってしまう型の誤りを捕まえられない。

### D-49. §4.2 の comefrom 禁止を撤廃

登録は save stack の対象なので、関数を抜けるときに巻き戻される。禁止は「既に成立していることを重ねて言っていた」だけだった。

### D-50. jump は depth 基準を跨げない——エラーではなく隠蔽

**隠蔽であってエラーではない**ことが重要である。§4.1-3 の「さもなくば何もしない」がそのまま処理するので、新しいエラー条件を一つも足さない。

これにより4つのものが一つの境界を共有する（`getdepth()` の原点・`break` の上限・jump の下限・`goto` の走査範囲）。**帰結としてラベル名がフレーム局所になる**——名前空間を持たない言語で、ラベルだけは自動的に閉じる。

### D-51. 跳び先の生存期間と、状態の2種類

> **撤回**：§4.8 の「巻き戻しは処理系のコンテキスト全般に統一して適用される」。

不正確だった。**値の変更は蓄積し、jump の跳び先は構造的である。** チェックポイントの journal は正常脱出時に破棄されるが、`comefrom` の登録だけは適用される。飛び込みの禁止はここから出る。

### D-52. `$frame`

`getdepth()` の原点・`break` の上限・jump の下限を**同時に**張る。3つは同じものなので分離できない。ブロックをクロージャのように使うとき、thunk が環境を捕捉しないことの帰結を制御についてだけ打ち消す。

### D-53. トップレベルの正常終了値

トップレベルもフレームなので `break` の段数超過が検査される。値はホストへ渡る正常終了の値になり、解釈はホストに委ねる。§3.6 によりエラーとは別経路である。

### D-54. 虚無の英名は `akasha`

**色を持たず形を持たない**——色が型、形が値。虚無が型も値も持たないことの規定がそのまま当たる。

**却下した候補**：

- `void` / `never` / `unit` / `nil` / `bottom` — いずれも既存言語で**型**の名前。虚無が型でないことと衝突する
- `lethe`（忘却）— 方向は合っているが、「存在したものが消される」という**操作**を指す。`;` が既に操作の名前なので役割が重なる。名詞が要るのは**行き先の状態**の方
- `erasure` — type erasure という既存概念と衝突する

**注意**：神智学の Akashic records（すべてを記録する書庫）は語を借りただけの別概念であり、**保持**を指すので方向が逆になる。英語圏ではそちらの方が通りが良いので、仕様には「色＝型、形＝値」の導出を明記して連想を防ぐこと。

**追記**：名前は「色も形もない」を根拠に選んだが、**もう一つの性質が後から当たった**。アーカーシャは一切の包括であり何かに含まれることがない——REod の akasha も、トップレベル（何にも囲まれていない場所）にしか在れない。この規則は波括弧の機構から独立に導かれていたので、**名前が後から規則を予測した**形になる。

誤解を招かない名前と、導出済みの規則を予測する名前とでは後者が強い。§1.4 の検査を通っただけではない。

`$frame` は akasha の在り処を新しく作らない（波括弧である以上は値として取り出す）。一切の包括は一つしかないので、在り処も一つである。

### D-55. `{}` は akasha でも paradox でもなく、「akasha を値位置に置く操作」である

一時、仕様に矛盾した2つの記述が並んでいた——「`{}` は paradox 型の正準な式」と「`let x := {};` の右辺は虚無」。どちらか一方が誤りだと考えたが、**問い自体が誤っていた**。

akasha は**何も書かれていないこと**である。`{ }` で囲んだ時点で式指向ゆえに値位置に置かれ、輪廻が強制される。したがって `{}` は akasha を akasha のまま指すのでも、paradox を直接産むのでもなく、**その操作を字面にしたもの**である。両方の記述が正しい。

**帰結**：`{}` が paradox の表示であるのは記憶術ではなく、字面が機構を描いているからである。

**帰結**：波括弧の規則が一つに畳める——「領域の中身を値として取り出す。中身が akasha なら、その取り出しが paradox を生む」。`{ 5 }` / `{ 5; }` / `{}` が同じ規則で説明される。

**帰結**：**akasha が残れるのはトップレベルだけ**である。波括弧に囲まれていないので値位置に置かれない。空のプログラムはホストへ何も渡さない。

### D-56. paradox は「実在できない値」ではなく「領域の終わりまでに消えねばならない値」

> **撤回**：「paradox は実在できず、記録もできない」。

この書き方は `{} -> i32` を説明できない。**実在できないものを一度作ってから型注釈で変換する**、という説明が矛盾しているからである。

規則を4行に置き換えた：

```
1. 領域は空であるか、値を一つ持つ
2. `;` は左の値を評価してから akasha へ潰し、領域を空にする
3. 空の領域が値として読まれると paradox が生じる
4. paradox は、その領域が終了する時点で実在していてはならない
```

**帰結1**：「記録できない」が独立した規則でなくなる。記録は値を領域の外へ持ち出すので、右辺の領域が終わる時点で paradox が残る。`let x := {};` / `f({})` / `1 + {}` / `if {} { … }` が同じ規則で捕まる。「二次発生」の節も不要になった。

**帰結2**：**文の位置のブロック式にも `;` が要るようになった。**

```
if c { n := 5; };
loop { … };
```

これを利点と判断した：

- Rust の `ExpressionWithBlock`（文の位置では `;` 不要）に相当する**特別扱いが消える**。規則は「すべての項は値を残すか `;` で潰すか」の一つだけになる
- `fn f () { loop { … } }` と `fn f () { loop { … }; 0 }` の区別が字面に出る。実装の「残りがちょうど1つの式として読み切れるか」という先読みが不要になる
- tree-sitter 文法の `_expression_no_block` という仕掛けが不要になり、editors/README.md に記録した「末尾式か文かは構文だけでは決まらない」という乖離も消える

セミコロンが増えるが、欠落は「値が残っている」として検査で捕まるので IDE が補助できる範囲と判断した。

### D-57. 「`->` の省略は `-> {}` の糖衣」を撤回

`fn f () { 5 };` は 5 を返す（実装で確認）。`{}` は paradox なので、糖衣が正しければ 5 を返せない。**仕様の記述が誤りだった。**

省略は**本体からの推論**である。

### D-58. 関数も動的スコープである（未記載だった）

```
let x := 1;
fn f () { x } -> i64;
{ let x := 2; f() }     % 2
```

仕様は「thunk は環境を捕捉しない」とだけ書いており、**`fn` 本体について何も言っていなかった**。実装は動的だが、書かれていないので別の実装者は lexical を作りえた。

規則：**名前解決は常に解決時点の環境で行われる。thunk も関数本体も、定義位置の環境を保持しない。**

クロージャ不採用（§3.2）と同じ一点から出ており、thunk だけが特殊なのではない。

### D-59. 丸括弧は領域を作らない

式をまとめるだけであり、項の列を持てない。`(1; 2)` は不正。項の列を持てるのは波括弧だけである。仕様が黙っていたので明記した。

### D-60. akasha は規範的規則から外し、付録に置く

4.9節の4行は「領域が空である」で閉じており、名前を要さない。**規則の記述からは外した。**

しかし **REod の認知モデルには要る**。REod は「何もない」を2種類区別するからである：

| | |
|---|---|
| 値がない（領域が空） | akasha |
| 値だが中身がない（単位型） | paradox |

大半の言語はこれを `()` に潰している。**潰したまま読むと必ず外す。**

実測がある。文脈を与えずに REod のコードを読ませたところ、`{ 5; }` も `{}` も `1; 2; 3;` も一律に「Unit/void」と読まれた。区別を持たないので `{ 5; }` を「無害な単位値」と解釈し、**「領域の終わりまでに消さねばならない」に到達できなかった**。

したがって線はこう引く：

- **paradox は名前が要る。** 型であり、エラー表示に `{}` として現れ、ユーザーが見る
- **akasha は規則には要らないが、認知モデルには要る。** 付録A に置く

### D-61. `{ e1; e2 }` が seq である

`;` が強制を伴い、ブロックが領域の値を返すことから出る。Haskell の `seq` に相当し、式の位置で使える。専用の演算子は要らない。

**批評者がこれを見つけられなかった**（「強制と破棄が抱き合わせで、強制だけを行う手段がない」と指摘された）ので、導出できるだけでは足りないと判断し、仕様に明記した。

### D-62. Model B を採らない（前回の検討を撤回）

「トップレベルもホストが読み、ホストだけが paradox を受容する」という案（Model B）を一度検討したが、**採らない**。

Model A（トップレベルは読まれない）と**観測上まったく同一**でありながら、paradox を作ってすぐ許容するという無駄な一段を挟む。加えて akasha の名前の第2の対応（含まれることがない）が壊れる。

直すべきは書き方だった。「akasha が残れるのはトップレベルだけ」ではなく、**読む位置の一覧を先に置き、トップレベルがそこに含まれないことを述べる**。特例ではなく一覧の帰結になる。

### D-63. フォールバック演算子 `??` を導入し、型注釈から「値を作る」仕事を外す

> **撤回**：「paradox に構文上書かれた型が付いていれば、その型の既定値になる」。

型注釈に**値を生成する**第2の仕事を負わせていた。`->` も `:` も本来「型を名指す／制約する」ためのものであり、無から値を作る操作ではない。§1.4 の単射原則に反していた。

加えて**表現力が低かった**。既定値しか選べず、`-1` を返したい場合に書けなかった。

```
E ?? F      E が paradox なら F、そうでなければ E。F は短絡
```

**帰結**：

- `->` と `:` が型を名指す仕事だけに戻る
- フォールバック値を選べる（`d[k] ?? 0 - 1`）
- **D-9 の「範囲が空なら既定値」が撤回される**。`nfor` の `-> T` は通常の型注釈になる
- ハッシュマップ読み出しの推奨形が変わる。`let cur : i64 := d[ai];` ではなく `let cur := d[ai] ?? 0;`——欠損時の値が書かれる

**記号について**：`??` は既存言語では null 合体演算子であり、REod に null は無い。しかし担う役割（値が無いときに何を置くか）が一致するので、示唆は正しい側にある。`else` は `if` と衝突し、`or` は真偽値を連想させる。

**この判断は Rust に寄る方向である。** Rust は `Default::default()` を明示させ、暗黙のゼロ初期化を持たない。REod が `->` で暗黙に生成していた方が逸脱だった。

### D-64. Rust との関係の整理

REod は Rust のアンチテーゼに見えるが、逆らっている対象は限定されている。

| | Rust | REod | 種別 |
|---|---|---|---|
| `;` | 「ブロックを持つ式は文の位置で `;` 不要」の例外あり | 例外なし | **Rust の一貫性の欠如を除去** |
| 脱出 | `return` / `break` / `break 'label` / `continue` / `?` | `break` の段数＋`continue`。`return` は派生 | 同上 |
| 「値がない」と「単位値」 | `()` に統一 | akasha / paradox に分離 | **意図的な排除への逆行** |
| 既定値 | `Default::default()` を明示 | `??` で明示（D-63 以前は暗黙） | **REod が Rust に寄る** |
| 遅延評価・動的スコープ | 排除 | 採用 | 別の軸 |

**本当のアンチテーゼは3行目だけ**である。1・2行目は PHECL 4（導入した概念について裏切らない＝Rustism）を Rust より厳しく適用した帰結にすぎない。

Rust の例外は**出荷可能なシステム言語であるための妥協**であり、REod はその制約を受けていない。「Rust が間違っていた」ではない。

**反例を1つ記録しておく**：`{ }` の3つのスコープ規律（D-23）は Rust より一貫していない。Rust のブロックは一様である。

### D-65. 領域は「空であるか、値を一つ持つ」ではなく「ちょうど一つの値を持つ」

**規則が4行から3行になった。**

```
1. 領域はちょうど一つの値を持つ。内部に何も置かれていなければ、その値は paradox である
2. `;` は左の値を評価してから捨て、内部を空にする
3. paradox は消さねばならない。消費するのは `;`、`??`、そしてホストである
```

**式指向であることの帰結**である。ブロックは式であり、式は値を持つ。したがって「値を持たない領域」は存在しない。以前の「空であるか、値を一つ持つ」は、この帰結を取り込めていなかった。

**消えたもの1：「読む」の位置一覧。** 以前は「読むのは波括弧・束縛の右辺・被演算子・引数。トップレベルは読まない」という表があった。**あの4つがなぜその4つなのかは説明されていなかった**——恣意的な一覧だった。領域が常に値を持つなら、読む・読まないの区別自体が消える。

**消えたもの2：`{}` の説明の一段。** 「波括弧で囲むと読まれる」ではなく「`{}` は領域であり、領域は値を持ち、内部が空なので値は paradox」。

**名前の対応が一般化された。** 以前は「一切の包括だから最外にしか在れない」だったが、「akasha は値ではないのでどこにも収まらない。収めようとすると paradox になる」になった。**トップレベルという例外が消えた。**

**Model B（ホストが paradox を受容する）を採用する。** D-62 でこれを「無駄な一段を挟む」として却下したが、**撤回する**。あのときは「領域は空でありうる」を前提にしていたので paradox の生成が余計に見えていた。領域が常に値を持つなら、生成は余計ではなく必然である。

ホストは領域ではないので、これは言語の例外ではなく境界のプロトコルである。

### D-66. コメントは字句の特別扱いではない。`%` から改行までを閉区間で飲む

コメントを独立した字句機能として規定するのをやめた。

> `%` から改行までを、**改行を含めて**飲む。飲まれた区間は何も産まない（akasha）。

`;` が「値を作ってから潰す」のに対し、コメントは最初から何も無い。**到達点が同じで経路が違う**だけである。これは akasha の当初の定義——「何も書かれていないこと」——とそのまま一致する。

**導出されるもの：**

1. **行末 `%` が行継続になる。** TeX と同一機構。マクロ層（Tier 4）の「継続は行末 `%`」がこの一つの規則から出る
2. **アトリビュートの後にコメントを置けない。** アトリビュートは行末で終端するが、コメントがその改行を飲むため。**規定ではなく帰結**
3. `%` が意味を持つのは改行が意味を持つ場所だけ（アトリビュートと返り値型）

**却下した選択肢**：半開区間（改行を含めない）。アトリビュート行に行末コメントを書けるが、**行継続と TeX との一致を失う**。§0 の位置づけを優先した。

**実装上の注意**：行番号は2系統要る。**物理行**（エラー位置）と**論理行**（改行の意味）。コメントが飲んだ改行では論理行だけが進まない。1系統で済ませるとエラー位置がコメントの数だけずれる。

### D-67. `#[flat]` — `goto` の走査から構造の認識を外す

走査が波括弧の深さを見なくなり、**最初に見つかった `label` に着地する**。depth 基準（フレーム）の境界は越えない——そこは構造ではなく制御の境界である。

**ブロックコメントがほぼ導出される。**

```
#[flat]
goto _comment_;
    壊れていてよい { { {  undefined( 1 2 3
label _comment_;
```

「ほぼ」の内訳：

- **字句解析だけは通る必要がある。** 未終端の文字列リテラルは飛ばせない。`%` コメント（D-66）が字句以前で消えるのとはここが違う
- **入れ子にならない。** 最初の `label _comment_` で終わる

**規約**：`_` で始まるラベル名はユーザーの使用を企図しない。

**却下**：「入っていないブロックの `}` は不活性とする」。§4.1 の「着地はカーソル移動以上の意味を持たない」からは自然に見えるが、`}` を無害な no-op にすると**本物の括弧不均衡が全域で黙って通る**。`#[flat]` は構造からの明示的な離脱なので、構造的に無効な位置へ着地したら実行時エラーになる方がよい。

**何も抑止しない属性は嘘になる**ので、`#[flat]` を `goto` 以外に付けるのはエラーにする（`#[forward]` を `fn` に付けるのと同じ扱い）。

### D-68. `#[lazy_attribute]` — アトリビュートのアトリビュート

次のアトリビュートを遅延させ、宣言に保存して**使用位置で**効かせる。

```
#[lazy_attribute]
#[flat]
flow comment = goto _comment_;
```

**`flow` の本体は使用のたびに使用位置で読み直される（D-39）ので、属性も本体と一緒に旅をする**のが自然である。

**却下した選択肢：**

- **`#[flat]` を `flow` 宣言に直接付ける。** 動作は同じだが、**同じ属性が2つのタイミングを持つのに表に出ない**——`goto` に付ければ即座、`flow` に付ければ保存されて後で。`#[lazy_attribute]` はタイミングの変更を明示するので、属性の意味は一つのまま保たれる
- **アトリビュートを作用素式の中に置く**（`flow f = #[flat] goto L;`）。より一般的だが置き場所の規則が2つになる。この一般化を必要とする属性は `#[flat]` だけである

**D-18r を破らない。** `#[lazy_attribute]` 自身も「次の行を修飾する」アトリビュートであり、次の行がたまたまアトリビュートであるだけである。

**マクロ層（Tier 4）でも同じ形が要るはず**である。マクロ本体も使用位置で展開されるので、遅延した属性の受け皿になる。用途は1つではない。

**無名標準ライブラリが2行になった：**

```
flow return = $repeat(break, getdepth());

#[lazy_attribute]
#[flat]
flow comment = goto _comment_;
```

`return` と**ブロックコメント**が、どちらも中核の機構の合成として書かれている。

### D-69. 道具経路はブロックコメントをブロックコメントとして扱う

**決定**：パーサ・ハイライタ・LSP は `comment; … label _comment_;` を**ブロックコメント**として処理する。実行経路（インタプリタ）はこれを `#[flat] goto` による読み飛ばしとして処理する。両者は同じ構文に**違う意味論**を与える。

**原則**：

> 同じ意味論を採用するなら、構文は意味に単射しなければならない。構文論の意味論は一意でなくてよい。

§1.4 の単射性は、意味論を固定したうえでの要求である。禁じているのは一つの意味論の内側での多義性であって、意味論そのものの一意性ではない。実行経路の内側でも道具経路の内側でも、この構文の意味は一つしかない。

**なぜ必要か**：D-68 でブロックコメントは中核の合成として導出された（`flow` + `#[lazy_attribute]` + `#[flat]` + `goto`）。実行経路にとってはそれで十分だが、道具経路がそのまま追随すると、コメントの中身を構文木に組み込もうとして ERROR ノードを撒く。**壊れていてよいはずの領域が、エディタでは壊れて見える。** 導出されたことと、道具がそれをどう見せるかは別の問題である。

**実装と、その既知の近似**：tree-sitter の外部スキャナに `block_comment` を追加した（`editors/tree-sitter-reod/src/scanner.c`）。ただし tree-sitter は `flow` の束縛を追えないので、**名前 `comment` を決め打ちしている**。ユーザーが `comment` を再束縛すると道具経路と実行経路が食い違う。

これは §1.5 の「道具経路は不完全でよい」の範囲内だが、**不完全性の質が違う**ことは記録しておく：§1.5 が想定していたのは「道具が判断を保留する」不完全性であり、ここにあるのは「道具が積極的に誤る」不完全性である。原理的に正しいのは、名前ではなく**形**——`#[flat]` な `goto` へ展開される別名——を認識することで、LSP（Tier 3）はそちらを実装すべきである。tree-sitter は文脈自由に近い道具なのでそこまで追えない。

**却下した案**：

- **道具経路も実行経路に完全に追随させる**（ブロックコメントを特別扱いしない）。導出の純粋さは保たれるが、コメントの中身が全部 ERROR ノードになる。ハイライトも折り畳みも壊れる。**導出は言語の性質であって、道具の性質ではない。**
- **ブロックコメントを字句層の組み込みに戻す**（D-68 を撤回する）。道具経路の都合で中核の機構を増やすことになる。道具の限界を言語の設計に転嫁している。
- **`comment` を予約語にする**（再束縛を禁じて決め打ちを正当化する）。無名標準ライブラリの宣言が中核の機構に昇格してしまい、二層構造（§1.6）が崩れる。近似のままにして、近似であることを書く方を採る。

### D-70. 束縛記法は意図的な PHECL 違反である

**何が起きているか**：`:=` は他言語では正格な代入である。REod では遅延サンクの束縛である。`let` `fn` `{}` `+=` も同様に、他言語で持っている意味と食い違う。

**測定**：3つの LLM に例を渡した結果、全員が他言語の意味で読んだ。

| | `let b := a + 10; a := 2; print(b);` | `twice` が呼出元の `k` を見るか |
|---|---|---|
| 予測 | 11 | 未定義変数エラー |
| 実際 | **12** | **42** |

さらに強い証拠がある。**出力を与えた後でも**、GPT は一つの機構に四つの別々の説明を与えた——(1) ゼロ除算が値になる、(2) `print` が特別扱い、(3) 遅延評価、(4) 定義時に環境を捕捉するクロージャ。正解は全部「使われるまで評価されない＋初回強制でメモ化」の一つである。

**帰結**：**束縛演算は誠実な示唆ではない。** `:=` は自分が何をするかを正しく示唆しておらず、他言語での意味を示唆する。結果として読み手は「分からない」ではなく **「間違って分かった」** 状態に置かれる。誤読が自信を伴う——これは「見慣れない記法で戸惑わせる」より悪い性質である。

**それでも採る理由**：

- §0 の位置づけ（TeX からの移行コストの低さ）は、見た目の親しみやすさに依存している。`plain1_numbers.reod` は誰でも読める
- 記法を変えると `:=` / `&=` / `^=` の族が壊れる（§4.6）
- 遅延を opt-in にすると言語が反転する

**却下した案**：

1. **別のトークンにする**（`<-` など）。「見慣れない記法＝見慣れない意味」という対応は正しい。しかし REod の機構は広範なので、全部に見慣れない記法を配ると、TeX からの移行コストの低さを謳えなくなる。族も壊れる
2. **`:=` を正格にし、遅延を別演算子にする**。§4.6 が反転する。thunk が既定でなくなれば、動的スコープの導出（4.6節）も消える。言語の中核を、読み手の予期のために捨てることになる
3. **使用位置に強制の印を付ける**（`!b` のような）。強制点は文脈で決まる——`;`、`#[immediate]`、関数引数、複合代入の左辺、`break` の被演算子。印を付けるならこの5箇所すべてに付き、式のほとんどが印だらけになる

**違反しているのは記法であって、機構ではない**：遅延評価そのものは PHECL に触れない。anti-functional が対象にしているのは**数理モデルへの過度な抽象化**であって、評価戦略ではない。「遅延評価は関数型言語の看板機能だから anti-functional に触れるのではないか」という読みは**却下**する——看板が同じであることと、原則が禁じている性質を持つことは別である。したがって D-70 は記法だけの問題であり、`:=` を正格にしても解決しない（却下案2を見よ）。

**宣言**：これは PHECL 違反であり、隠さない。§1.4 の単射性は**言語内**の検査であって、言語間の検査ではない。REod は**言語間の単射性を意図的に放棄している**。

**放棄したことに伴う義務**：埋め合わせはドキュメントが負う。チュートリアルは (1)(2)(3)(4) を四つの現象としてではなく、**一つの機構として**提示しなければならない。現に、出力を手にしていた読み手が四つに分解した。3章（束縛と遅延評価）の構成はこの制約の下で書く。

**3章の提示順（測定に基づく）**：**副作用込みの例を、値の例より先に置く。**

誤読の原因が特定できている。読み手は「遅延評価＝値の計算を先送りする仕組み」という部分理解を先に完成させ、副作用を例外として処理する。値の例を先に見せると、この部分理解が固まってしまう。

したがって `examples/plain4_side_effects.reod` の3例（未参照なら副作用も起きない／参照すれば一度だけ起きる／再束縛は新しいセルを作り古いセルは捨てられる）を先に置き、そのうえで値の例に進む。2回目の `print(a)` で `99` が出ないという**出力の非対称性**が、メモ化を見せる最も強い装置になる。

この盲点の強さは二重に測定されている。指摘した読み手自身が、盲点を正確に言語化した直後に `let r1 := addk(1);` を「束縛時に呼び出しが走る」と読んで外した。`print` を関数呼び出しに置き換えただけで再発する。

**観測点**：`examples/plain3_forcing.reod`（理由つき）と `examples/probe3_forcing.reod`（理由なし、他の処理系・LLM に当てるための版）。後者は 概要.md と同じ規律で書く——理由を書くと純粋な反論が返ってこない。

**測定の付記**：4つ目の読み手（別セッションの Claude）は、推測せず**仕様を質問した**——(1)(2)(4)(5)(7) は与えられたコードだけでは一意に定まらない、と正しく指摘したうえで意図を尋ねた。4つのうちこれだけが正しい認識論的態度であり、出力を与えた後の復元も最も正確だった（(1)(3)(4) を一つの機構に統合できたのはこの1つだけ）。それでもなお (2) を別の現象として切り出した。**出力を持ち、機構を言い当てた読み手でさえ、4つの現れを完全には束ねられない。** D-70 の「ドキュメントが負う義務」の重さはこの測定に基づく。
