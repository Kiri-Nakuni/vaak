# 固い REod — AST を持つ方言の検討

現在の実装（カーソル機械）を **REod の正規形**とし、`goto` / `comefrom` を削除して AST を持つ方言を作れるか、を検討する。結論を先に書く。

> **作れる。ただし「REod から `goto` を引いたもの」にはならない。**
> 除かれるのは跳躍ではなく、**未解析のまま実行する能力**である。

---

## 1. 誤った前提の除去

`goto` を消せば全体を先に解析できる、という見立ては**成り立たない**。実測：

```
if 0 == 1 { let x := ; }          → 1
if 0 == 1 { print(( 1 ; }         → 1
fn never () { let x := ; } -> i64; → 1
let z := { let x := ; 1 };        → 1
loop { if i == 0 break; let y := ; } → 1
```

`goto` はどこにも無い。それでも**通らない `if` の枝・呼ばれない関数・強制されないサンク・到達しないループ分岐**の中身は解析されない。

§4.3 が言っている性質は `goto` の帰結ではなく、**カーソル機械そのものの帰結**である。`goto` はその性質を最も派手に使う機能にすぎない。

したがって固い REod の定義は次になる。

> **固い REod ＝ 全体が解析でき、かつ跳躍しない REod プログラムの集合。**

前半が主で、後半が従である。

---

## 2. 保存されるもの

| 機構 | 保存 | 根拠 |
|---|---|---|
| サンク・遅延・メモ化 | ✓ | AST 断片を `Rc<Expr>` で持てばよい。実測で +35行（別実装での測定） |
| 動的スコープ | ✓ | 環境を捕捉しないという性質は AST でも同じ。むしろ単純 |
| `break` の動的段数 | ✓ | `Flow::Break(u32, After)` を上へ伝播。実測で42行 |
| `getdepth()` | ✓ | ブロック深度のカウンタで足りる |
| 作用素式・`flow` | ✓ | 本体を AST 断片で保持し、使用位置で評価する。動的スコープなので捕捉は不要 |
| 巻き戻しジャーナル（3規律） | ✓ | 実行時の機構であり、解析方式と直交する |
| `#[global]` / `#[immediate]` | ✓ | 同上 |
| 名前検査 | ✓ | むしろ強くなる |
| 領域・paradox・`;`（Tier 2.1） | ✓ | 未実装だが、AST の方が素直に書ける |

**「特異」と呼ばれてきた部分は全部保存される。** 遅延・動的スコープ・メモ化・段数付き脱出は、AST と何の緊張もない。

---

## 3. 失われるもの

### 3.1 `goto` / `comefrom` / `label` / `#[flat]`

`After` は `Goto` `Label` `Comefrom` を失い、`Value` と `Continue` だけになる。`scan_to_label_with` と comefrom レジストリが不要になる。

### 3.2 §4.3 の「隠しコードの安全性」

TeX の `\iffalse … \fi` と同型の性質。**これは PraTeX への埋め込みという §0 の要求から来ている。** 固い REod は、この一点において PraTeX の要求を満たさない。

**したがって固い REod は正規形の置き換えではない。** 用途が違う。

### 3.3 ブロックコメント——ただし救済がある

`comment; … label _comment_;` は `#[flat] goto` からの導出なので、跳躍を消すと導出も消える。

しかし**字句層で同じ構文を認識すれば、ソース互換のまま救える**。そしてそれは既に書かれている——D-69 で tree-sitter の外部スキャナに入れたものが、まさにこれである。

> **D-69 で「道具経路の近似」として実装したものが、固い REod では「実装そのもの」になる。**

同じ構文に二つの意味論を与えてよく、重要なのは相似であること——という D-69 の原則が、方言という形で実体を持つ。近似が仕様に昇格する。

---

## 4. 決定的な性質：この方言は保守的である

固い REod が正規形と**違う答えを出すこと**があるか。

無い。差は常に一方向である。

| | 正規形 | 固い REod |
|---|---|---|
| 全体が解析でき、跳躍しない | 動く | **同じ答え** |
| 解析できない部分がある | 動く | **受理しない** |
| 跳躍する | 動く | **受理しない** |

**固い REod は、答えを変えない。受理する範囲を狭めるだけである。** 黙って違う結果を出す経路が無い。

これは方言として最良の性質であり、差分テストに使える——同じプログラムを両方で走らせ、出力を比較できる。本セッションで見つかったバグ（式位置のブロックからの制御脱出、`goto` による引数破壊）は、この設定なら機械的に検出できた。

---

## 5. §1.5 が精密になる

現在の §1.5 は「道具経路は不完全でよい」と書いている。固い REod があると、これが書き換わる。

> **道具経路は、固い REod の上では完全である。その外では不完全である。**

そして帰属判定は容易である——固い REod の実装が受理するかどうか、それだけ。`goto` / `label` / `comefrom` / `#[flat]` の不在は字句で見え、解析可能性は解析すれば分かる。

これは「不完全でよい」より強い主張であり、しかも**検査できる**。LSP は「この関数は固い REod の範囲内なので、型検査と参照解決を提供します」と言える。

## 6. 規模の見積もり——小さくならない

現行 2088行から:

| | 増減 |
|---|---:|
| 走査・読み飛ばし（実行しないためのコード）が不要 | −208 |
| `scan_to_label_with`・comefrom レジストリ・`After` の3変種・`#[flat]` | −96 |
| AST 定義と再帰下降パーサ（属性・`flow`・作用素式・型注釈・式ブロックを扱う） | +350〜500 |
| 字句層のブロックコメント | +30 |
| **差し引き** | **+76〜226** |

> **固い REod ≈ 2,150〜2,300行。現行よりむしろ少し大きい。**

（初稿で「1,100〜1,400行」と書いたのは算術の誤りである。別実装での測定値 523行と混同していた。記録として残す。）

**したがってこれは特殊化ではない。** 特殊化なら制限した分だけ安くなるはずだが、安くならない。制限した分は**丸ごと別の場所——パーサと AST——に移るだけ**である。

走査208行が消えて、パーサとASTが350〜500行増える。**REod を高くしているのは AST の不在ではなく、意味論そのものである**——制御転送299・ジャーナル151。これらは両方の実装が等しく払う。

### 買えるもの（実測）

| | 現行（カーソル） | 固い REod（AST） |
|---|---|---|
| 規模 | 2,088 | ≈2,200 |
| 速度 | 1x | **2〜2.7倍速** |
| §4.3（未解析実行） | あり | **失う** |
| 静的解析 | 不完全 | 完全 |

同じ費用で性質を交換する。**規模の議論ではなく、性質の議論である。**

### 外部からの独立な確認

同じ仕様を渡した3つの読み手が、いずれも AST を持たない設計を支持した。

- **Gemini**：「本質的に AST ベースと相性が悪く、トークン列直接実行のほうが自然」「Save stack とトークン列のカーソル巻き戻しが**完全に同一の概念として統合できる**」（§4.8 / D-23 の独立な再発見）
- **GPT**：「AST インタプリタとして設計するより、ソース位置・動的環境・制御スタックを持つ小さな抽象機械として設計するほうが**仕様に忠実**」——提示された構造 `Source / Cursor / DynamicEnv / ControlStack / SaveStack / LabelIndex / ThunkTable` は現行実装そのもの
- **Grok**：「非 AST にするとパーサは軽くなるが評価器が重くなり、**トータルでは大きく減りにくい**」

**問うべきは「AST を持つか」ではなく「§4.3 を要るか」である。** 要るならカーソル、要らないなら AST。規模は同じで、速度と解析可能性が付き、未解析実行を失う。

そして §4.3 は PraTeX への埋め込み（§0）から来ているので、**正規形の答えは既に決まっている。**

---

## 7. 何のために作るか

置き換えではないので、目的を明示しないと持てない。

1. **差分テスト。** 正規形の実装を検証する独立実装。意味論の記述が正しいかを機械的に試せる
2. **§1.5 の精密化。** 道具経路の完全性に、検査可能な境界を与える
3. **教育。** チュートリアルの範囲（1〜7章）は跳躍を使わない。固い REod で全部書ける
4. **Tier 3 の受け皿。** 型検査とプリプロセッサは相を必要とする（[実装費用.md](実装費用.md)）。相を持つ実装は固い REod である
5. **PHECL の「規律を組む自由」（§1.6）。** 「胸元まで撃ち抜く自由」の対として、撃たないことを宣言する手段になる

---

## 8. 規律

方言を持つと、乖離が発生する。正規形の原則をそのまま適用する。

> **乖離を見つけたら消さず、記録する。** 固い REod が受理しないプログラムは、なぜ受理しないかを書く。正規形の側の意味論を変える理由にはしない——固い REod は正規形に従う側である。

そして**名前**について。「固い REod」は方言名であって別言語ではない。同じプログラムが両方で動くなら、意味は同じでなければならない。これは D-69 の相似の要求を、方言間に拡張したものになる。
