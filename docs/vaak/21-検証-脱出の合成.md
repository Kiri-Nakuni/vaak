# 検証 2 — 脱出の合成

**この言語で最も特徴的で、最も検証されていない部分。**
`break` の合成・`$repeat`・`getdepth()`・`outward`・フレーム越え。

実装が無いので机上で追う。**破綻を見つけたら記録する。**

---

## 1. 段数を数える

まず、何が脱出段を作るかを確認する（C-20 の表）。

| | 脱出段 |
|---|---|
| 裸のブロック `{ }` | ○ |
| ループ本体 | ○ |
| 関数本体 | ○（**フレームの上限**） |
| `( )` | × |
| `if` の分岐 | × |
| `switch` の腕 | × |
| 演算子の被演算子位置 | × |

```
fn f () {                     ← 深さ 1（フレーム）
    loop {                    ← 深さ 2
        if (c) {              ← if の分岐は数えない
            …                 ← ここで getdepth() は 2
        } fi;
    };
};
```

**`if` の分岐に `{ }` を書くと数える。** 分岐そのものは数えないが、
分岐の中に置いたブロックは脱出段である。

```
if (c) { … } fi           分岐（数えない）の中にブロック（数える）
```

**これは正しい**が、`if (c) { break; } fi` の `break` が
**ブロックを抜けるだけで `if` の外に出ない**ことを意味する。

### 🔴 問題1：`if` の分岐に `{ }` を書くと `break` が届かない

```
loop {
    if (c) { break; } fi;
    step();
};
```

読み手の意図はほぼ確実に「ループを抜ける」である。しかし：

1. `{ }` が脱出段を作る
2. `break` はその `{ }` を抜ける
3. `if` の分岐は透明なので、そのまま `loop` の本体に戻る
4. **`step()` が実行される**

意図どおりにするには `break break;` と書くか、`{ }` を外す。

```
if (c) break; fi;             ← ブロックを書かなければ届く
if (c) { break break; } fi;   ← 書くなら二段
```

**意味論としては一貫している。** `{ }` は三つの単位を作ると宣言してあり、
脱出段はその一つである。

**しかし字面が意図を裏切る。** C 系の言語では `if (c) { break; }` の波括弧は
**無害な飾り**であり、付けても外しても同じである。Vaak では**段数が変わる。**

**受け入れるしかない**——`{ }` の意味を一つに保つ（C-20 まで）という決定の代償である。
`{ }` が脱出段を作らないようにすれば直るが、それは `{ }` に二つ目の意味を与えることになる。

**規約として書く**：**`if` の分岐に `{ }` を書かない。** 必要なら書くが、段数を数える。

## 2. `return` を追う

```
flow $return = $repeat(break, getdepth());
```

```
fn find (a : i64 array alias, x : i64) {      ← 深さ 1
    nfor (i, 0, a.len()) {                    ← 深さ 2
        if (a[i] == x) $return i; fi;          ← ここで getdepth() は 2
    };
} -> i64;
```

1. `return` が `$repeat(break, getdepth())` に置き換わる
2. 使用位置で `getdepth()` を評価 → **2**
3. `$repeat(break, 2)` → `break break`
4. 被演算子は `i`
5. `break break i` → 2 段抜けて `i` を置く
6. `nfor` の領域を抜け、**関数本体の領域に `i` が置かれる**

**通る。** そして `getdepth()` が**使用位置で評価される**（C-15：`flow` の本体は使用のたびに読み直される）ことが効いている。

### 🟡 問題2：`return` の後の `;` が二重に見える

```
if (a[i] == x) $return i; fi;
```

`$return i;` の `;` は **`break` が産む paradox** を潰す（C-43）。
`fi;` の `;` は **`if` が産む paradox** を潰す。

**どちらも要る**が、一行に `;` が二つ並ぶのは読みづらい。
そして**脱出した場合、一つ目の `;` には到達しない**——それでも書く必要がある（C-43）。

**受け入れる。** C-43 の「領域を閉じてから脱出する」を採った代償である。

## 3. `break` の被演算子が外界面で評価される

```
loop {                        ← 深さ 1
    let x := { break 5; };    ← ブロックは深さ 2
    …
};
```

`break 5` は**ブロックを 1 段抜けて、5 を外界面に置く**。
外界面はブロックの値なので、**`x` に 5 が入る。ループは抜けない。**

ループを抜けたいなら：

```
loop {
    let x := { break break 5; };
    …
};
```

内側の `break` がブロックを抜け、外界面（＝`let` の右辺の位置）で `break 5` が実行される。
それが**ループを抜けて 5 を置く。**

### 🟡 問題3：`let` の右辺で脱出すると、束縛が起きない

```
let x := { break break 5; };
```

`x` への束縛は**実行されない**。ループを抜けてしまうので。

**一貫している**が、`let x := …` と書いてあるのに `x` が存在しないまま
外へ出るのは、静的検査を書くときに注意が要る——**`x` は宣言されたのか。**

字句スコープなので、**`x` の宣言は構文上存在する**（名前解決は通る）。
実行時に束縛が起きないだけである。そして脱出しているので、
**`x` を参照するコードには到達しない。**

**問題なし。** ただし検査器は「宣言されたが束縛されていない名前」を
扱えなければならない。記録しておく。

## 4. `outward`

```
fn main () { break outward break 1; }
main();
```

1. `break` が `main` の本体（フレーム）を抜ける
2. `outward` により**フレームを越える**ことが許される
3. 外界面——**`main()` の呼び出し位置**——で `break 1` が実行される
4. 最上位の領域を 1 段抜けて、1 を置く
5. **ホストが 1 を受け取る**（C-32）→ `exit 1`

**通る。** `main();` の `;` には到達しない。

### 🔴 問題4：`outward` の被演算子が空だと何が起きるか

```
fn f () { break outward; }
```

`outward` は「フレームを越える」と言っているが、被演算子が無い。
**越えた先で何もしない**——つまり呼び出し位置の領域を 1 段抜ける、ということか。

```
fn f () { break outward; }
loop { f(); };
```

これは**ループを抜ける**のか。

**規定されていない。** `outward` が「越える」だけで被演算子を要求しないなら、
「呼び出し側で 1 段抜ける」という強力な操作が**印一つで書ける**ことになる。

**提案：`outward` は被演算子を要求する。** 越えた先で何をするかを書かせる。

```
break outward break 1;    よい
break outward;            エラー。越えた先で何をするか書かれていない
```

C-34 が `outward` を非推奨としたのは「呼び出し位置に何も現れない」からであり、
**せめて書き手の側では明示させる**のが一貫する。

## 5. フレーム越えのエラー

```
fn main () { { break break break 1; } }
```

`main` の本体（1 段）＋裸のブロック（1 段）で上限は 2 段。
三つ目の `break` が越えようとするので**制御のエラー**（C-46 の 3）。

**静的に数えられる。** `break` が三つ並んでいて、囲むフレームの深さが 2 なので。

```
fn f () { $repeat(break, n) 1; }
```

`n` が実行時の値なので**実行時に落ちる。** これが「制御のエラー」を
実行時エラーとして持たねばならない理由である（C-34 の A）。

**通る。**

## 6. `continue` の合成

```
loop {                        ← 深さ 1
    nfor (i, 0, 10) {         ← 深さ 2
        if (skip(i)) continue; fi;
        …
    };
};
```

`continue` は「1 段抜けて、外側のループを次の周回へ」（C-50）。
`nfor` を 1 段抜けて、**`nfor` の次の周回へ**。

外側の `loop` を次の周回にしたいなら：

```
break continue;
```

2 段抜けて、そこ（`loop`）を次の周回へ。**通る。**

### 🟡 問題5：`continue` の「1 段抜ける」の数え方

`continue` が抜けるのは**直近のループ本体**か、**直近の脱出段**か。

```
loop {
    { continue; };            ← 裸のブロックの中
};
```

`continue` が「1 段抜ける」なら、抜けるのは**裸のブロック**である。
そして裸のブロックはループではないので、「次の周回へ」の対象が無い。

- **エラーにする**——`continue` の抜けた先がループでなければ制御のエラー
- **ループまで探す**——脱出段を無視してループを探す

**前者を推す。** 後者は `continue` だけが段数を無視することになり、
`break` との対称性が壊れる。そして**書き手は `break continue;` と書けばよい。**

**規定が要る。** 現在の C-50 は `continue` を「1 段抜けて外側のループを次の周回へ」と
書いているが、**抜けた先がループでない場合を規定していない。**

## 7. まとめ

| # | 判定 |
|---|---|
| 1 | 🔴 `if` の分岐に `{ }` を書くと `break` が届かない。**規約で補う** |
| 2 | 🟡 `$return i; fi;` の `;` が二重。C-43 の代償として受け入れる |
| 3 | 🟡 脱出で束縛が起きない場合がある。**検査器が扱えればよい** |
| 4 | 🔴 **`outward` の被演算子を必須にする**（規定の追加） |
| 5 | 🔴 **`continue` の抜けた先がループでない場合を規定する**（規定の追加） |

**骨格は通った。** `break` の合成・`getdepth()` の使用位置評価・`outward` の
フレーム越え・段数の静的／動的な検査、いずれも意味論どおりに動く。

**規定の追加が二つ（4・5）、規約が一つ（1）。** 設計の変更は要らない。
