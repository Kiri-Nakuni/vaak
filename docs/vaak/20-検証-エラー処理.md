# 検証 1 — エラー処理

**paradox が言語全体を貫いているので、そこが破綻していないかは全体の健全性の指標になる。**

実装が無いので机上で追う。各行を意味論に照らし、**破綻を見つけたら記録する。**

---

## 1. 題材

```
%{ 成績表を読み、平均と最高点を出す }%

struct Record {
    let name : str;
    var score : i64 := 0;
};

fn average (rs : Record array alias) {
    var sum := 0;
    nfor (i, 0, rs.len()) {
        sum += rs[i].score;
    };
    sum / rs.len()
} -> i64;

fn best (rs : Record array alias) {
    var top := 0;
    nfor (i, 1, rs.len() - 1) {
        if (rs[i].score > rs[top].score) top := i; fi;
    };
    rs[top].name
} -> str;

fn grade_of (score : i64) {
    switch (score / 10)
        case 10 => "A"
        case 9  => "A"
        case 8  => "B"
        case 7  => "C"
    ?? "F"
} -> str;

var table : str i64 map := ( "alice" => 90, "bob" => 72 );

fn score_of (name : str) {
    table[name] ?? -1
} -> i64;
```

---

## 2. paradox の発生点を全部たどる

| # | 発生点 | 起きる条件 | 受けているもの | |
|---|---|---|---|---|
| 1 | `sum / rs.len()` | 配列が空 | **無い** | ✗ |
| 2 | `rs[i].score` | 範囲外 | **無い** | ✗ |
| 3 | `nfor (…) { … }` | 0周 | 直後の `;` | ✓ |
| 4 | `rs[top].name` | 配列が空 | **無い** | ✗ |
| 5 | `switch (…) case …` | どの腕にも当たらない | `?? "F"` | ✓ |
| 6 | `table[name]` | 欠損キー | `?? -1` | ✓ |
| 7 | `sum += …` などの宣言・代入 | 常に | 各行の `;` | ✓ |

**三つが受けられていない。** そして**それは正しい**——空の配列の平均に値は無い。

### 呼び出し側が受ける

```
let avg := average(rs) ?? 0;
let top := best(rs) ?? "（該当なし）";
```

**関数は paradox を返してよい**（C-28）。ただし**なぜ paradox だったかは分からない**——
代数的型が無いので情報を付けられない。ここでは「空だった」以外の理由が無いので足りる。

---

## 3. 見つかった問題

### 問題1：`??` の右辺に緩い式を書けない 🔴

```
table[name] ?? 0 - 1
```

`??` は優先順位 4、`-` は 5 である（C-27）。したがって：

```
(table[name] ?? 0) - 1
```

**欠損なら −1、存在すれば「値 − 1」になる。** 意図と違う。

```
table[name] ?? (0 - 1)      括弧が要る
table[name] ?? -1           前置マイナスは優先順位 2 なので、これは通る
```

**これは C-27 の代償である。** `??` を強くしたのは paradox を産んだ場所の直近に掛けるためだが、
**掛かるのは左だけで足りたのに、右にも強く掛かってしまう。**

**提案：`??` を非対称な優先順位にする**（採用、C-45。非対称なので右結合になる）。
左は強く（乗除の次）、**右は緩く**（加減より下）取る。

```
a + b / c ?? d + e     →  a + ((b / c) ?? (d + e))
```

左辺は「paradox を産んだ領域」に届き、右辺は「素朴に読んだ通りの式」になる。
非対称な優先順位は普通の道具ではないが、**`??` の左右は役割が違う**——
左は捕まえる対象、右は代わりに置く値である。**同じ強さで括る理由が無い。**

### 問題2：`nfor` の後の `;` を落としやすい 🟡

```
fn average (rs : Record array alias) {
    var sum := 0;
    nfor (i, 0, rs.len()) {
        sum += rs[i].score;
    }                       ← ここに ; が無いと
    sum / rs.len()
} -> i64;
```

`nfor` は**反復回数という値を産む**（C-3）。`;` が無ければ、
関数本体という一つの領域に**値が二つ**置かれる。エラーである。

**意味論としては正しい。** しかし C 系の言語から来た読み手は必ず落とす——
`for` の後に `;` を書く習慣が無いので。

**これは受け入れる。** ループが値を産むと決めた以上、避けられない。
そして**エラーは静的に出る**（領域に値が二つ、読み取り時に数えられる）ので、黙って動かない。

### 問題3：`switch` の `??` が腕の直後に見える 🟡

```
switch (score / 10)
    case 10 => "A"
    case 7  => "C"
?? "F"
```

`?? "F"` は **switch 全体**に掛かる（C-39）。しかし字面は**最後の腕の続き**に見える。

**改行と字下げで区別している。** 意味論は改行を見ないので、**規約に頼っている。**

代案は無い——腕の中で `??` を使いたければ括弧を書く、で一貫している。
**規約として書く。**

### 問題4：`rs[top].name` で `top` が有効か検査していない 🟢

```
fn best (rs : Record array alias) {
    var top := 0;
    nfor (i, 1, rs.len() - 1) { … };
    rs[top].name
} -> str;
```

配列が空なら `rs[0]` が範囲外 → paradox → 関数の値が paradox。
**呼び出し側が `??` で受ける。**

**言語として正しい。** 空の配列に「最高点」は無いので、paradox が正しい答えである。
`if (rs.len() == 0) …` のような番兵を書く必要が無い。

## 4. 通った確認

### `break` の paradox が消費されている

```
loop {
    if (done()) break; fi;
    step();
};
```

1. `break` の値は paradox（C-43）
2. `;` が潰す。分岐の中身に何も残らない
3. 分岐の領域が閉じる。中身が空 → 外界面は paradox
4. `if` の値が paradox
5. `fi` の後の `;` が潰す
6. **その後で脱出が起きる**

**paradox が二回産まれて二回消費されている。** どちらの `;` も要る。

### 0周のループが `;` で受かる

```
nfor (i, 0, 0) { … };
```

領域は `{}` になり、外界面は paradox（C-44）。`;` が潰す。**エラーにならない。**

値が欲しければ `?? 0` を書く。**書かなければ捨てる**という既定は、
「ループを回した結果に興味が無い」場合が多数派である以上、正しい。

### 空のループ本体が通る

```
loop { };
```

C-44 により**中身に何も残っていない**ので通る。無限ループとして正しい。

---

## 5. まとめ

| # | 判定 |
|---|---|
| 1 | 🔴 **`??` の優先順位を非対称にする提案。** 右辺に緩い式を書けない |
| 2 | 🟡 `nfor` の後の `;` を落としやすい。**静的に出るので受け入れる** |
| 3 | 🟡 `switch` の `??` が腕に見える。**規約で補う** |
| 4 | 🟢 番兵が要らない。paradox が正しい答えになっている |

**エラー処理の骨格は通った。** `??` が唯一の回復手段で、`;` が唯一の黙殺手段、
という C-22 の構造が、実際の題材でも成り立っている。

**問題1だけが設計の変更を要する。**
