# Vaak 設計判断

前身 REod の判断は [../../legacy/reod-tier1/docs/decisions.md](../../legacy/reod-tier1/docs/decisions.md)（D-1〜D-70）にある。
**却下理由は捨てない**（§1.5）。判断を変えたときも、誤りが見つかったときも、そのまま残す。

---

## C-1. 跳躍（`goto` / `comefrom` / `label`）を持たない

**決定**：任意跳躍を言語から外す。

**理由**：

> **`break` が動的に段数を取れる今、`goto` の誠実な運用はほとんど無い。**
> 足元を撃ち抜く自由は `loop` が与えている。

前身では `break` の段数が実行時の値でよく（`$repeat(break, getdepth())`）、
「今いる深さぶんだけ抜ける」を書き手が書けた。この機構が入った時点で、
`goto` が引き受けていた仕事の大半——多重ループからの脱出、早期リターン、
条件付きの巻き戻し——は構造化された形で書けるようになっていた。

残っていたのは「構造を無視して飛ぶ」ことそのものであり、
それを誠実に使う場面が挙げられない。**REod と Vaak の違いはここから始まる。**

**これは費用の問題ではない。** 実行時費用はほぼゼロ（使わなければ 0）、
実装は 96 行だった。同一性と汎用性（R4）の問題として決めた。

---

### 連鎖：この一つの決定が消すもの

跳躍を外すと、それを支えていた機構が根こそぎ不要になる。

| 消えるもの | なぜ |
|---|---|
| `label` / `comefrom` / `goto` | 決定そのもの |
| `#[flat]` | `goto` の走査からブロック構造の認識を外す属性。対象が消えた |
| `#[lazy_attribute]` | `#[flat]` を `flow` の使用位置で効かせるためだけに導入された。用途が消えた |
| 脱出後の動作のうち `Goto` / `Label` / `Comefrom` | `Value` と `Continue` だけが残る |
| フレーム基準の「`goto` の走査範囲」という役割 | 深さの原点と `break` の上限としては残る |
| **§4.3（跳び越される区間は構文解析されない）** | **消費者がいなくなる**（下記） |

### §4.3 が丸ごと消える

§4.3 の用途は3つあった。

1. `goto` で壊れた区間を跳び越す → **決定 C-1 で消滅**
2. ブロックコメント → **字句層へ移す**（C-2 で扱う）
3. TeX の `\iffalse … \fi` 同型の「隠しコードの安全性」 → 2 に吸収される

**消費者が一人もいなくなる。** したがって Vaak は
**すべてのコードが構文解析できることを要求する。**

### さらに連鎖：カーソル機械の存在理由が消える

前身がカーソル機械（AST を持たず、トークン列上をカーソルが走る）だったのは、
§4.3 を満たすためである。実行しない区間を解析しないには、
解析と実行を分離できない構造でなければならなかった。

**§4.3 が消えれば、その制約も消える。**

| | 測定値 |
|---|---|
| 走査・読み飛ばし（実行しないためだけのコード） | **208行**が不要になる |
| カーソル機械の実行時費用 | **2.7倍**（同じ意味論の AST 実装との実測比） |

つまり **C-1 は R2（性能）に直接効く。** 跳躍の実行時費用はゼロだったが、
跳躍のために選んだ実装方式が 2.7倍を払っていた。

### 副産物1：道具経路が完全になる

前身の §1.5 は「道具経路は不完全でよい」と書いていた。**§4.3 が強制していたからである。**

すべてのコードが解析できるなら、パーサは全部を見る。
LSP・型検査・tree-sitter 文法が**正確になる**。
前身で必要だった回避策（式位置のブロックを別規則に分けるハック、
跳び越される区間が ERROR ノードになる問題）が消える。

### 副産物2：ブロックコメントに何でも書けるようになる

前身のブロックコメントは `#[flat] goto` からの導出だったため、
**字句解析の後**に読み飛ばされていた。したがって字句が通る文字しか置けず、
**日本語の句点 `。` で落ちた**（[../非直感性.md](../非直感性.md) §6）。

字句層に置けば `%` 行コメントと同じく**字句解析より前に消える**ので、
中身に何を書いてもよくなる。**日本語で書く言語として、これは実害の解消である。**

---

### 却下した案

- **`goto` を残し、跳び先を構造的に制限する**（ループの外へ出るだけ、等）。
  制限した `goto` は `break` の段数で書けるものと一致するので、
  **同じ操作に二つの構文を与えることになる**（PHECL 原則6）。
- **`comefrom` だけ残す。** 前身で「かなり Vaak 的」と評価された機構であり、
  逆向きのフックという他に代替の無い性質を持つ。しかし
  **どこから制御が来るかがソースから決まらない**ので、§1.2 の境界基準
  （読み手がソースだけから、どの演算がどの順で走るかを決められること）に落ちる。
  前身の設計時にこの基準は無かった。
- **§4.3 だけ残す**（跳躍は外すが、実行しない区間は解析しない）。
  R5（コンパイラビリティ）と両立しない。かつ、消費者がいない性質を
  仕様に残すことになる。

---

### 失うもの（記録）

- 逆向きフック（`comefrom`）。ある文を通過するたびに別の場所へ制御を渡す、という書き方
- 前身の `ex5_comefrom.reod` / `ex6_goto_reset.reod` は Vaak では書けない
- TeX の `\iffalse … \fi` を言語機構として持つこと。**字句層のブロックコメントで代替する**

**代替可能性は確認していない。** `ex6_goto_reset.reod` が `loop` と `break` で
書き直せるかは、構文が決まってから凍結実装と突き合わせて確かめる。
書き直せない場合、それは C-1 の再検討事由になる。

## C-2. Vaak は状態を巻き戻さない

**決定**：言語の機構としての巻き戻し（save stack / ジャーナル）を持たない。

前身は3つの規律を持っていた——`if` 本体はレベル無し、ループ本体は checkpoint（正常終了で破棄）、
裸のブロックと関数本体は group（退出で適用）。これを**ゼロにする**。

### 判断基準

巻き戻しの可否は、次の三つで判定する。以後の拡張もこの基準に掛ける。

**基準1（§1.2 の境界基準から）**
> 巻き戻しが起きる場所が、ソースに現れているか。

暗黙の巻き戻しは、**書いてある代入が、それに言及しない構文によって取り消される**ことを意味する。
読み手はソースから「どの代入が効くか」を決められない。**落ちる。**
明示的な構文——「ここから群」と書いてあるもの——なら通る。

**基準2（R4 から）**
> その状態は Vaak のものか、ホストのものか。

ホストの状態なら、ホストが決める。Vaak が代行しない。

**基準3（R2 から）**
> 使わないプログラムが費用を払うか。

払うなら opt-in でなければならない。ジャーナルは**書き込みのたびに** undo を記録するので、
常時有効なら全プログラムが払う。

### 適用

| | 判定 | 理由 |
|---|---|---|
| ブロック局所の名前が外に漏れないこと | **機構不要** | 字句スコープの構造から出る。ジャーナルの仕事ではなかった |
| 跳躍の巻き戻し先 | **消滅** | C-1 |
| ループ本体 | 巻き戻さない | D-2r（前身）——蓄積器が壊れる |
| 関数の退出 | 巻き戻さない | 局所はフレームを畳むだけ |
| 裸のブロック | 巻き戻さない | 閉じ込めは束縛の選択で書く（下記） |
| レジスタ層 | 巻き戻さない | 「速い確保階層」に巻き戻しの理由は無い。TeX から借りた概念に、TeX の挙動が付いてきていただけだった |
| ホストのメモリへの書き込み | **ホストの領分** | 基準2 |

### 閉じ込めは束縛の選択で表現する

変更を外へ漏らしたくないなら、**自分のセルを持つ**（値の束縛）。漏らしたいなら**共有する**（`&=`）。

```
自分のセル   → 書いても外に影響しない
共有         → 書けば外も動く
```

スコープ規則ではなく**束縛の位置に書いてある**ので、読み手は探さなくてよい。基準1を通る。

費用も逆転する。

| | |
|---|---|
| ジャーナル | レベル push は O(1)。ただし**書き込みのたびに記録** = O(書き込み回数) |
| 自分のセルを持つ | 変数ごとに1回 = O(変数の数) |

ループがあれば書き込み回数が変数の数を圧倒する。**複製が勝つ。**

### 拡張の余地の残し方

> **Vaak は「書き込みが取り消されない」ことを規定しない。
> 「Vaak 自身は取り消さない」ことを規定する。**

ホストがジャーナルを持つことを禁じない。将来 Vaak に明示的な群構文を足すことも禁じない。
基準1により、足すなら**必ず見える形になる**というだけである。

### 連鎖

| | |
|---|---|
| **波括弧の意味が1つになる** | `if` は既に別記法（`break` に透明である必要から領域ではありえない）。残る `{ }` は裸のブロックとループ本体だけで、両方が「巻き戻さない領域」で同一 |
| **前身の非直感性 #1 が消滅** | 「関数からの外部代入が黙って消える」（カウンタが数えない）は関数本体が group だったから起きていた。エラー検査も `#[global]` も要らなくなる |
| 前身の非直感性 #2 が消滅 | 「メモ化が巻き戻らない」——巻き戻し自体が無い。C-1 と先行評価と合わせて、前身の6項目のうち5つが消える |
| **書き込みごとの費用が消える** | R2。151行と、代入ごとの記録が不要になる |

### 失うもの（記録）

**「TeX の save stack と同型の巻き戻し」は、前身を他言語と区別していた4つの機構の一つだった。**
C-1（跳躍）と合わせて2つが消える。

Vaak の特徴として残るのは、**領域と虚無**、**動的段数の脱出と作用素式**、**完全後置型修飾**、
そして（C-3 で扱う）**ホストとの無変換共有**である。

### 却下した案

- **レジスタ層だけ巻き戻す。** TeX の save stack が本来保存しているのはレジスタとパラメータなので、
  相続分としては正確である。しかし前身の §3.7 はレジスタ層を**言語のメモリモデル**（一様に安い確保階層）
  として定義していた。**速い確保階層に巻き戻しが要る理由は無い。**
  TeX のレジスタそのものを指すなら、群を管理しているのはホストであって Vaak ではない。どちらの読みでも要らない。
- **フレーム境界だけ巻き戻す。** 前身の非直感性 #1 がそのまま残る。
  そして字句スコープでは局所がフレームを畳むだけで消えるので、ジャーナルの仕事が無い。

## C-3. ループは反復回数を産む演算子である

**決定**：`loop` / `while` / `nfor` / `ifor` の値は**反復回数**。
ただし0周なら **paradox**。`break V` があればそれが上書きする。

### ループの領域には、本当に N 個の値がある

この判断に至るまでに二度誤ったので、両方記録する。

**誤り1（規定を導出と偽った）：**

> ループ本体は周回ごとに領域を作り、各周回が自分の値をループの領域に置く。
> 領域はちょうど一つを持つので、**後の周回が前を置き換える**。

N 個のうちどれを選ぶかは規則から出ない。**恣意的な規定であって導出ではなかった。**

**誤り2（過剰に訂正した）：**

> 本体の各周回の値は内側の領域にあり、**ループの領域には入らない**。

これも違う。`loop { 1 }` は

```
{1} {1} {1} …
```

を意味する。各内側の領域はちょうど一つの値を持つので問題ないが、
**ループの領域はこの全体である。** したがって外から見て **N 個の値が存在する。**

### 消費するものは無い。ゆえに本体は値を置いてはならない

`1 2` が通らないのは**消費するものが間に無い**からである。
そして**ループは消費しない。** 溜まるだけである。

したがって：

> **ループ本体は値を置いてはならない。** 置けば N 周で N 個が溜まり、N ≥ 2 で規則違反になる。

`loop { 1 }` は——循環が高々一回のときを除き——**エラーである。**

本体が `;` で終われば、置かれるのはアーカーシャであり、アーカーシャは領域を占めない。
**ループの領域は空のままになる。** その上で、ループが自分の値を置く。

### 何を産むか

**反復回数。**

| | 値 |
|---|---|
| N ≥ 1 周して正常終了 | **N** |
| **0 周**（条件が最初から偽、空範囲） | **paradox** |
| `break V` | **V**（上書き） |
| 値の無い `break` | 打ち切りまでの回数 |

### 0周が paradox である理由

**回らなかったなら、中はアーカーシャである。** 何も起きていない。
そして**アーカーシャを値の位置に置けば paradox へ輪廻する**——既にある規則がそのまま効く。

「回数は 0 である」ではない。**数えるべきものが無かった。**

### 理由はエラーハンドリングである

0 周のときに数値 `0` を返すと、「一度も回らなかった」ことを**呼び出し側が検出できない**。
paradox ならフォールバック演算子がそのまま受ける。

```
while cond { … } ?? 回らなかったときの値
```

空範囲の探索、空の入力、条件が最初から成立しない集計——いずれも**そこで気づきたい**場面である。
連想配列の欠損キーが paradox を産むのと同じ形をしている。

### 前身との違い（記録）

前身も `while` の値を反復回数としていたが、**理由が違った**——原始再帰（`nfor`）と μ再帰（`while`）の
対応という、計算可能性の梯子からの正当化だった。

**その正当化は PHECL 原則10（数学的に綺麗であることのみを理由として…）に掛かる。**
今回は同じ結論に、**エラーハンドリングという実用上の理由**から到達した。
結論が同じでも理由が違うので、**両方を記録する。**

そして 0 周の扱いが違う。前身の梯子からは 0 が出る。**paradox はエラーハンドリングの要求から出る。**

### これは規定である

「ループが反復回数を産む」ことは、規則から導出されない。
**`+` が和を産むのと同じ圏の規定である。** 正当化はエラーハンドリングのみ（上記）。

一時、**「N 個の値を消費した演算子が恣意的な選択なしに産める値は個数しか無い」**という
論証を立てたが、これは**ループが本体の値を消費するという誤った前提**に依っていた。
ループは消費しない。溜めるだけである。したがってこの論証は成立しない。**規定は素の規定である。**

**導出でないことは書いておく。** PHECL は守るべき原則の集合ではないので規定してよいが、
規定を導出と偽ることはしない。

### 検査は静的に課す（意図的な判断）

「ループ本体は値を置いてはならない」を**静的に**課す。本体の末尾が値を置く形なら、
実際に何周するかによらず拒否する。`loop { 1 }` は常にエラーである。

**これは意味論からの直接の示唆ではない。** 意味論が言うのは「領域はちょうど一つの値を持つ」だけで、
N が 1 なら規則を満たす。したがって動的に課せば「循環が高々一回なら通る」が正しい。

**それでも禁止する。** 理由：

- **「たまたま一回しか回らなかったので通った」プログラムが書ける。** 同じソースが、
  入力によって通ったり落ちたりする。書かれたものから可否が決まらない
- §1.5 の約束——**値がいくつ置かれるかは走らせなくても数えられる**——が、ループでだけ破れる

**意図的な判断であることを明記する。** 導出ではない。禁止する価値があると判断した。

## C-4. `switch` を持つ

**決定**：値による多分岐を中核構文として持つ。`match` には昇格させない。

**中核である理由**：導出する手段が無い。腕は**選ばれてから評価される**ので、
先行評価では標準ライブラリに置けない（`while` と同じ理由——C-3）。
したがって「`if` の連鎖を書き手が書く」か「中核構文にする」かの二択であり、後者を採る。

**`match` に昇格させない理由**：代数的型を持たないので、パターンマッチは**二つの別操作に分解する。**

| | 失敗しうるか |
|---|---|
| 値の照合（`switch` 相当） | **する**。どの腕か決まっていない |
| 順序対・構造体の分解 | **しない**。形は一つしかないので常に成功する |

ML や Rust で `match` がこの二つを一つにできるのは**バリアントがあるから**である。
「どの構成子か」を判定した結果として「そのフィールドを束縛する」ので、一つの操作になる。

バリアントが無ければ、一方は分岐で、他方は束縛である。**無関係な操作である。**

> 6. 人間の価値観の都合で、異なる処理を同じ構文に抽象化しないこと — anti-C++

**分解は束縛の形で別に与える**（決定Dで詳細）。そうすると：

- 分解が関数の引数位置でもループの中でも使える。腕の中に閉じ込められない
- 失敗しない操作が、失敗しうる構文の中に入らない
- **実装費用が構文糖の水準まで落ちる。** パターンの木も照合の再帰も要らない——形は一つしかないので

前身は `match` → `switch` に改名していた（ADT が無いのでパターンマッチではない、D-32）。
**同じ結論に別の原則から到達した**ことになる。

## C-5. レジスタ層を言語仕様から外す

**決定**：0–255 のレジスタ層を言語の機能として持たない。**ホストへの依存機能**とする。
POSIX Vaak は持たない。

前身の §3.7 はこれを「型ごとに1つ確保される単一のレジスタ層オブジェクト、一様に安い経路しかない」
と定義していた。存在理由は二つあった。

1. TeX のレジスタとの対応（群の意味論を含む）
2. 一様に安い確保階層

**1 は C-2 で消えた**（巻き戻しを持たない）。残る 2 だけでは、
**0–255 という上限を言語仕様に置く理由にならない。** 単に速い確保があればよく、
番号で区切る必然が無い。

そして `&=` が**ホストとの無変換共有の中核**に格上げされた（C-2 の議論）ことで、
「ホストの記憶域を名前で掴む」機能は既に別の形で存在する。
**レジスタ層はその特殊例に過ぎない。**

したがって、TeX のレジスタを掴みたければ `&=` でホストの記憶域に別名を張る。
言語は 0–255 を知らなくてよい。

**R4（やや汎用的であること）の具体的な帰結の一つである。**

## C-6. 集合体の既定は複製である。費用は隠さず示す

**決定**：`:=` は複製、`&=` は共有。**集合体でも同じ**。配列を `let b := a;` と書けば複製が走る。

C-2 で「閉じ込めは束縛の選択で表現する」と決めた時点で、これは従っている。
`:=` が共有なら、閉じ込めを書く手段が無くなる。

### 費用について

**既定が高い。** 大きい配列を渡すたびに複製が走る。安くしたければ `&=` と書く。

**これを欠点として隠さない。** 複製は素朴である——**値は値である**。
高いのはその**帰結**であって、意味論の失敗ではない。

> **費用は帰結として、積極的に示す。**

「渡すと複製される」は書かれたものを見れば分かる。`&=` と書けば共有される。
どちらも見える。**隠された最適化も、隠された共有も無い。**

これは §1.2 の境界基準（読み手がソースだけから、どの演算がどの順で走るかを決められる）を
**費用の側に延長したもの**である。原則として §1 に置く。

### 却下した案

- **集合体だけ共有を既定にする**（スカラは複製、配列は共有）。速いが、
  **同じ演算子が型によって違う操作になる**（PHECL 原則6）。
  そして閉じ込めを書く手段が集合体について失われる。
- **`^=` を「深い複製」として復活させる。** `:=` が既に複製なので、区別する対象が無い。

## C-7. 文字列は `u8 array` である。UTF-8 は標準ライブラリが扱う

**決定**：`str` は `u8 array` の別名。**言語は文字を知らない。**

- 添字は**バイトを返す**。文字ではない
- 長さは**バイト数**
- UTF-8 の解釈——符号位置の切り出し、文字数、境界の判定——は
  **無名標準ライブラリのメソッドが提供する**

**言語が文字を知らないことは、隠蔽ではなく開示である。**
「1文字」を言語が定義すると、UTF-8 の符号位置なのか書記素クラスタなのかを
設計者が勝手に決めることになる。PHECL 本文：

> その判断を誰が行ったのか、何を捨てたのか、何を同一視したのかが明らかでなければならない。

標準ライブラリのメソッドとして提供すれば、**何を「1文字」と数えているかがメソッド名に現れる。**
そして二層構造（§2.4）により、剥がして生のバイトを触ることもできる。

**文字列リテラルは字句層に要る。** ただし数値リテラルと同じ規律に従う——
**型が決まるまでソースの表現を保持する**（ホスト方言が別の文字列型を持ちうるため）。

## C-8. 反復子を持たない。列は配列だけである

**決定**：`ifor` も反復子プロトコルも「反復可能な型」という概念も持たない。

| | 反復の書き方 |
|---|---|
| 配列・文字列 | `nfor` ＋ 添字 |
| 連想配列 | **`.keys()` が配列を返す** → `nfor` ＋ 添字 |

**言語が知る列は配列だけ。** 反復したいものは配列を作る。

`nfor` は三つの被演算子を取る——**束縛する名前、開始、終了**。範囲は値ではなく構文の一部なので、
範囲型は要らない。**歩幅は取らない。歩幅が要るなら配列を作る。**

### 理由

- **概念が増えない。** trait の無い言語で反復子を入れると、**言語が反復可能な型を固定列挙する**
  ことになり、拡張の余地が構造的に閉じる
- **費用がちょうど見えるところに出る**（C-6）。`m.keys()` は配列を確保する。それは高い。
  **そして高いことが呼び出しとして書かれている**
- **中核が一つ減る。** C-3 で `while` と `switch` が「先行評価だから中核でしかありえない」として
  増えたばかりなので、減らせるものは減らす
- 添字が見える。要素と位置の両方が要る場面は多い

### 代償と、逃げ道（今は入れない）

連想配列の反復が**確保を伴う**。大きい写像を回すたびに鍵の配列ができる。

許容できなくなったときは、**中核を変えずに足せる**——カーソルと paradox の組み合わせで：

```
loop {
    let k := m.next(c) ?? break;
    …
}
```

`break` は作用素式なので**フォールバック演算子の右辺に置ける**。
「次が無ければ抜ける」が、既にある機構だけで書ける。

**今は入れない。** 必要が実測で出てから足す。R3（素朴で根本的な表現能力）に照らして、
最初から入れる理由が挙がらない。

## C-9. 無名ブロックは引数を取らない（現時点）

**決定**：無名ブロックは前身と同じく**引数を持たない**。外の名前は見える。
「封じたブロック」は入れない。

### 経緯：クロージャ嫌悪の正体

議論の途中で、クロージャを避ける理由が特定された。**機構ではなく、捕捉を隠す界面宣言である。**

```
|x| x + y
```

引数リストは `x` しか挙げていないのに、`y` も入力である。
**リストは入力の一部だけを列挙し、残りを隠す。**

> Syntax は Semantic を誠実に示唆しなければならない。

引数リストは界面の宣言であり、**それが嘘をついている。**

### 誠実な形はちょうど二つある

| | 引数リスト | 外の名前が見えるか | |
|---|---|---|---|
| **裸のブロック** | **無い** | 見える | **沈黙による誠実**。何も主張しないので嘘がない |
| **封じたブロック** | 有る | **見えない** | **完全性による誠実**。リストが入力の全部 |
| ラムダ | 有る | 見える | **嘘** |

前身の無名ブロックが好まれたのは、**引数リストが無いから嘘をつきようがなかった**からである。
そして「使いやすくない」のは、界面が書けないからである。

### それでも今は入れない理由

**封じたブロックの用途が、具体的に挙がらない。**

前身の `plain2_blocks.reod` に現れた用途は三つだった——
一時変数の囲い込み、早期脱出、式の途中の計算。このうち：

- **早期脱出は `if/else` が式なので不要**
- **一時変数の囲い込みには引数が要らない**
- 残るのは「同じ計算を違う入力で二度書きたい」場合だが、それは**関数を定義すればよい**

用途が無いまま記号を消費しない。C-8 でカーソルを見送ったのと同じ規律である——
**必要が実測で出てから足す。**

### 却下した記法（記録）

**`|{ … }|`。** 「封じる」を視覚的に正しく示唆し、`{ }` とも区別が付く。
しかし **`|` はラムダの標識として最も強く定着した記号**である（Rust、Ruby）。

**ラムダではないものを作るのに、ラムダの記号を借りることになる。**
読み手は捕捉があると期待し、無い。D-70（前身）で `:=` について記録したのと**同じ型の誤り**である。

副次的に、`|` を二項演算子（ビット論理和）に使うなら `a |{ … }|` と `a | { … } |` の区別が要る。

**再開するときは、`if … fi` に合わせてキーワードで囲う形から検討する。**
記号は連想に依存するが、語は意味を持つ。

## C-10. `if` は演算子である。分岐は被演算子位置である

**決定**：読みA を採る。`if` の分岐は**領域だが、スコープでも脱出段でもない**。

| | 領域 | スコープ | 脱出段 |
|---|---|---|---|
| `if` の分岐 | ○ | **×** | **×** |

**`break` に透明であることが導出で従う。** 被演算子位置は脱出段ではないので、
`loop { if c { break; } … }` の `break` はループを抜ける。個別の規定が要らない。

`if` 全体の値は `if` が産む。`1 + 2` の 3 を `+` が産むのと同じ圏である。

### 帰結：分岐の中で導入した名前は外へ漏れる

スコープではないので。**閉じ込めたいなら裸のブロックを使う**——それが `{ }` の仕事である。

これは損失ではなく、**役割の分離**である。`if` は分岐であって、閉じ込めではない。
二つが要るなら二つ書く。

### 読みB を却下した理由

「分岐は領域かつスコープだが脱出段ではない」。名前は漏れないが、
**脱出段でないことを個別に規定する必要がある。** 読みAは規定を一つも要さない。

## C-11. 構造体とメンバ関数を持つ

**決定**：構造体を持ち、メンバ関数をレシーバ型で解決する（静的）。

### PHECL 原則6 との関係

`foo.len()` が型によって違うコードを呼ぶことは、原則6（異なる処理を同じ構文に抽象化しない）の
検査対象になる。**しかし緊張は激しくない。**

> `foo.len()` は `len()` という関数ではない。**ある種の名前空間を持っている。**

`.` は型の名前空間を開く演算子であり、`foo.len` と `bar.len` は**別の名前**である。
同じ構文に異なる処理を押し込んでいるのではなく、**異なる名前が異なる処理を指している。**

### ただしコーディング規則として指示する

名前空間が分かれていても、**同じ名前が型ごとに違う意味を持てば読み手は誤る。**

> **同じメンバ関数名は、型が違っても同じ意味を持たねばならない。**
> `.len()` が「要素数」なら、どの型でも要素数である。バイト数を返す型と要素数を返す型が
> 同じ名前を使ってはならない。

これは**処理系が検査できない**。規約として書き、レビューで守る。
PHECL 本文の「何を同一視したのかが明らかでなければならない」に対する、この言語の答えである。

## C-12. 複合代入は糖衣である

**決定**：`x += E` は `x := x + E` の糖衣。導出であり、中核ではない。

前身では `+=` が**強制点**であり、`:=` とは別操作だった——`x := x + 1` は
自己参照 thunk を作って発散し、`x += 1` は左辺を強制した。

**先行評価にした時点で、この区別が消えた。** `x := x + 1` は普通に動く。
したがって `+=` に独立した意味論は無い。

前身の非直感性 #4（`x := f(x)` が発散する）が消えたことの、直接の帰結である。

## C-13. 名前検査を持ち、それを抑止する手段を持つ

**決定**：名前が存在することを検査する。相互再帰と前方参照のために、**抑止する手段**を持つ。

### 帰結：属性機構が生き残る

前身の属性は**全部消えた**。

| | |
|---|---|
| `#[immediate]` | 先行評価なので消滅 |
| `#[global]` | 巻き戻しが無いので消滅（C-2） |
| `#[flat]` | 跳躍が無いので消滅（C-1） |
| `#[lazy_attribute]` | 同上 |
| **名前検査の抑止** | **残る** |

**残るのがこれ一つなら、属性という一般機構を持つ必要があるかは別途決める。**
専用の構文（前方宣言など）で足りるなら、属性機構ごと落とせる。

一つしか使わない一般機構を持つ理由は無い——PHECL 原則9（無駄に階層化しないこと）。

## C-14. 値・虚無・paradox の規則と、`??` の位置づけ

**決定**：次の三規則を中核とする。

1. **領域は終結した時点で値を持つ**
2. 領域の内部が**アーカーシャ**であるか、領域内の値が **paradox** であるなら、
   その領域の値は **paradox**
3. paradox は**アーカーシャに潰す**（`;`）か、**`??` で消す**かしなければならない

paradox は領域の閉じを通って伝播するが、**終結した領域の値としては残存しない**——規則3が消費を要求する。

### `??` は領域を一度閉じて開き直す

> **`??` は直前の領域を一度閉じてから開き直す操作である。**

閉じれば規則2によりアーカーシャと paradox の区別が **paradox 側に潰れる**。
開き直せば paradox は領域の値として残らない。

**これは恣意的な設計ではなく、規則1から出る。** 値の不在は**閉じた瞬間にしか観測できない**ので、
不在を検出する演算子は閉じることを強制するしかない。

そして `??` が領域の境界を操作する唯一の演算子であることも、これで説明が付く——
**不在の検出を仕事にしている唯一の演算子**だからである。他の演算子は値を扱うので境界に触らない。

### 優先順位は最低（`;` の次）

`??` は境界そのものを操作するので、**優先順位が意味に直結する**。
`+` は境界に無関心なので優先順位を知らなくても意味は変わらないが、`??` は変わる。

最低優先順位にすれば `a + b ?? c` は `(a + b) ?? c` となり、
**「その式の全体」が閉じる領域**になる。素朴な読みと一致し、境界を逆算する必要がほぼ消える。

### 記録：代数的型を持たないことによる緩やかな緊張

`??` は ADT のある言語における `Option` + `unwrap_or` に相当する。ADT が無いので、
**「値があるかもしれない」が型に現れない。**

**null の病は起きない。** paradox は規則3により消費が強制されるので、変数に入って遠くで落ちることがない。

**残る緊張は二つ。いずれも緩やか。**

1. **どの領域を閉じるかが暗黙になる。**
   `{E ?? D} -> T` は閉じる領域が書いてあるが、`let x : T := E ?? D;` は暗黙の被演算子領域である。
   最低優先順位にすることで実害はほぼ消えるが、消えはしない
2. **型注釈が `??` から離れる。**
   `{E ?? D} -> T` では `->` が閉じた領域の値に直接付くが、
   `let x : T := E ?? D;` では `T` が `x` に付いていて `??` から離れている。
   完全後置型修飾が持っている性質が、`let` の側では弱まる

**ADT を入れて解消しない。** 入れると C-4 が反転し（バリアントができるので `match` が正当になり、
`switch` と分解を統合すべきになる）、網羅性検査も要る。**言語の規模が一段変わる。**
得られるのは「paradox が型に現れる」ことだけで、それは**構文的識別と検査器で代替できる**——
paradox が生じうる場所（連想配列の添字、`while`/`nfor` の 0周、`else` の無い `if`、
剥がされたホスト別名）は**すべて構文的に識別できる**。R3 に照らして割に合わない。

## C-15. `|>` を持つ

**決定**：`x |> f(a)` は `f(x, a)` の糖衣。中核構文。

第一級関数を要求しない。**構文の水準で定義される。**

`g(f(x))` は内側から外へ読むが、`x |> f() |> g()` は**書いた順に走る**。
§1.2 の境界基準を通るだけでなく、改善する。完全後置型修飾とも向きが揃う。

### `.` との境界（規定）

> **`.` は型の名前空間を開く。`|>` は自由関数に適用する。**

`x |> f()` は `x` の型の名前空間を探しに行かない。探すなら `.` を書く。
これを分けないと、同じ処理に二つの構文を与えることになる（PHECL 原則6）。

## C-18. 型検査は別プログラムである

**決定**：標準実装（POSIX Vaak）は型検査をしない。検査は**独立したプログラム**が行う。

R1（起動が速いこと）から従う。実行前に全体を検査する相を持てば起動が遅くなる。

**「硬い POSIX Vaak」**——検査を行う版——を別に作ってよい。
同じ意味論の上で、受理する範囲が狭い実装になる。
前身で検討した「固い REod」（[../固いREod.md](../固いREod.md)）が、
方言ではなく**検査器**という形で実現することになる。

## C-19. 別名と実値は本質的に区別する

**決定**：別名であることは**型に現れる**。そして別名は自分より短命なものを指せない。

C-2（巻き戻しを持たない）と字句スコープを組み合わせた時点で、**宙ぶらりんの参照が作れてしまう**
穴が開いていた。前身では巻き戻しがこれを塞いでいた（ブロック退出で束縛が戻る）。

```
let outer := 0;
{
    let inner := …;
    outer &= inner;      ← inner のスコープが終わると outer は何を指すのか
}
```

### 三つの規則で塞ぐ

**1. 別名であることは型に現れる**

値の名前と別名の名前は**別の型を持つ**。`let outer := 0;` と宣言した名前に `&=` はできない。
完全後置型修飾があるので、型の側に置ける（記法は構文設計で決める）。

**2. 別名は、同じか外側のスコープで宣言されたものしか指せない**

> **別名の対象は、その別名と同じか外側で宣言されていなければならない。**

字句スコープなので**宣言の深さを比べるだけ**で検査できる。実行時費用はゼロ。
借用検査器も生存期間の型付けも要らない。

素朴である——「自分より長生きするものしか指せない」。
そして両方の宣言がソースに見えるので §1.2 を通る。

**3. 関数は別名を返せない**

局所への別名を返せば同じ穴が開く。**保守的に禁止する。**
必要なら別名を引数で渡す。緩めるのは後からできる。

### 副産物：所有が完全に字句的になる

C-6（複製が既定）と合わせると、**メモリモデルが確定する。**

| | |
|---|---|
| 値 | 宣言したスコープが所有する。スコープが終われば解放 |
| 複製 | 新しい所有者ができる |
| 別名 | **所有しない**。対象より長生きしない |
| ホストのメモリへの別名 | ホストの所有。無効化はホスト契約。剥がされた別名は paradox を産む |

**GC も参照カウントも要らない。** 「GC は無し」が、穴のある主張から**導出された性質**になる。

そしてこれは C-6 にとって不可欠である。`&=` は複製の高さから逃げる唯一の道なので、
**`&=` が安全でなければ C-6 の費用の話が破綻していた。**

## C-20. 束縛が複製する。アクセスは複製しない

**決定**：複製か別名かは、次の一つの原則で決まる。

> **束縛が複製する。アクセスは複製しない。**
> **別名であることは型にあるので（C-19）、すべての束縛地点が「値か別名か」を宣言する。**

| | 判定 | 理由 |
|---|---|---|
| `let x := E` / `x := E` | **複製** | 束縛 |
| `let x &= E` | 別名 | 束縛（別名と宣言している） |
| **`.` によるアクセス** | **複製しない** | **束縛ではない** |
| **`[]` によるアクセス** | **複製しない** | 同上 |
| `s.field` を読む | 複製しない | 同上 |
| **メンバ関数のレシーバ** | **複製しない** | `.` はアクセスだから |
| `a[i] := v` | アクセスで場所を得て、そこに束縛 | 二段階 |
| **関数の引数** | **宣言が決める** | `fn f(a : T)` は複製、`fn f(a : T alias)` は別名 |
| 関数の返り値 | 値のみ | C-19（別名は返せない） |
| ホストのメモリ | 別名 | C-2 |

### `.` が複製しないことは導出である

「`.` だけ特別扱い」ではない。**アクセスは束縛ではない**から複製しない。
`[]` も `s.field` も同じ規則に乗る。

### 関数の引数は C-19 で既に解けていた

別名であることが型にあるなら、**関数の宣言が「複製で受ける」か「別名で受ける」かを書く。**
呼び出し側は署名を見れば分かる。

**大きい集合体を渡す関数は `alias` で受けると宣言に書く**——費用が署名に現れる。
C-6 の「費用は帰結として示す」がここでも効く。

### メンバ関数はレシーバを破壊する

レシーバが複製されない以上、メンバ関数は**レシーバを書き換える**。

**複製したいなら明示する。**

```
let sorted_arr := arr;      % ここで複製される（束縛だから）
sorted_arr.sort();          % 複製の方を並べ替える
```

やや煩雑だが、許容できないほどではない。そして**複製が起きる場所が一行として見える**——
`arr.sorted()` のような非破壊版を用意して隠すより、C-6 の原則に忠実である。

### 破壊は呼び出し側から見えない。規約で補う

`arr.sort()` は破壊し、`arr.len()` はしない。`f(x)` は宣言次第で破壊する。
**どれも字面が同じである。** 読み手は宣言を見に行かないと分からない。

§1.2 の境界基準は「どの演算がどの順で走るか」を要求しており、
**「何が壊れるか」は要求していない**。厳密には違反ではないが、同じ精神に属する。

**規約で補う。** C-11 の規約に次を足す。

> **メンバ関数の名前は、レシーバを破壊するかどうかを示さねばならない。**
> `sort` が破壊するなら、非破壊版は別の名前（`sorted` 等）を持つ。

**呼び出し側に印を付ける案は却下する。** 別名であることは既に型にある（C-19）ので、
呼び出し側にも書かせるのは同じ情報の二重化になる。

そして**補っていることを書く**——PHECL 本文の
「設計者自身が、何を隠し、何を同一視し、何を前提としていたのかを自覚することの請求」に対する答えである。

### 二段階に分かれていることが効く

`let x := a[i];` は正しく複製する。**アクセスは複製しないが、その結果を束縛すれば複製される。**
二段階が分かれているので、どちらも素朴に読める。

## C-21. 数値の意味論

**決定**：

| | |
|---|---|
| **溢れ** | **折り返す**。最も素朴 |
| **暗黙変換** | **禁止**。異なる数値型の混在は書けない（Rust に倣う） |
| **0 除算** | **paradox を産む** |
| **真偽値** | **`u1`**。独立した型ではなく、1ビット符号なし整数 |
| **`if` の条件** | **`u1` のみ** |
| **`while` の条件** | **任意の整数型。0 以外で継続** |
| **比較演算子** | **`u1` を返す** |

### `u1` が bool であることの効き方

真偽値が数値型族の一員なので、**型体系に bool を足さなくてよい**。
そして `if` が `u1` しか取らないので、**真偽値らしさ（truthiness）が存在しない。**
`if some_i64` は書けない。

### `if` と `while` の条件が違うのは、変換ではない

当初これは「`while` だけ暗黙のキャストを許す妥協点」と考えられたが、**妥協は要らない。**

- **`if E`** — E は `u1`。**真偽の検査**である
- **`while E`** — E は任意の整数型。**`E ≠ 0` の検査**である

**二つは違う述語であって、変換は起きていない。** `while` は μ 作用素であり、
μ 再帰は「f(x) = 0 となる最小の x を探す」ものなので、
**整数に対する `≠ 0` の検査が `while` の本来の姿である。**

比較演算子が `u1` を返し、`u1` は整数型なので、`while x < 10` も自然に通る——
`u1` に対する `≠ 0` の検査になる。**規則は一つのままである。**

> 過度な理論に動機づけられるのは避けるが、**実際をよく再現する理論があることは望ましい。**

### 0 除算が paradox であることの効き方

エラー処理が `??` に一本化される。

```
a / b ?? 既定値
```

そして **paradox を産む場所の一覧に加わる**——連想配列の欠損キー、
`while`/`nfor` の 0周、`else` の無い `if`、剥がされたホスト別名、**0 除算**。
いずれも構文的に識別できる（C-14）。

## C-22. エラーは一つしかない

**決定**：**言語の実行時エラーは「消費されなかった paradox」ただ一つである。**

| | |
|---|---|
| エラーの正体 | **領域の終結時に paradox が残ること** |
| エラーは値か | **値ではない。純粋な副作用である** |
| 起きたら | **処理を即座に終了する** |
| ホストが受け取るもの | **paradox の発生点** |

### すべての実行時失敗が paradox に集まる

| | |
|---|---|
| 0 除算 | paradox |
| 連想配列の欠損キー | paradox |
| 配列の範囲外 | paradox |
| 剥がされたホスト別名 | paradox |
| 0周のループ | paradox |
| `else` の無い `if` で条件が偽 | paradox |

**そして未処理の paradox が唯一のエラーである。** 例外機構も、エラー値も、
エラー型も要らない。`??` が唯一の回復手段であり、`;` が唯一の黙殺手段である。

ホストが**発生点**を受け取るので、伝播経路を辿らずとも原因の位置が分かる。

### 未決：どこが「終結時に残った」なのか

規則2（領域の内部が paradox なら、その領域の値も paradox）により、
**paradox は外側へ伝播する。** したがって「残る」がどこを指すかを決める必要がある。

| 読み | |
|---|---|
| **A. ホストに届いた時点** | paradox は自由に伝播し、`;` にも `??` にも消費されずホストへ届いたらエラー |
| **B. 実在する値を要求する地点** | 束縛の対象、`??` 以外の演算子の被演算子など。`let x := 5/0;` はその場でエラー |

**B でなければ `let x := 5/0;` が通ってしまう**（`;` が潰すので）。しかしそのとき
`x` に何が束縛されるのかが説明できない。**paradox は実在しないので束縛できない。**

したがって B が正しそうだが、**「実在する値を要求する地点」の一覧を仕様に書く必要がある。**

## C-23. 脱出の細部

### フレーム基準

前身では四つがこの境界を共有していた——深さの原点、脱出の上限、跳躍の巻き戻し床、`goto` の走査範囲。
C-1 で後ろ二つが消えたので、**残る二つで定義し直す。**

> **フレームは関数本体である。関数の外側ではプログラム全体がフレームである。**

- `getdepth()` は**フレーム基準からの段数**を返す
- `break` は**フレームを越えられない**

**脱出が関数を越えられないのは規定ではなく必要である。** 越えれば呼び出し元の
文脈に非局所的に飛ぶことになり、それは C-1 で外した跳躍そのものになる。
「関数から抜ける」は `break getdepth()` として書ける——**上限まで抜ける**のであって、越えるのではない。

### 脱出は二つの成分を持つ

> **段数と、脱出後の動作。**

| 成分 | 取りうる値 |
|---|---|
| 段数 | 整数。**実行時の値でよい** |
| 脱出後の動作 | **値を置く**（既定：何も置かない）／**外側のループを継続する** |

前身は五種（値・継続・goto・label・comefrom）だったが、跳躍系が消えて**二種になった。**

これで `break` / `break V` / `continue` / 「N 段抜けてから継続」がすべて書ける。
`continue` は「1段抜けて継続する」であり、独立した機構ではない。

## C-24. 静的検査と前方宣言

### ループ本体の検査

C-3 で「ループ本体は値を置いてはならない」を静的に課すと決めた。**判定規則：**

> **ループ本体の末尾は、`;` で終わるか、脱出であること。**
>
> **（C-43 で短縮：末尾は `;` である。脱出も `;` で終わる）**

`;` で終われば置かれるのはアーカーシャであり、領域を占めない。

それ以外の形は**すべて拒否する。** 実際に値になるかどうかを問わない。

```
loop { 1 }                拒否。値を置く
loop { if c then 1 fi }   拒否。値を置きうる
loop { E ?? D }           拒否。?? は実在する値を産む
loop { E; }               通る
loop { break 5 }          通る。脱出である
```

**保守的である。** `if` が paradox を産む場合や `??` の左が常に実在する場合まで拒否するが、
**周回数によらず一様な規則**の方が素朴である（C-3 の判断）。

### 前方宣言

**抑止するのは名前の存在検査だけ。** 型検査は別プログラム（C-18）なので影響しない。

> **前方宣言した名前が実際には定義されなかった場合、その名前の参照は paradox を産む。**

これで C-22（エラーは消費されなかった paradox ただ一つ）が保たれる。
名前解決の失敗が別種のエラーにならない——**剥がされたホスト別名と同じ形**である。

## C-25. 型注釈の意味は中核仕様が固定する

型集合はホスト方言に開いており（C-3 の議論）、検査は別プログラムである（C-18）。
**注釈の意味を中核が固定しないと、方言ごとに違う言語になる。**

> **ホスト方言が拡張できるのは型の集合であって、注釈の意味ではない。**

中核が固定すること：

1. **注釈は型を名指す。値を生成しない**
2. **注釈は変換を起こさない。** 暗黙変換は禁止（C-21）なので、
   注釈が実際の型と食い違えば、それは検査器が捕らえる誤りである
3. **注釈はリテラルの型を決める。** リテラルは型が決まるまでソースの表現を保持するので、
   **注釈には実行上の役割がある**——検査器が無くても、リテラルがどの型になるかを決める
4. 注釈が偽であるときの扱い（拒否するか、実行するか）は**検査器が決める**。
   標準実装は検査しない

3 が重要である。「注釈は値を生成しない」は正しいが、**「実行に影響しない」わけではない。**
`let x : u8 := 300;` は、注釈があって初めて 300 が `u8` として解釈され、
C-21 の折り返し規則が適用される。

## C-26. `switch` の値と、`;` と `??` の合成

### `switch` はどの腕にも当たらなければ paradox を産む

**これは規定ではなく帰結である。**

どの腕にも当たらなければ、`switch` の領域の内部は**アーカーシャ**である。
規則2（内部がアーカーシャなら領域の値は paradox）により、`switch` の値は **paradox** になる。

したがって `switch … ?? 既定` と書ける。既定の腕を構文として持つ必要が無い。

### `X; ?? c` は常に `c` になる

```
a ?? b; ?? c        →  c
```

導出：

1. `a ?? b` は実在する値を産む
2. `;` がそれをアーカーシャへ潰す
3. `?? c` が領域を閉じる。内部はアーカーシャなので、規則2により値は **paradox**
4. `??` が paradox を c で置き換える

**`;` の左に何があっても同じである。** `;` がアーカーシャにするので、
その後の `??` は必ず発火する。

これは規則が合成した結果であり、`;` と `??` について個別に規定していない。
**C-14（`??` は領域を一度閉じて開き直す）が正しく効いている確認になる。**

## C-27. `??` は強く結合する（C-14 の優先順位を撤回）

**決定**：`??` の優先順位を**高く**する。C-14 で「最低優先順位（`;` の次）」としたのを撤回する。

### 撤回の理由

C-22 の解決——**領域が paradox を持って終結したら、その時点でエラー。
終結を撤回できるのは `??` だけ**——と、最低優先順位は両立しない。

```
a + 5/0 ?? 0
```

最低優先順位なら `(a + 5/0) ?? 0` と読まれる。しかし **`5/0` の領域が先に paradox で終結するので、
`??` が届く前にエラーになる。**

**`??` は、paradox を産んだ領域そのものに掛からなければ意味がない。**

```
a + (5/0 ?? 0)
```

### 却下した案

**paradox を伝播させ、`??` がどの高さでも捕まえられるようにする。**
そうすると「終結時にエラー」が「どこかで捕まらなければエラー」になり、
**paradox がどこまで伝播したかを追う必要が出る。** 今回の規則の単純さが失われる。

### 具体的な位置：乗除の次

> **`??` は乗除算（`*` `/` `mod`）の次に強く結合する。加減算より強い。**

| 強い順 | |
|---|---|
| 前置・後置（呼び出し、添字、`.`） | |
| `*` `/` `mod` | |
| **`??`** | |
| `+` `-` | |
| 比較 | |
| 論理 | |
| `;` | 最低 |

これで paradox を産む構文が**すべて `??` より強く結合する。**

```
5 / 0 ?? d          →  (5 / 0) ?? d
a + b / c ?? d      →  a + ((b / c) ?? d)
arr[i] ?? d         →  添字は後置なので (arr[i]) ?? d
f() ?? d            →  呼び出しは後置なので (f()) ?? d
```

**除去は導入点の直近で起きる。** 括弧を書かずに済む。

### 副次的な利点

**エラーが発生点の近くで処理されることが、構文上強制される。**
C-22 で「ホストは paradox の発生点を受け取る」と決めたのと方向が揃う。

代償として `??` を書く回数が増える。

```
let x := (a ?? 0) + (b ?? 0);
```

### C-14 の誤りの所在（記録）

C-14 は「`??` は境界そのものを操作するので優先順位が意味に直結する。
最低優先順位にすれば『その式の全体』が閉じる領域になり、素朴な読みと一致する」と書いた。

**「素朴な読み」の方が間違っていた。** paradox は式の全体で観測されるのではなく、
**産まれた領域で観測される。** 最低優先順位は、観測できない場所に `??` を置くことになる。

## C-28. 関数は paradox を返せるが、情報を持たない

**決定**：関数の返り値が paradox であることを許す。

代数的型を持たないので、**paradox に情報を付けられない。** したがって

```
f() ?? d
```

は「`f()` の値」か「`d`」か、それだけである。**なぜ paradox だったかは分からない。**

探索関数が「見つからなかった」を伝える等の用途には足りるが、
**失敗の種類を区別することはできない。** 区別が要るなら、値として返す設計にする。

---

## C-29. paradox は型としては直和である。除去の強制は実行時

**決定**：**すべての型は paradox との直和である。** `??` はその除去子である。

```
E  : T | paradox
E ?? D : T
```

### 標準実装は除去を要求しない

**paradox の腕を切らなくてもよい。切らなければ実行時エラーになる**（C-22）。
標準実装（POSIX Vaak）は静的に要求しない。R1（起動が速いこと）から従う。

### 硬い Vaak が静的に解析する

検査器（C-18）は、**paradox の腕が除去されているかを静的に検査できる。**

paradox の腕を導入する構文は**すべて構文的に識別できる**——
0 除算、添字、連想配列の欠損キー、0周のループ、`else` の無い `if`、
定義されなかった前方宣言、剥がされたホスト別名。

したがって検査は**局所的な解析で済む。** フロー解析は要らない。

### これで検査器の仕事が定義された

C-18 で「型検査は別プログラム」と決めたが、**何を検査するかが定義されていなかった。**
直和にしたことで、少なくとも一つは決まる——**paradox の腕の除去。**

### C-14 の「ADT を持たないことによる緩やかな緊張」が解ける

paradox 自身が**組み込みの直和**であり、**除去子が一つだけある**。
ユーザ定義の ADT を持たずに、`Option` 相当の型付けが得られる。

### null にならない線

**paradox の腕が束縛できてしまえば、それは null である。**

現在の規則——**領域が paradox を持って終結したらエラー。撤回できるのは `??` だけ**——が
これを防いでいる。**直和は型の話であり、除去の強制は値の話である。**
二つが揃って初めて null にならない。

## C-30. `:` は識別子に、`->` は領域に付く

**決定**：型注釈の規則は二つだけである。

| | 注釈の対象 |
|---|---|
| **`:`** | **識別子** |
| **`->`** | **領域** |

どちらも対象の**直後**に来る。完全後置修飾が保たれる。

当初これを「束縛位置は `:`、式の途中は `->`」と言っていたが、**位置ではなく対象で分けるのが正確である。**

### 関数の返り値型の位置が導出される

前身は `fn f (…) { … } -> i64;` と本体の後ろに書いていた。当時は「後置だから」としか言えなかった。

> **関数本体は領域である。その領域の値が返り値である。ゆえに `->` は本体の直後に付く。**

`->` が領域に付くから、領域の直後に来る。**規定ではなく帰結である。**

### 帰結

```
let x : i64 := 5;              識別子 x に付く
{ E } -> i64                   領域に付く
fn f (a : i64) { … } -> i64    引数は識別子、返り値は本体の領域
5 -> u8                        リテラルの領域に付く
```

**任意の領域に注釈できる**——被演算子位置、`if` の分岐、ループの領域。
そして C-25 により、注釈はその領域内のリテラルの型を決める。

## C-31. 最上位の外界面は Vaak の意味論ではない

**決定**：プログラム全体の領域は終端するが、**その外界面は Vaak の意味論に属さない。メタ意味論である。**

### 内界面と外界面

用語を確定させる。

| | |
|---|---|
| **内界面** | 領域の内側から値が置かれる面。計算中の値やリテラルが置かれる |
| **外界面** | 領域の値として外から見える面。**これが「実在する値」である** |

規則2はこう言い直せる：

> **内界面がアーカーシャであるか、内界面に置かれた値が paradox であるなら、外界面は paradox である。**

### 最上位では、外界面の向こうに Vaak がいない

プログラム全体の内界面がアーカーシャである場合——`;` で終わるプログラム——
**その解釈はホストに委ねる。**

**POSIX Vaak では `exit 0` の意味とする。** これ以上の解釈は実装に任せる。

**規則2の例外ではない。** 規則2は「外界面が Vaak の中で観測されるとき」を述べており、
最上位では観測者が言語の外にいる。C-2 で巻き戻しについて
「例外ではなく適用範囲の確認」としたのと同じ形である。

### ホストが受け取るのは値かアーカーシャだけである

**最上位の外界面が paradox になることはない。**

paradox は生まれた領域で終結し、そこでエラーになる（C-22）。
`??` が撤回しなければ、**最上位まで到達しない。**

したがってホストが受け取るのは：

| | |
|---|---|
| **値** | 末尾に値を置いた |
| **アーカーシャ** | `;` で終わった |

### エラーは別の経路である

C-22 の「ホストは paradox の発生点を受け取る」は、**プログラムの値ではない。**
エラーの報告である。

> **プログラムの値（外界面）と、エラーの報告（発生点）は別の経路であり、混ざらない。**

### 記録：私の誤り

C-14 で規則3 を書いたとき、前身にあった「消費するのは `;`、`??`、**そしてホスト**」から
ホストを落とした。そのため「ホストを消費者に戻すべきか」という問いを立てたが、**問いが間違っていた。**

**ホストは消費者ではない。言語の外にいる。** 消費者の一覧に加えるのではなく、
**外界面の向こうは意味論の範囲外である**と言うのが正しい。

## C-32. `break` は外界面での操作を決める

**決定**：`break` の被演算子は、**外界面で評価される作用素式**である。

| 渡すもの | 外界面で起きること |
|---|---|
| 値 | それが領域の値になる。それ以上何も起きない |
| 作用素式（`break` など） | **外界面で即時に実行される** |

C-23 で「脱出後の動作は値を置く／継続する の二種」と書いたのは**誤りである。**
閉じた列挙ではない。**外界面で評価される式であり、値はその特別な場合**にすぎない。

### フレームは越えていない

```
fn main () { break break 1; }
main();
```

内側の `break` が main を抜ける。main の外界面——**呼び出し位置**——に `break 1` が置かれ、
**そこで実行される。** 呼び出し側の領域を値 1 で閉じる。

**個々の `break` はフレームを越えていない。** 抜けてから、新しい `break` が呼び出し位置で始まる。
C-23（`break` はフレームを越えられない）は保たれたまま、**合成で効果が得られる。**

### 最上位の `break`

最上位で `break` すれば、その時点で領域を閉じ、**値をホストへ渡す。**
解釈はホストの自由。**POSIX Vaak では終了コードとして扱う。**

### 落とし穴：`;` が終了コードを消す

```
fn main () { return 1; } main();     → exit 0
fn main () { return 1; } main()      → exit 1
```

`;` が値をアーカーシャへ潰すので、**セミコロンの有無で終了コードが変わる。**
導出としては正しいが、C や Rust から来た読み手は踏む。

**隠せない。** 隠せば「`;` は値を消す」が嘘になる。上の `break break 1` の形で書けば、
`;` があっても exit 1 になる——**`break` が呼び出し位置で領域を閉じるので、`;` に到達しない。**

### §1.2 に触れる点

`main()` が呼び出し側を閉じうるのに、**呼び出し位置には何も現れない。**
`main();` と書いた人は、そこで処理が終わるとは読めない。

C-20（破壊は呼び出し側から見えない）と**同じ形**である。**規約で補う。**

## C-33. 複製は深い。部分的な浅さを許容しない

**決定**：集合体の複製は**深い複製**である。例外を作らない。

- 構造体が配列を持てば、複製で中の配列も複製される
- 連想配列が集合体を値に持てば、同じ
- **部分的に浅くすることは許容しない**

**費用は高い。** しかし C-6 の通り、それは**帰結であって隠さない**。
安くしたければ `&=` と書く——費用が字面に現れる。

**部分的な浅さを許さない理由**：許せば「どこまでが複製されたか」が型ごとの規則になり、
読み手が覚える対象が増える。**「複製は深い」の一行で終わる方が素朴である。**

## C-34. 脱出はフレームで止まる。越えるには `outward` と書く

**決定**：`break` の連鎖は**フレームの上限で止まる**。越えようとすればエラーである。
越えたいときは **`outward`** と明示する。

```
fn main () { { break break break 1; } }
main();
```

**これは落ちる。** main の本体（1段）と裸のブロック（1段）で上限は2段であり、
三つ目の `break` がフレームを越えようとしている。

**黙って越えない。黙って止まらない。エラーにする。**

### 理由：字句スコープでは関数の界面が本質的である

前身は動的スコープだったので、関数の境界は名前に対して透過的だった。
**字句スコープにした以上、関数の境界は本物の壁である。** 名前が越えられないなら、制御も越えない。

C-23 で「脱出が関数を越えられないのは規定ではなく必要である」と書いたことが、
合成（C-32）を入れた後も保たれる。

### `outward`

```
fn main () { break outward break 1; }
main();                                  → exit 1
```

`outward` は「**ここでは評価せず、外界面へ持っていく**」ことを示す。
`break` がフレームを抜け、`break 1` が**呼び出し位置で**実行される。

**名前の由来**：外界面へ向かうことが本質なので、方向を名前にした。
TeX の `\expandafter` と機能は近いが、Vaak では**面をまたぐ**ことが本質である。

### 非推奨とする

**トリッキーな操作である。** 推奨する場面は二つだけ。

1. **構造化プログラミングの見た目でやりたいとき**——`fn main` から終了コードを返す形
2. **足元を撃ちたいとき**

それ以外では使わない。`main()` が呼び出し側を閉じうるのに呼び出し位置には何も現れない
（C-32 の §1.2 の論点）ので、**使えば読み手の負担が上がる。**

### エラーは二種になる

C-22 は「実行時エラーは消費されなかった paradox ただ一つ」と決めた。
**フレームを越える脱出は、それに当てはまらない。**

静的に数えられる連鎖（`break break break`）は**読み取り時に検査できる**。
しかし `break N` の N は実行時の値でよい（C-23）ので、
`break getdepth() + 1` のような形は**実行時にしか分からない。**

| | |
|---|---|
| **A. 二つ目のエラーとして認める** | 正直だが、C-22 の一元性が崩れる |
| **B. paradox を産む** | 一元性は保たれるが、制御の誤りを値の不在として表すのは無理がある |
| **C. 静的にのみ許す**（`break N` の N を静的に決まる形に制限する） | 動的段数を捨てることになる。C-23 の中核機構が消える |

**A を採る。** B は paradox の意味を歪める——制御の誤りは値の不在ではない。
C は `$repeat(break, getdepth())` で `return` を導出する仕掛けを失う。

**C-22 の主張は少し弱まる。** 「実行時エラーは一つ」ではなく：

> **値のエラーは一つ**（消費されなかった paradox）。
> **制御のエラーは一つ**（フレームを越える脱出）。
> **それぞれ一つずつ、合わせて二種である。**

静的に数えられる連鎖は読み取り時に検査できる。動的段数のものは実行時に落ちる。

## C-35. `var` / `let` / `const`

**決定**：三つの束縛種を持つ。**二つの軸**である。

| | 何を禁じるか | 軸 |
|---|---|---|
| **`var`** | 何も禁じない | **経路**（この識別子から） |
| **`let`** | この識別子を経由したセルの変更 | **経路** |
| **`const`** | **そのセルの変更（誰からも）** | **セル** |

`var` / `let` は**名前の権限**であり、`const` は**セルの性質**である。
一次元の強弱ではないので、「なぜ三つなのか」に答えられる。

### 権限は別名に伝播する

```
let x := 5;
var y &= x;      ← 許さない
```

`let` から作れるのは `let` 別名だけである。伝播しなければ `let` は何も保証しない。

### `const` は既存の経路まで凍らせる

```
var a := 5;
const b &= a;    ← この時点で a からも書けなくなる
```

これが `let` との差である。**`let` はこれから作る経路しか縛らない。`const` はセルを凍らせる。**

### C-19（別名は型に現れる）と噛み合う

`let` への別名と `var` への別名は**別の型**になる。
**可変性が別名の型に乗るので、規則を足す必要がない。**

### 硬い Vaak では `const` をより強く解釈してよい

標準実装は検査しない（C-18）。検査器（硬い Vaak）は `const` について
**Rust に近い意味論**——たとえば凍結の範囲や期間の静的検証——を採ってよい。

**型の集合と同様、注釈の意味の中核は仕様が固定するが（C-25）、
検査の厳しさは実装に委ねる。**

## C-36. 前方宣言を持たない。関数宣言はスコープ全体で見える

**決定**：前方宣言（プロトタイプ宣言）を持たない。

> **関数宣言は、それを囲むスコープ全体で見える。**
> **変数宣言は、宣言の位置から先で見える。**

```
fn is_odd (n : i64) {
    if n == 0 then 0 else is_even(n - 1) fi
} -> u1;

fn is_even (n : i64) {
    if n == 0 then 1 else is_odd(n - 1) fi
} -> u1;
```

**前方宣言なしで相互再帰が書ける。**

### 理由：PHECL 原則8

> 8. **実行器の都合で、人間が使える構文を制約しないこと** — anti-off-side rule

前方宣言は**実行器が上から読むという都合**である。人間の都合ではない。
「後で定義するものを、先に書いておく」ことに、書き手にとっての意味は無い。

### 実行順序は変わらない

**関数宣言は何も実行しない。** 本体は呼ばれたときに走る。
したがってスコープ全体で見えるようにしても、実行順序に影響が無い。§1.2 に触れない。

変数は初期化順があるので宣言位置から見える。
**「初期化順を持つものだけが順序に縛られる」**で分かれる。

```
fn f () { x } -> i64;    エラー。x はまだ見えない
var x := 1;
```

### C-1 の帰結でもある

C-1 で「すべてのコードが構文解析できる」と決めた時点で、**先読みが可能になっていた。**
前方宣言は、カーソル機械時代（実行しない区間は解析しない）の制約の名残りである。

### C-13 の「抑止する手段」が不要になる

C-13 は「名前検査を持ち、それを抑止する手段を持つ」と決めた。**後半が要らなくなる。**

属性機構を落とした（C-16）とき、残る唯一の用途が名前検査の抑止だった。
**それも消えたので、抑止機構は言語から完全に無くなる。**

名前検査は残る。**抑止できないだけである。**

## C-37. 別名の型注釈は省略できる。`const` の凍結はスコープで解ける

**決定**（C-35・C-19 の細部）：

### 別名の型注釈は省略できる

```
var y &= x;                  よい
var y : i64 alias &= x;      よい。ただし alias が無ければエラー
```

`&=` が既に別名であることを言っているので、型の `alias` は冗長である。
**冗長な記述を強制しても読み手が得るものが無い。**

### `const` の凍結はスコープで解ける

```
var a := 5;
{
    const b &= a;    a が凍る
    a := 7;          エラー
}
a := 7;              よい。b のスコープが終わったので解けた
```

**字句スコープにした利点がここで出る。** 凍結の範囲が構文から決まる。

追跡が要る点は認める——読み手は `const` 別名がどのスコープにあるかを見る必要がある。
しかし**永久に凍る方は使いにくく**、動的に追う方は字句スコープを持つ意味を失う。

## C-38. `nfor` の第三被演算子は回数である

**決定**：`nfor (i, start, count)`。`i` は `start` から始まり、`count` 回まわる。

```
nfor (i, 0, n)             i は 0 から、n 回
nfor (i, 0, a.len())       配列をちょうど一周する
```

### 却下した案

| | `nfor (i, 0, n)` | 配列を回るとき |
|---|---|---|
| **終点を含む** | n+1 回 | `nfor (i, 0, a.len() - 1)` |
| **終点を含まない** | n 回 | `nfor (i, 0, a.len())` |

**終点を含む**方は名前に忠実だが（PHECL 原則3）、`- 1` が書き間違いの源になる。
そして `a.len() - 1` は長さ 0 のとき `0, -1` になり、**負の数を経由する。** 素朴ではない。

**終点を含まない**方は実用的だが、`finish` と書いて含まないなら**名前が嘘になる。**

**回数にすれば、両方が同時に解ける。** 名前が嘘にならず、`a.len()` がそのまま書け、
境界の off-by-one が構造的に消える。

代償は `nfor (i, 5, 3)` が「5 から 3 回」となることで、
**終点を書きたい人には読み替えが要る。** それは受け入れる。

## C-39. `switch` は閉じる語を持たない。腕は一つの値である

**決定**：`switch` を残す。構文は次の形。

```
switch (e) case P1 => V1 case P2 => V2
```

- 対象は直後の一つの領域
- **腕の右辺は一つの値である**
- **閉じる語を持たない。** `case` 以外が来た時点で switch が終わる
- `=>` は `??` より強く結合する

### 閉じる語が要らない理由

**腕が一つの値だから**である。腕が `;` を含められるなら、
switch がどこで終わるかを決めるものが無くなる。

```
switch (v) case 1 => a(); b()
```

`b()` が腕1の続きか switch の後かを**決められない。**
腕を一つの値に限れば、この曖昧さが構造的に消える。

`if … fi` が閉じる語を要するのは、分岐が式を丸ごと取るからである。
**switch は腕が一つの値なので要らない。** 違いは必然であって不統一ではない。

### `=>` が `??` より強い理由

```
switch (v) case 1 => 2 case 2 => 3 ?? 0
```

`?? 0` は **switch のもの**でなければならない。C-26 で
「既定の腕は要らない、`??` が受ける」と決めたので、それが主用途である。

腕の中で `??` を使うなら括弧を書く——`case 2 => (read() ?? d)`。

### 副作用だけの腕

```
switch (val) case 1 => (a();) case 2 => (b();) ;
```

`(a();)` は内界面がアーカーシャなので、外界面は **paradox**（C-14 規則2）。
末尾の `;` がそれを潰す。

**腕をアーカーシャにしたいなら、`( )` か `{ }` で paradox へ輪廻させる。**
腕の位置に裸の `;` は書けない。

### 却下：`switch` を落とす案（記録）

一度、次のように提案して却下された。

> 腕が値なら連想配列の引き（`table[e] ?? 0`）で書ける。
> 腕が計算なら `if` / `elif` で書ける。したがって `switch` は要らない。

**連想配列はリテラルを組み立てる時点で全部の腕を評価する。** 選んでから評価する
switch とは違う。そして `if (n == 0) … elif (n == 1) …` は `n ==` を繰り返す。

C-4 の判断（腕は選ばれてから評価されるので中核）は**正しかった。**
落とせないのは、腕の評価時点が違うからである。

**ただし、値の表を書くなら連想配列の方が素朴である**——有限写像は関数であり、
`( 1 => 2, 2 => 3 )` は無名の有限関数である。`=>` はその記法と共有される。

## C-40. 宣言は paradox を産む。`;` はその消費である

**決定**：宣言は値を置かない。したがって宣言の領域は内界面がアーカーシャであり、
**外界面は paradox** になる（C-14 規則2）。

```
var x := 5 var y := 6        二つの paradox が同じ領域に置かれる。規則違反
var x := 5; var y := 6;      ; が潰す
```

> **`;` が宣言の後に要るのは、宣言が paradox を産むからである。**
> 「文の終わりに書く記号」ではない。

### 帰結：改行に意味を持たせる必要が無い

```
fn f () { … } -> i64 array;
```

**`;` が来るまでが型である。**

前身は属性（D-18r）と返り値型（D-21r）を**改行で終端**しており、
字句解析器に**物理行と論理行の二重管理**を強いていた（`%` コメントが論理行を進めない、D-66）。
tree-sitter にも外部スキャナを要求していた。

**それが丸ごと消える。** 宣言が paradox を産むという意味論から、終端が出る。

### 引数の束縛種の既定は `let`

```
fn f (a : i64)          a は let
fn f (var a : i64)      a は var
```

C-35 は宣言について `var` / `let` / `const` を明示させるが、
**引数は「呼び出し側から値が来る」ことが確定している**ので、既定を置いても読み手が迷わない。
そして書き換える引数の方が少数なので、**少数の側に印を付ける。**

`fn f (let a : i64, let b : i64)` は冗長である。

## C-41. 構造体の宣言語は `struct`。返り値型は省略できる

**決定**：

### `struct`

```
struct Point {
    var x : i64 := 0;
    var y : i64 := 0;
};
```

**`typ` でも `type` でもない。**

Vaak でユーザが定義できる型は**構造体だけ**である。`type` と名乗れば
名前が実際より多くを約束する（PHECL 原則3：名称を計算上の意味から乖離させない）。

そして **`type` を空けておく。** 後から型別名を入れるなら、そこが自然な場所である
（`str` が `u8 array` の別名であることを、利用者にも書かせる余地）。

前身の `typ` は `type` の略語であり、`fn` / `var` / `let` / `const` / `flow` と並べたとき
**そこだけ略語だった**。`fn` も略語だが知名度が違う。

### 返り値型は省略できる

```
fn f (…) { … };              返り値の型注釈が無い
```

`->` が無ければ注釈が無いというだけである。**注釈は義務ではない**（C-30）。

値を置かない関数は、本体の内界面がアーカーシャなので**外界面は paradox** になる。
呼び出し側は `f();` と潰す——**宣言と同じ形である**（C-40）。

`-> ;` のような「空の型」を書かせない。

## C-42. コメントは `%` と `%{ }%`

**決定**：

```
% 行コメント。改行まで

%{
   ブロックコメント。入れ子にできる。
   %{ 内側 }%
   字句解析より前に消えるので、中身は何でもよい。
}%
```

- **どちらも字句解析より前に消える**（C-1）
- ブロックコメントは**入れ子にできる**

### `%` を維持する理由

TeX 由来であり前身から続く。そして `#` や `//` と違い**演算子と衝突しない**——
剰余は `mod` なので `%` が空いている。

`%{ }%` は `%` の家族に見える。`/* */` を採ると `%` と `/*` という**無関係な二つの記法**が並ぶ。

### 前身の実害が構造的に消える

前身のブロックコメントは `#[flat] goto` からの導出だったので**字句解析の後**に読み飛ばされ、
**日本語の句点 `。` で落ちた**（非直感性 #6）。入れ子にもできなかった。

字句層に置けば、**中身は何でもよい。** 壊れたコードも隠せるので、
§4.3 の「隠しコードの安全性」の用途も代替される（C-1）。

## C-43. 脱出は領域を閉じてから発生する

**決定**：

1. **`break` は式の亜種である。その値は paradox**
2. **領域が閉じる。** `;` があれば paradox がアーカーシャへ潰れる
3. **その後で脱出が起きる**

```
loop { break 5; }
if (a[i] == x) $return i; fi;
```

### 「制御が消える」と読んではならない

脱出を「無条件の脱出——制御がそこで消える」と読むと、**通過した領域の中身を
決めないまま捨てることになる。**

> **ここに何があったのかを決める前に、捨象することはできない。**

`break` の値が paradox であり、`;` がそれを消費する。**通常の式と同じ扱いである。**
脱出はその後に起きる。

### 実装の費用

**少しの先読みをするだけ。** 脱出を実行する前に `;` を見る。安い。

### 帰結：C-24 の静的規則が一節短くなる

C-24 はこう書いていた。

> ループ本体の末尾は、**`;` で終わるか、脱出であること**。

脱出も `;` で終わるので：

> **ループ本体の末尾は `;` である。**

**「脱出は例外」を覚える必要が無くなる。** そして「`;` で終わる」という見た目が、
脱出の場合にも崩れない。

```
loop { break 5; }
loop { i += 1; }
```

`;` は脱出の後には到達しないが、**領域を閉じるために書かれている。**
死んだ記号ではない。

## C-44. ループ本体の内界面には何も置かれていない

**決定**：ループ本体の規則は、これだけである。

> **ループが受け取るブロックの中身は、何も残ってはいけない。**

「内界面」ではない。**中身**の話である。

```
loop { }              通る。空でよい
loop { E; }           通る
loop { E }            拒否
loop { break 5; }     通る（C-43：`break` の値は paradox、`;` が潰す）
```

### 構文の話ではなく、中身の状態の話である

C-24 は「末尾は `;` か脱出」、C-43 で「末尾は `;`」と短縮した。**まだ構文を言っていた。**

中身の状態を言えば、**空のブロックが自然に受かる。**
「末尾は `;`」では `loop { }` を説明できなかった——末尾が無いので。

### 「何も残っていない」に名前を振るが、付録に送る

**この言語における「何も残っていない」の意味は特異である**——値が無いのではなく、
値が置かれる場所そのものを占めていない。通常の言語の `void` や `null` とは別のものである。

**そのため、我々はこれに名前を振っている**（アーカーシャ）。
ただし**通例の理解には必須ではない**ので、**付録に送る。**
規範の規則はこの語を使わずに書ける。

前身も同じ規律だった（akasha は付録Aのみ、規範の規則には出さない）。

規則はこう書き直される。

1. 領域は終結した時点で値を持つ
2. **内界面に何も置かれていない**か、内界面に置かれた値が paradox であるなら、
   **外界面は paradox** である
3. paradox は `;` で潰す（**内界面を空にする**）か、`??` で消す（**値に置き換える**）
   かしなければならない

## C-45. `??` の優先順位は非対称である

**決定**：`??` は**左を強く、右を緩く**取る。

| | 強さ |
|---|---|
| **左辺** | 乗除の次（C-27 のまま） |
| **右辺** | 加減より下 |

```
a + b / c ?? d + e     →  a + ((b / c) ?? (d + e))
table[name] ?? 0 - 1   →  table[name] ?? (0 - 1)
```

### 撤回の理由

C-27 で `??` を強くしたのは、**paradox を産んだ領域そのものに掛けるため**だった。
しかし必要だったのは**左だけ**である。右にも同じ強さで掛かった結果、
**代わりに置く値に緩い式を書けなくなっていた。**

```
table[name] ?? 0 - 1        →  (table[name] ?? 0) - 1
```

欠損なら −1、存在すれば「値 − 1」。**意図と違う。**（検証1 の問題1）

### 非対称は正当である

**`??` の左右は役割が違う。**

| | |
|---|---|
| 左 | **捕まえる対象**。paradox を産んだ領域に届かねばならない |
| 右 | **代わりに置く値**。素朴に読んだ通りの式であればよい |

**同じ強さで括る理由が無い。** 非対称な優先順位は普通の道具ではないが、
役割が違う以上、同じ扱いにする方が恣意的である。

## C-46. エラーは三種である。領域の終結は二段階である

### 領域の終結は二段階である

`??` が「終結を撤回できる」（C-14）とは、**終結が二段階あるということである。**

| | |
|---|---|
| **第一段** | `??` の**前**に起きる終結 |
| **第二段** | `??` の**後**に起きる終結 |

`??` が介入できるのは、その間だけである。

```
( break ) ?? 42
```

**無効である。** `( )` が領域を**完全に終結させる**ので、`??` が届かない。

```
{ break ?? 42 }
```

こちらは同じ領域にあるが、**`break` が二段閉じるので、`??` の割り込みより先に
paradox のエラーが生じる。**

> **`??` が脱出を捕まえることはない。**

（検討の途中で「`??` が `break` の paradox を捕まえて制御転送が消えるのではないか」
という懸念を立てたが、**終結の二段階を勘定に入れれば起きない。** 認識の齟齬だった。
C-43 の「`break` 自身の値は paradox」は正しく、訂正の必要は無い。）

### エラーは三種である

C-22 は「実行時エラーは二種」としたが、**静的なものが抜けていた。**

| | 種類 | |
|---|---|---|
| **1** | **静的** | **領域に値が複数ある** |
| 2 | 実行時（値） | 消費されなかった paradox。ホストは発生点を受け取る |
| 3 | 実行時（制御） | フレームを越える脱出 |

**1 は書かれたものを見れば分かる**（§1.5 の読み取り時検査）。走らせる必要が無い。

```
{ a b }                  値が二つ
if (c) 1 fi 2            if の値と 2 で二つ
nfor (…) { … } x         nfor の反復回数と x で二つ
```

### C-44 は 1 の先取りである

> ループが受け取るブロックの中身は、何も残ってはいけない。

残っていれば、N 周で **N 個の値が同じ領域に置かれる**。
つまり **C-44 は「領域に値が複数ある」を、周回数を待たずに静的に捕らえる規則**である。

**独立した規則ではなく、1 の適用である。**

## C-47. 細部の確定

### 作用素式は右結合である

```
break break break     ≡  break (break (break))
```

C-32（`break` の被演算子は**外界面で評価される**作用素式）から出る。
内側の `break` が外界面に置くものが、次の `break` である。

### 関数は外側の局所変数を見ない

関数の本体から見えるのは、**引数と、最上位（およびそれを囲むスコープ）の宣言だけ**である。

```
let x := 1;
fn f () { x } -> i64;      x が f を囲む局所なら、エラー
```

**見えればクロージャになる。** 第一級関数を持たない以上、
関数が環境を捕捉する経路を作ってはならない。

### `switch` の腕は上から順に照合する

```
switch (e) case P1 => V1 case P2 => V2
```

`P1` から順に評価して比較する。**当たった腕の値だけを評価する。**
当たらなかった腕の値は評価しない（C-4：腕は選ばれてから評価される）。

### `str` は NUL 終端を持たない

`u8 array` そのものである（C-7）。長さは配列の長さである。

## C-48. 別名は値ではない。束縛の形態である

**決定**：**別名は値として保持できない。** `alias` は型修飾子ではなく、**束縛の形態**である。

C-19 は「別名であることは型に現れる」としたが、**正確には型ではない。**

### 記法は変わらない。位置が制限される

```
fn f (a : i64 array alias)     よい。alias は最も外側
let b : i64 array alias &= a;  よい

var s : i64 alias array;       エラー。alias が型の内側にある
struct S { var p : i64 alias; }  エラー。欄は値の場所である
```

> **`alias` は型注釈の最も外側にのみ書ける。そこで束縛の形態を示す。**

### 効くところ

**深い複製が純粋な値だけに定義できる**（C-33）。
別名が値の中に入り得るなら、「配列の中の別名を複製する」とは何かを決めねばならなかった。
**入り得ないので、問う必要が無い。**

型の組み合わせも減る——`i64 alias array`、`i64 alias alias` のような型が消える。

### C-19 の書き換え

C-19 の三規則のうち、**第一規則を書き直す。**

| | |
|---|---|
| 旧 | 別名であることは**型に現れる** |
| **新** | 別名であることは**束縛の形態である**。型注釈の最も外側に書く |

第二・第三規則（同じか外側のスコープしか指せない／関数は別名を返せない）は変わらない。
そして**第三規則の理由が強くなる**——別名は値ではないので、返り値になりようがない。

## C-49. 型は逆ポーランド記法である

**決定**：型の修飾子は**引数の数が決まった後置演算子**であり、型全体は**逆ポーランド記法**で書かれる。

| 修飾子 | 取る型の数 |
|---|---|
| `array` | 1 |
| `map` | 2（**鍵、値の順**） |

```
i64 array            i64 を積む → array が 1 つ取る
str i64 map          str と i64 を積む → map が 2 つ取る
str i64 array map    str と (i64 array) を積む → map が 2 つ取る
```

**読み方は、左から順に積んで、修飾子が取る。** 最後に**ちょうど一つの型が残らねばならない。**

### C-46 と同じ形をしている

「最後にちょうど一つ残る」は、**領域の規則と同じ形**である。
一つ余れば型が二つ、足りなければ修飾子の引数が不足する。どちらもエラーである。

### 前の記述の誤り

```
type := basetype ('array'|'alias'|'map')*
```

と書いていたが、**これは `map` が 2 つ取ることを表現していない。**
`i64 array map` が何なのか決まらなかった。**私の写し誤りである。**

`alias` は C-48 により修飾子ではなくなったので、この列から外れる。

```
type      := valuetype ['alias']
valuetype := 逆ポーランドで書かれた基底型と修飾子の列
```

## C-50. 脱出の文法。段数は反復でのみ表す

**決定**：脱出は次の文法を持つ。

```
escapeexpr := escapehead escapeexpr          右結合
            | escapehead [expr]
escapehead := 'break' ['outward']
            | 'continue'
            | '$' IDENT '(' args ')'
            | FLOWNAME
```

- **最も緩い優先順位**（`;` の次）。したがって `break 1 + 2` は `break (1 + 2)`
- 被演算子は省略できる。`;` `)` `}` `fi` `case` などが来れば無いものとする

### 段数は反復でのみ表す。被演算子は段数ではない

**これは私の誤りの訂正である。** 15-文法.md にこう書いていた。

```
break     := 'break' [expr]
break N                  N 段抜ける。N は実行時の値でよい
```

**二つの規則が衝突していた。** 同じ `break 5` が「5 を置く」とも「5 段抜ける」とも読める。

**正しくは、段数は反復でのみ表す。**

| | |
|---|---|
| `break 5` | **1 段抜けて、5 を外界面に置く** |
| `break break break` | **3 段抜ける** |
| `$repeat(break, n)` | **n 段抜ける。n は実行時の値でよい** |

**被演算子は常に「外界面で何をするか」である**（C-32）。段数ではない。

したがって `break 0` は「0 を置いて 1 段抜ける」であり、`break -1` は「−1 を置く」である。
**特別な意味は無い。** 段数として読む余地が無いので、問いが立たない。

### `continue`

**被演算子を取らない。** 継続は値を運ばない。

```
continue                 1 段抜けて、外側のループを次の周回へ
break continue           2 段抜けて、そこのループを次の周回へ
```

`escapehead` の一つなので、合成できる。

### `outward`

```
break outward break 1
```

`break` の直後に置き、**その脱出がフレームを越える**ことを示す（C-34、非推奨）。

`outward` を書かずにフレームを越えようとすれば、**制御のエラー**である（C-46 の 3）。

### `flow` で名付けたものは escapehead になる

```
flow $return = $repeat(break, getdepth());

$return i;        ≡  $repeat(break, getdepth()) i;
```

`flow` は**前置作用素に名前を与える**。名前は `escapehead` の位置に現れ、
**続くものがその被演算子になる。**

### `break` は式である

値は paradox（C-43）。したがって式の位置に置けるが、**優先順位が最も緩い**ので、
実際には行の先頭にしか現れない。`;` を書いて潰す。

## C-51. 細部の確定（四件）

### (1) 別名の権限：経路の権限は増やせない。凍結は常に許される

**二つの軸で決まる**（C-35）。

| | 経路の権限 | セルへの効果 |
|---|---|---|
| `var` | 書ける | 無し |
| `let` | 書けない | 無し |
| `const` | 書けない | **凍らせる** |

> **経路の権限は、別名を作るときに増やせない。**
> **凍結は常に許される——能力を奪うだけで、与えないから。**

```
var a := 5;    var b &= a;     よい
var a := 5;    let b &= a;     よい（権限を減らす）
var a := 5;    const b &= a;   よい（凍らせる。a からも書けなくなる）

let a := 5;    var b &= a;     エラー。権限が増える
let a := 5;    let b &= a;     よい
let a := 5;    const b &= a;   よい

const a := 5;  var b &= a;     エラー。権限が増える
const a := 5;  let b &= a;     よい
```

`let` の経路から凍結できるのは奇異に見えるが、**凍結は誰の能力も増やさない。**
そして範囲は字句スコープに限られる（C-37）。

### (2) インタプリタは型を解決する。検査はしない

**「型検査をしない」と「注釈がリテラルの型を決める」は衝突しない。**

| | |
|---|---|
| **解決** | 注釈を読んで、リテラルがどの型になるかを決める。**する** |
| **検査** | 型が整合しているかを確かめる。**しない** |

```
let x : u8 := 300;      解決する。300 を u8 として読み、C-21 により折り返して 44
```

> **標準実装は、検査を通したプログラムを受け取ることを前提とする。**
> **通していないプログラムの挙動は規定しない。**

これは C-46 の「エラーは三種」を守るために要る契約である。
四種目（実行時の型エラー）を持たないなら、**入力が検査済みであることを前提にするしかない。**

ホストが検査器を通さずに投げることは妨げないが、**そのときの挙動は仕様の外**である。

### (3) 別名は内へは渡せるが、外へは返せない

C-19 の二つの規則——「同じか外側のスコープしか指せない」「関数は別名を返せない」——は、
**一つのことを言っている。**

> **別名は内へは渡せるが、外へは返せない。**

| | 別名の指す先 | |
|---|---|---|
| 関数に**渡す** | 呼び出し側のスコープ＝**外側** | よい |
| 関数から**返す** | 関数のスコープ＝**内側** | エラー |

**メンバ関数のレシーバが別名であることも、これで説明が付く**——
レシーバは**渡されたもの**である。「関数は別名を受け取れるのに返せない」という非対称は、
**方向の規則そのもの**であって、例外ではない。

### (4) 静的検査は到達可能性を問わない

**プログラムの全文を検査する。** 実行されない箇所も含む。

```
switch (v)
    case 1 => 2
    case 2 => { a b }      当たらなくても静的エラー
```

C-1（すべてのコードが構文解析できる）と §1.5（走らせずに数えられる）から出る。
**到達可能性の解析は要らない**——検査が到達可能性に依らないので。

## C-52. 構築は `型 ( 引数 )` である

**決定**：**型に括弧を付ければ、その型の値ができる。**

```
Point ( x := 1, y := 2 )       構造体。欄は名前で与える
i64 array ( 10, 0 )            長さ 10、初期値 0 の配列
str i64 map ( )                空の写像
```

### プリミティブでなければ循環する

`Point.new(1, 2)` を標準ライブラリで書こうとすると、**欄を持つ値を作る手段が要る。**
それが構築そのものである。**循環する。**

### 「既定値から作って後から書き込む」案は破綻する

```
struct Config { let name : str; … };
```

`let` の欄には**後から書けない**（C-35）。初期化の機会は構築の瞬間しか無い。

### 欄は名前で与える

位置で与えると**欄の順序という隠れた知識**が要る（PHECL 原則3）。

そして **`:=` の意味がそのまま効く**——「セルに値を書く」（C-20）。
構築とは、新しいセルを作って初期値を書くことである。**新しい記号が要らない。**

既定値のある欄は省略できる。既定値の無い欄は**ちょうど一度**現れねばならない。
知らない欄、重複——**すべて静的に検査できる。**

### 帰結：標準ライブラリから構築が消える

`Point.new` も `Array.new` も要らない。**構築が言語にあるので、その上に何も要らない。**

### 配列の初期値は明示する

`i64 array (10)` のような形は採らない。**隠れた既定値を持たない。**
`str array (10)` の既定が何かという問いも立たない。

## C-53. 配列は動的である。別名は名前だけを指す

**決定**：

> **`&=` の対象は名前である。値の部分（`a[i]`、`p.x`）ではない。**

```
var b &= a;         よい。名前 a を指す
var e &= a[0];      エラー。要素は名前ではない
var f &= p.x;       エラー。欄は名前ではない
```

**その上で、配列は動的である。** `.push(x)` などで伸びる。

### 動的配列と別名は衝突していた

配列が伸びると記憶域が移動する。要素への別名があれば**宙に浮く。**

巻き戻しも GC も無く、所有は字句的である（C-19）。
**実行時の無効化機構を持ちたくない。**

**別名が名前だけを指すなら、衝突が消える**——別名は配列そのものを指すので、
中身が動いても指し先は変わらない。

### C-48 が強くなる

C-48 は「別名は値ではなく束縛の形態である」とした。
**別名は名前を名前に結ぶ。値の中を指さない。** 一行の規則になる。

### 固定長と動的を分けない

別名が要素を指さないので、**動的であることの危険が消えた。**
二つの型を持つ理由が無い。

### 失うもの

「要素への参照を関数に渡す」が書けない。**配列と添字を渡す。**

C 風だが素朴であり、`&=` の主用途——ホストの記憶域を掴む、大きい値の複製を避ける——は
**どちらも名前単位**なので実害は小さい。

---

## C-54. 配列リテラルを持つ

```
[ 1, 2, 3 ]
```

`a[i]` は後置、リテラルは前置なので衝突しない。

`i64 array (3, 0)` してから代入する形でも書けるが、**書き並べたいものは書き並べられる方が素朴**である。

## C-55. `outward` は被演算子を要求する

**決定**：`break outward` を被演算子なしで書けない。

```
break outward break 1;    よい
break outward;            エラー。越えた先で何をするか書かれていない
```

**理由**：被演算子なしを許すと、「呼び出し位置の領域を 1 段抜ける」という
強力な操作が**印一つで書けてしまう。**

```
fn f () { break outward; }
loop { f(); };            ← f() がループを抜ける
```

C-34 が `outward` を非推奨としたのは「呼び出し位置に何も現れない」からである。
**せめて書き手の側では、越えた先で何をするかを明示させる。**

---

## C-56. `continue` の抜けた先はループでなければならない

**決定**：`continue` が抜けた先がループの本体でなければ、**制御のエラー**（C-46 の 3）。

```
loop { { continue; }; };      エラー。抜けた先は裸のブロックであってループではない
loop { break continue; };     よい。2 段抜けて、そこ（ループ）を次の周回へ
```

### 「ループまで探す」を採らない理由

`continue` が脱出段を無視してループを探す設計もありうるが、
**`continue` だけが段数を無視することになり、`break` との対称性が壊れる。**

そして書き手は `break continue;` と書けばよい。**段数を数える規律が一様に保たれる。**

---

## C-57. 規約：`if` の分岐に `{ }` を書かない

**規約**（処理系は検査しない）。

```
loop {
    if (c) { break; } fi;     ← break は { } を抜けるだけ。ループを抜けない
    step();                   ← 実行される
};

loop {
    if (c) break; fi;         ← 意図どおり
};
```

`{ }` は脱出段を作る（C-20 まで）。`if` の分岐そのものは作らない（C-10）。
したがって**分岐の中にブロックを書くと、段数が一つ増える。**

**C 系の言語では `if (c) { break; }` の波括弧は無害な飾り**であり、
付けても外しても同じである。**Vaak では段数が変わる。**

意味論は一貫している。直すには `{ }` に二つ目の意味を与えるしかなく、
それは C-20 までの決定を覆す。**受け入れて規約で補う。**

> **`if` の分岐に `{ }` を書かない。書くなら段数を数える。**

## C-58. 文法の穴を塞ぐ（八件）

外部の吟味で見つかったもの。**一件は安全性の穴である。**

### (1) 🔴 `alias` 引数が受け取れるのは名前だけ

```
fn f (x : Point alias, arr : Point array alias) { arr.push(…); … };

f(arr[0], arr);        ← 禁じる
```

C-53 で `&= a[i]` を禁じたが、**引数として要素を `alias` 引数に渡す経路を塞いでいなかった。**
渡した先で `arr.push()` すれば、**再確保で `x` が宙に浮く。**

> **`alias` を受ける引数に渡せるのは名前だけである。** `&=` と同じ規則（C-53）を、
> **引数の位置にも適用する。**

### (2) 構築は `new` を伴う

```
new Point ( x := 1, y := 2 )
new i64 array ( 10, 0 )
new str i64 map ( )
```

C-52 は `型 ( 引数 )` としたが、**`Point ( … )` と `f ( … )` を区別するのに
`Point` が型であることを知る必要があった。文脈自由でない。**

`new` を置けば、**続くものが型だと構文だけで決まる。**

`new` は C++ / Java の語だが、**この言語では領域確保を含意しない**——所有は字句的である（C-19）。
「新しく一つ作る」という意味だけを取る。

### (3) 宣言から `;` を外す

```
decl      := ('var'|'let'|'const') binding (',' binding)*
fndecl    := 'fn' fnname '(' [params] ')' block ['->' type]
structdecl:= 'struct' IDENT '{' expr* '}'
fielddecl := ('var'|'let'|'const') IDENT ':' type [':=' expr]
```

**宣言は式である。** paradox を産み（C-40）、`;` が潰す。

**文法が意味論を裏切っていた**——`decl := … ';'` と書けば、`;` は終端子であって演算子ではなくなる。
C-40 の導出（`;` が要るのは宣言が paradox を産むから）が、文法の上で消えていた。

型注釈の終端も変わらない。**型は修飾子でない語が来れば終わる**ので、`;` が来れば終わる。

### (4) `expr` を定義する

```
expr := literal | IDENT | paren | block
      | construct | arraylit | maplit
      | decl | fndecl | flowdecl | structdecl
      | if | loop | while | nfor | switch
      | escapeexpr
      | prefix expr | expr infix expr | expr postfix
```

**すべてが式である**（C-40 まで）。文法にもそう書く。

### (5) 脱出は `;` より強い

```
break 5;        ≡  (break 5);
```

「最も緩い優先順位」とだけ書くと `break (5;)` と読める。
**正しくは `;` の次に緩い。**

### (6) `switch` の `??` を文法に書く

```
switch := 'switch' paren ('case' expr '=>' expr)* ['??' expr]
```

「末尾の `??` は switch に付く」は散文でしか書いていなかった。
**優先順位表からは導けない**（`=>` は 14、`??` は 4）。生成規則に入れる。

### (7) `alias` の束縛は `&=` に限る

```
var y : i64 alias &= x;      よい
var y : i64 alias := x;      エラー
```

`alias` は束縛の形態である（C-48）。**`:=` は値を複製するので、別名の束縛にならない。**

### (8) 被演算子は脱出の前に評価されない

```
break break break        3 段抜ける
```

C-32 は「被演算子は**外界面で評価される**」と書いたが、
**順序を明記していなかった。**

> **脱出が先に起きる。被演算子は、抜けた先で評価される。**

したがって `break (break (break))` の内側が先に走ることはない。
左端の `break` が 1 段抜け、外界面で残りが実行される。

### 付記：`if` の分岐で複数の式を書く

```
if (c) ( a; b ) fi;
```

`( )` は領域だが、スコープでも脱出段でもない（C-20）。
**`{ }` を書くと段が増える**（C-57）が、`( )` なら増えない。

規約 C-57 と対になる。動作例に加える。

## C-59. 実行と評価を区別する

### 実行と評価

| | |
|---|---|
| **評価** | 式が自分の領域で値になること |
| **実行** | 外界面に置かれた作用が起きること |

```
break break 2;
```

**外側の `break` が評価され**（脱出が起きる）、**内側の `break 2` が外界面で実行される。**

これで C-32 の「被演算子は外界面で評価される」の中身が定まる。

| 被演算子 | |
|---|---|
| **値** | **ここで評価されて置かれる。** `break y` の `y` はスコープを出る前に読まれる |
| **作用素式** | **外界面で実行される** |

「値はその特別な場合」（C-32）とは、**評価される側に落ちること**を言っていた。

### 却下：`( )` が領域を完全に閉じる案

一度、次のように定めた。

> `( )` は脱出段を作らないが、**領域を完全に閉じる**（二段階の隙間が無い）。
> `{ }` は普通に閉じる。したがって `( break ) ?? 42` は無効であり、
> `( 1 / 0 ) ?? 42` もエラーになる。

**撤回する。** 三つの理由で。

**1. 規則が一つ多い。** `( break ) ?? 42` が無効な理由は、括弧ではなく
**`??` が何であるか**から出る。

> **`??` は値に作用する演算子である。脱出は値ではない。**

これは C-46 に既に書いてあり、**括弧から導く必要が無かった。**

**2. 避けられる代償だった。** A では `( a / b ) ?? 0` が書けなくなる。
C-57（`if` の分岐に `{ }` を書くと段が増える）は `{ }` が三つの単位を作ると決めた以上
**避けられない**が、`( )` の方は**避けられる。** 避けられる代償は負わない。

**3. 塞ごうとした穴が、最初から開いていなかった。**

`break 5` は脱出を起こし、5 を運ぶ。`break` 式そのものの値（paradox）は、
囲む領域の帳尻合わせでしかない。`??` がそれを置き換えたとしても、
**脱出は既に起きていて、置き換えた値の行き先が無い。** 害が無い。

つまり **C-43（領域を閉じてから脱出）と `??` は、そもそも衝突していなかった。**
「`??` が脱出を消すのではないか」という懸念が空振りで、
二段階終結と `( )` の特別扱いで塞いだ穴は、**最初から開いていなかった。**

### したがって

```
1 / 0 ?? 42          → 42
{ 1 / 0 } ?? 42      → 42
( 1 / 0 ) ?? 42      → 42     ( ) は領域を作るだけ。?? は届く
( break ) ?? 42      → 無効。?? は値の演算子であり、脱出は値ではない
```

**`( )` は領域だけを作る。** スコープも脱出段も作らない、それだけである。
終結が二段階であること（C-46）は残るが、**`( )` と `{ }` を区別しない。**

## C-60. 作用素式の名前は `$` で始まる。文法が文脈自由になる

**決定**：`flow` で名付けるものの名前は **`$` で始まる。** `$` は名前の一部である。

```
flow $return = $repeat(break, getdepth());

$$return i;
```

### 文脈自由になる

```
escapehead := 'break' ['outward'] | 'continue' | '$' IDENT ['(' escargs ')']
```

**名前解決が構文解析に要らなくなる。** 文脈自由でない箇所が**ゼロ**になる。

C-1 で「すべてのコードが構文解析できる」と決め、副産物として道具経路が完全になるとした。
**文脈自由なら、その完全性が構文の水準でも成り立つ**——tree-sitter のような文脈自由の道具が、
名前表なしで正しく解析できる。

### `$repeat` と揃う

C-15 で **`$` は作用素式の組み合わせ子を示す印**と決めた。
`$return` も作用素式なので、**同じ印が付くのが一貫する。**

これまでは組み込みの `$repeat` にだけ `$` が付き、`flow` で名付けたものには付かなかった——
**同じ圏のものに違う印**だった。

### 誠実になる

> Syntax は Semantic を誠実に示唆しなければならない。

**`return` は関数ではない。** `$` が無ければ `return i` は関数呼び出しに見える。
（外部の吟味で、`$repeat(break, …)` を「`break` を値として渡している」と読まれた。
印が無いと値の世界に見える。）

### 宣言にも `$` を付ける

```
flow $return = …;        採る
flow return = …;         採らない
```

**「いつ `$` を書くか」を覚える必要が無くなる。** `$` は名前の一部である。

### 代償

**`return` を書くたびに `$` が要る。** 最も頻繁に書くものなので実際に効く。

ただし **`return` は組み込みではない**（標準ライブラリの一行）。
`$` はそのことを字面に出す——**言語が与えた語ではなく、`flow` で名付けられたもの**だと。

## C-61. 外部の吟味で見つかった穴（十件）

### (1) 🔴 `operand := escape | expr` が束縛力表と矛盾していた

```
break_esc := 'break' ['outward'] [operand]
operand   := escape | expr
```

`expr` は `;` を含むので、**BNF どおりなら `break 5;` が `break (5;)` になる。**
束縛力表（脱出の右束縛力 8 > `;` の左束縛力 5）とは逆である。

**修正**：`operand := escape | expr@8`。**最低束縛力 8 で解析した式**とする。
`escargs` の値側も同様。

**BNF と束縛力表を併用したことによる穴**である。両者が同じことを言っているか、
書いた側が確かめていなかった。

### (2) 🔴 ループの値：脱出が上書きすることを書いていなかった

```
loop { break 5; }        値は 5
loop { 1; }              値は反復回数
```

C-3 は「ループの値は反復回数」とだけ書いた。**脱出で終わった場合を書いていない。**

> **正常終了したループの値は反復回数である。**
> **脱出で終わったループの値は、脱出が置いた値である。**

そして **`break` に被演算子が無い場合**（`loop { break; }`）：
`break` は外界面に何も置かないので、**ループの領域は空 → 外界面は paradox** になる。

```
loop { break; };          ; が潰す
let n := loop { break; } ?? 0;
```

**「値の無い脱出で抜けたループには値が無い」**——一貫している。

### (3) 🔴 `outward` の前後で段数が連続するか

```
break outward break break;
```

**規定していなかった。**

> **`outward` を越えた時点で段数は数え直される。**
> 越えた先は新しいフレームであり、そこでの段数はそのフレーム基準で数える。

`getdepth()` がフレーム基準である（C-23）ことと一貫する。
**フレームが変われば基準が変わる。**

### (4) 🔴 `let` の名前に破壊的メンバ関数を呼べるか

```
let a := new i64 array (10, 0);
a.push(1);
```

**規定していなかった。** レシーバは別名であり（C-20）、メンバ関数は破壊的である。
しかし `let` は「この名前から書けない」（C-35）。

> **破壊的メンバ関数はレシーバに `var` を要求する。**
> **書き込み能力は経路に伝播する**（C-51 の権限規則）。

```
let a := …;  a.push(1);     エラー
var a := …;  a.push(1);     よい
```

宣言側の `var self`（C-20）と、呼び出し側の `var` 束縛が**対になる。**

### (5) 🔴 `nfor` の回数が負のとき

**規定していなかった。**

> **回数が 0 以下なら 0 周。** 領域は `{}` になり paradox（C-44）。

`i` の増加は通常の整数演算なので、**溢れれば二の補数で折り返す**（C-21）。
反復回数の型は `i64` とする。

### (6) 🟡 「paradox は値である」が誤解を招く

```
f(1 / 0)
```

**paradox は関数に届かない。** 引数の領域が paradox で終結した時点でエラーになる。

したがって **paradox は「通常の値位置に置ける値」ではない。**

> **paradox は値の一種だが、`??` 以外の演算子は受け付けない。**

内部表現では次のように分けるのが正確である。

```
値 = 通常の値 | paradox
通常の演算子は「通常の値」だけを受け付ける
?? だけが paradox を受け付ける
```

「値である」と書いたのは、**`;` と `??` が扱える対象**だという意味だった。
**通常の値位置に置けるという意味ではない。**

### (7) 🟡 「エラーは三種」が不正確だった

C-46 は「静的1・実行時2 の三種」としたが、**静的エラーは一種ではない。**

名前解決の失敗、権限の違反、型構築の引数不足、比較の連鎖、`alias` 引数に名前以外を渡すこと——
**すべて静的エラーである。**

> **正しくは：実行時エラーは二種である。**
> **消費されなかった paradox と、フレームを越える脱出。それだけ。**
> **静的エラーは複数あってよい**——走らせる前に分かるので、数を絞る必要が無い。

「エラーは三種」は**実行時の一元性を言おうとして、静的側まで数えてしまった。**

### (8) 🟡 `switch` の入れ子

```
switch (x)
    case 1 => switch (y) case 2 => 10
    case 3 => 20
```

**`case 3` は内側の switch に食われる。** `case` 以外が来た時点で終わるので、
`case` が来れば内側が続く。

**入れ子の switch を最後の腕に置くには括弧が要る。**

```
case 1 => ( switch (y) case 2 => 10 )
case 3 => 20
```

**規約として書く。** 閉じる語を持たない代償である。

### (9) 🟢 循環データ構造は作れない（確認）

**別名は値の中に入れない**（C-48）。値は自己完結している。
したがって**値のグラフに循環は作れず、深い複製は必ず停止する。**

C-48 が意図せず**深い複製の停止性を保証していた。**

### (10) 🟢 `const` は値ごと凍る（確認）

```
const p := new Point ( x := 1, y := 2 );
p.x := 2;        エラー
```

構造体の値は**一つのセルに入る**（別名を含めないので、C-48）。
`p.x` は独立したセルではなく**セルの一部**である。
したがって**セルを凍らせれば欄も凍る。**

「セルが誰からも書けない」（C-35）から出る。**追加の規定は要らない。**

### 併せて確認したこと

- **`&&` / `||` は短絡する。** `0 && (1 / 0)` は右辺を評価しないので paradox が発生しない
- **比較の結果は `u1`**
- **無限ループは評価結果の第四の分類（発散）である。** エラーではない

## C-62. 束縛力表と BNF の境界で残っていた穴（十件）

C-61 で BNF を表に従属させたが、**表に載せるべきものを載せていなかった。**

### (1) 🔴 `:=` `&=` 複合代入を束縛力表に入れる

```
assign := path (':=' | compound) E | IDENT '&=' IDENT
```

を**一次式**に置いていた。しかし Pratt 解析は `x` を `IDENT` として読んだ後、
**`:=` を知らないので止まる。**

一次式として認識するには `path` を先読みせねばならず、`path` は
`a.b.c[i].d` と**任意長**である。**無限先読みになる。**

**修正：代入演算子を束縛力表に入れる。**

| 演算子 | 位置 | 左束縛力 | 右束縛力 |
|---|---|---:|---:|
| `:=` `&=` `+=` `-=` … | 中置・**非結合** | 7 | 6 |

- **`;`（5）より高い**ので `x := 5;` は `(x := 5);` になる
- **脱出（8）より低い**ので `break x := 5` は `break (x := 5)` にならない——
  脱出の被演算子は `parse(8)` であり、`:=`(7) を吸わない。**`break x` で切れる**
- **非結合**なので `a := b := c` は書けない。比較と同じく別の検査で禁じる
- **左辺が `path` であることは静的検査**である。文法は決めない（C-59 の方針どおり）

**`assign` を BNF から消す。** 代入は演算子になった。

**C-61 で「表を一次仕様にする」と決めたのに、表に入れ忘れた項があった。**
一次仕様にするとは、**演算子をすべて表に載せる**ということである。

### (2) 🔴 `switch` の腕が `;` を吸う

```
switch (x) case 1 => foo; bar;
```

腕を `parse(0)` で読むと **`;` を吸う。** すると腕の内面が空になり、
**腕の値が paradox になる。** 書き手の意図ではない。

**修正：腕の値は `parse(6)` で読む。** `;`（5）を吸わない。

すると `case 1 => foo;` は**構文エラー**になる——腕の後に `;` は書けない。
**黙って paradox になるより、書けない方がよい。**

腕の後に来てよいのは `case` か、switch の終わりだけである。

### (3) 🔴 `flow` の再帰

```
flow $a = $a;
flow $a = $b;  flow $b = $a;
```

**本体は使用位置で読み直される**（C-15）ので、**展開が止まらない。**

> **`flow` の本体に `flow` 名を書けない。**

`$repeat` は組み込みの組み合わせ子であって `flow` ではないので、この規則に触れない。

併せて規定する:

- **`flow` はスコープ全体で見える**（`fn` と同じ、C-36）
- **同名の再定義は不可。** 影を作れない
- **`$repeat` の第一引数は `break` か `continue` に限る。** `outward` を繰り返せない

### (4) 🟡 `&=` の再束縛

BNF に `assign := … | IDENT '&=' IDENT` があるので、**別名は指し直せる。**

```
var b &= a;
b &= c;        指し直す
```

**許す。** ただし:

- **`var` の別名にだけ許す。** `let` / `const` の別名は指し直せない
- **指す先の検査は宣言時と同じ**——同じか外側のスコープ、権限は増やせない

**指し直しは「名前が別のセルを指す」ことであり、セルの中身は変えない。**
`b := c` はセルに書き、`b &= c` は名前を動かす。**別の操作である。**

### (5) 🔴 `outward` の後の段数は静的に検査できない

```
fn f () { break outward break; }
loop { loop { f(); }; };
```

`outward` を越えた先の段数は**呼び出し位置による。** 同じ関数を別の場所から呼べば、
**同じ `break` が別の段を抜ける。**

> **`outward` を含む脱出の段数は静的に検査できない。**
> **実行時に検査する**（C-46 の実行時制御エラー）。

**これは `outward` の費用である。** `outward` を含まない脱出は静的に数えられる。

C-34 が `outward` を非推奨としたのは「呼び出し位置に何も現れない」からだが、
**「静的検査を捨てる」という費用の方が重い。** 記録する。

### (6) 🟡 反復回数の型

**`i64`。** 溢れれば二の補数で折り返す（C-21）。

`nfor` の `i` の型は**開始値の型**であり、増加は通常の整数演算である。
**開始値と回数の型は一致しなくてよい**——回数は `i64` に変換して読む。

### (7) 🔴 領域の値の数え方は「正常に続く経路」だけ

```
if (c) break else 2 fi
```

分岐の一方が脱出、他方が値。**領域に値がいくつあるか。**

> **脱出する経路は値を置かない。** 数えるのは**正常に続く経路**だけである。

```
loop { if (c) continue; fi; 1; }      通る
loop { if (c) break 1 else 2 fi }     エラー。else が値を残す
```

**これは単なる構文の数え上げではない。** 静的検査は
**式が値を置くか・paradox を置くか・脱出するか**を追わねばならない。

**検査器が制御フローを見る必要がある**ことを、初めて明記する。

### (8) 🟢 フレームの上限まで抜けるのは許される（確認）

```
fn f () { if (c) break 42 fi; … } -> i64;
```

`break` は関数本体（フレーム）を 1 段抜ける。**これは越えていない。**
`$return = $repeat(break, getdepth())` と一貫する——`getdepth()` が 1 なら `break` 一つ。

**エラーになるのは「越える」場合だけ。** 上限に到達するのは正常な脱出である。

### (9) 🟢 `switch` は脱出段を作らない。腕に脱出を書ける（確認）

腕は被演算子位置なので**脱出段ではない**（C-20）。したがって

```
loop { switch (x) case 1 => break 5 }
```

の `break` は**ループを抜ける。**

そして**脱出は前置演算子なので、式の先頭に書ける**——腕に書ける。

### (10) 🟢 `??` の右辺が paradox なら全体が paradox（確認）

```
1 / 0 ?? 2 / 0             paradox
1 / 0 ?? 2 / 0 ?? 42       42（右結合なので (2/0) ?? 42 が先）
```

`??` は**左を右で置き換える**だけであり、右を検査しない。
右が paradox なら、その paradox がそのまま外界面に出る。

### 併せて

- **別名は値の内部ではなくセルを指す。** `a.push()` で配列が再確保されても
  別名は同じセルを指したままである。**壊れない**
- 別名の読み出しは**値を読む。** `var z := y;` は `y` の指すセルの値を深く複製する

## C-63. `E` を監査していなかった（同じ誤りの三度目）

### (1) 🔴 宣言と欄の `:=` の右辺が `;` を吸う

```
binding    := IDENT [':' valuetype] ':=' E          E = parse(0)
fielddecl  := (…) IDENT ':' valuetype [':=' E]
structdecl := 'struct' IDENT '{' (fielddecl ';')* '}'
```

`E` は `parse(0)` なので **`;`（5）を吸う。**

```
let x := 1 / 0;      →  let x := (1 / 0;)     意味論と逆になる
struct Point { var x : i64 := 0; … }          欄が ; を吸うので、
                                              (fielddecl ';')* の ; が無い
```

**プローブに載せた `struct` の例が、自分の文法で解析できなかった。**

### これは三度目である

| | |
|---|---|
| **C-61** | `operand := escape \| expr` が `;` を吸った。`parse(8)` に直した |
| **C-62** | `:=` を束縛力表に載せていなかった。載せた |
| **C-63** | **BNF の `E` を全部監査していなかった** |

**三度とも同じ形である**——「式が要る箇所に、束縛力を書かずに済ませた」。

C-61 で「BNF に式が要る箇所は、すべて束縛力 N から解析した式と書く」と決めたのに、
**`E` という略記を作って、それが `parse(0)` だと一箇所で決めただけだった。**
略記は**一つの束縛力しか持てない**のに、式が要る箇所は**複数の束縛力を要求する。**

> **`E` という略記を廃止する。すべての箇所に束縛力を書く。**

### 監査の結果

| 箇所 | 束縛力 | なぜ |
|---|---|---|
| `paren` / `block` の中身 | **0** | 閉じ括弧で終わる。`;` を吸ってよい |
| `binding` の `:=` の右辺 | **6** | `;` が宣言を終える |
| `fielddecl` の `:=` の右辺 | **6** | `;` が欄を終える |
| `if` / `elif` / `else` の分岐 | **6** | `;` を吸うと分岐が黙って paradox になる |
| `switch` の腕 | **6** | 同上（C-62） |
| 脱出の被演算子 | **8** | `;` も `:=` も吸わない（C-61） |
| `[ ]` の中、引数、リテラルの要素 | **0** | 閉じ記号や `,` で終わる |
| `while` / `switch` の条件、`nfor` の三項 | **0** | 閉じ括弧で終わる |

**「閉じる記号があるなら 0、無いなら 6」** という規則である。

`if (c) a; fi` は**構文エラー**になる。`parse(0)` なら黙って paradox の分岐になっていた。

### (2) 🔴 私が書いた例が間違っていた

```
if (c) break else 2 fi          loop の中なら通る
```

**通らない。** `c` が偽なら `2` がループ本体に残る。
**「正常に続く経路だけ数える」なら、これは静的エラーである**（C-62 の規則が自分の例を否定した）。

正しくは:

```
loop { if (c) break else 2 fi }        エラー。else が値を残す
loop { if (c) break else 2; fi }       通る
loop { if (c) break fi; }              通る
```

**規則を書いた直後に、その規則に反する例を書いた。**

### (3) 🔴 段数を静的に検査できる条件

C-62 (5) は `outward` について書いたが、**`$repeat` も同じである。**

```
$repeat(break, n)      n が実行時の値なら、段数は実行時にしか分からない
```

> **段数を静的に検査できるのは、脱出が定数個並んでいる場合だけである。**
> **`$repeat` の回数が定数でない場合と、`outward` を含む場合は、実行時に検査する。**

`$return` は `$repeat(break, getdepth())` であり、`getdepth()` は**解析時に決まる**
（使用位置の字句的な深さ）ので、**`$return` は静的に検査できる。**

### (4) 🔴 脱出が値位置に現れたとき

```
(break 5) ?? 42
1 / (break 2)
f(break 3)
```

**規定していなかった。**

> **脱出は値位置を突き抜ける。** 演算子は適用されず、残りの被演算子も評価されない。

```
42 ?? break 5          42。右辺は評価されない
1 / 0 ?? break 5       break が実行される
break 5 ?? 42          脱出。?? は届かない
```

**`??` が捕まえるのは paradox だけである**（既定）。**脱出は通り抜ける。**

### (5) 🔴 再帰的な構造体

```
struct Node { var next : Node; };
struct A { var b : B; };  struct B { var a : A; };
```

**値は自己完結している**（C-48）ので、これは**無限の大きさ**になる。

> **構造体の型依存グラフは DAG でなければならない。** 静的エラー。

別名は値の中に入らないので、**再帰的なデータ構造はこの言語で作れない。**
必要なら**添字で表す**（配列に置いて `i64` で指す）。

**これは C-48 の帰結である**——記録していなかった。

### (6) 🟡 評価順序

> **すべての被演算子・引数・レシーバは左から右に評価する。**
> **代入は、左辺の場所を先に解決してから右辺を評価する。**

破壊的メンバ関数と別名があるので、**実装の細部ではない。**

### (7) 🟡 浮動小数と `mod`

- **`1.0 / 0.0` は paradox。** IEEE-754 の `inf` を作らない
- **`0.0 / 0.0` も paradox。** NaN を作らない
- **`i64` の最小値 ÷ −1 は折り返す**（二の補数、C-21）
- **`mod` の符号は左被演算子に従う**（`-7 mod 3` は `-1`）

**浮動小数の特殊値を言語に持ち込まない。** paradox が既にその役割を持っている。

### (8) 🟢 `const` の凍結に実行時の状態は要らない（確認）

「巻き戻し機構は無い」と「`const` はスコープを抜けると解ける」は矛盾しない——
**凍結は字句的であり、検査器が知っている。** 実行時にセルへ旗を立てる必要が無い。

**`const` は実行時に何もしない。** 静的検査だけで閉じる。

### (9) 🟡 `|>` の意味論をプローブに書いていなかった

```
x |> f(a)        ≡  f(x, a)
x |> f()         ≡  f(x)
```

**構文の水準の糖衣**（C-15）。第一級関数を要求しない。
**自由関数に適用する**——`x` の型の名前空間は探さない（探すなら `.` を書く）。

**束縛力表に載せながら意味論に書いていなかった。** 表と本文の対応も監査が要る。

## C-64. 入れ子の破壊的更新と、表の作り方の誤り

### (1) 🔴 入れ子の破壊的更新が書けなかった

```
var arr := [ [ 1 ], [ 2 ] ];
arr[0].push(3);
```

**書けなかった。** 「`alias` 引数に渡せるのは名前だけ」（C-53）が
**メンバ関数のレシーバにも掛かっていた。**

迂回するには要素を取り出して押し込み直すしかなく、**深い複製が二回走る。**
**性能のために作った言語で、入れ子の配列を更新できない。**

### C-53 の理由を読み直す

`&= a[i]` を禁じたのは**別名が束縛だから**である——`.push()` で再確保されたとき、
**束縛はその後も生き続けて壊れる。**

**メンバ関数のレシーバは呼び出しより長く生きない。** 危険が無い。

> **メンバ関数のレシーバは経路でよい。**
> **`&=` の制限は束縛にだけ掛かる。**

```
arr[0].push(3);        よい。レシーバは経路
p.inner.push(3);       よい
var b &= arr[0];       エラー。束縛は生き続ける
```

**規則の理由を確かめずに、規則の形だけを他へ広げていた。**

### (2) 🔴 `f(arr[0], arr)` の禁止は理由が違う

こちらは**同時に二つの別名が生きる**のが理由である——`f` が `arr` を伸ばせば
`arr[0]` の別名が壊れる。**寿命ではなく重複が理由。**

したがって規則を正しく述べ直す:

> **同じ呼び出しで、同じセルに届く別名を二つ以上渡せない。**
> **`alias` 引数に渡せるのは名前だけ**（これは寿命ではなく、重複を検査しやすくするため）。

```
f(arr[0], arr)         エラー。arr[0] は名前でない
f(p, p)                エラー。同じセルに別名が二つ
```

**二つ目は規定していなかった**（Claude の指摘）。

### (3) 🔴 ループ本体の `{ }` が二重の段に見えた

プローブの表:

```
| { E … }     | ○ | ○ | ○ |
| ループ本体   | ○ | ○ | ○ |
```

**これだと `loop { break }` がブロックを抜けるだけになる。**

元の記述（21-検証）は**「裸のブロック」**だった。**私が表を作ったときに「裸の」を落とした。**

> **`{ }` が段を作るのは、それ自体が式として置かれたときだけ。**
> **`loop` / `while` / `nfor` / `fn` の本体は、その構文の段である**——一つであって二つではない。

```
loop { break; };          ループを抜ける。段は一つ
loop { { break; }; };     裸のブロックを抜けるだけ。段は二つ
```

**四者中三者が指摘した。** 表を圧縮したときに修飾語を落とすと、意味が変わる。

### (4) 🔴 代入式が何を置くか

C-62 で `:=` を演算子にしたが、**何を置くか書いていなかった。**

> **代入は値を置かない。外界面は paradox である。**

宣言と同じ形になる（C-14）。だから `;` が要る。

```
x := 5;                 ; が代入の paradox を潰す
while (m) { m /= 10; }  本体に何も残らない
(x := 5) + 3            エラー。+ が paradox を受け付けない
```

**「セルに書く」は作用であって値ではない。** 一貫している。

### (5) 🔴 関数から見えるもの

「外側の局所変数を見ない」と「囲むスコープの宣言」が**矛盾して読めた**（四回連続で指摘された）。

> **関数本体から見えるのは、引数・自身のスコープの宣言・そして**
> **囲むスコープの `fn` / `struct` / `flow` 宣言だけである。**
> **局所変数（`var` / `let` / `const`）は、どのスコープのものも見えない。**

```
{
    var x := 1;
    fn f () { x }        エラー。局所変数は見えない
    fn g () { h() }      よい。fn は見える
    fn h () { 1 } -> i64;
}
```

**名前解決は関数の境界で鎖を切る。** ただし宣言の種類ごとに切る場所が違う。

### (6) 🟡 `const` の別名は元の名前も凍らせる

```
var a := 1;
{
    const b &= a;
    a := 2;            エラー。セルが凍っている
}
a := 2;                よい。スコープを抜けたので解ける
```

**「セルが誰からも書けない」は、字義どおりである。** `a` からも書けない。

**検査器は別名の指すセルを追う必要がある。** これが `const` の実装費用である。

### (7) 🟡 その他

- **`$repeat(op, n)` の `n` が 0 以下なら、作用素を一つも重ねない。** 被演算子がそのまま残る
- **浮動小数の非有限な結果はすべて paradox。** 溢れも、0 除算も、不定形も。**inf も NaN も作らない**
- **`str` は独立した基底型である。** `u8 array` とは別の型で、相互に代入できない。
  「`u8` の並び」という説明は表現の話であって、型の同一性ではない
- **評価順序は「評価されるものについて」左から右。** 短絡する `&&` / `||` と `??` は右を評価しないことがある
- **`path` に無限先読みは要らない**——**任意長の反復**である。C-62 の書き方が誤り。
  代入を演算子にした理由は変わらない（一次式として認識するには `path` を読み切ってから
  `:=` を見る必要があり、それは先読みではなく**投機的な解析**になる）

### この回の教訓

**(1) は規則の理由を確かめずに形だけを広げた誤り**、
**(3) は表を圧縮したときに修飾語を落とした誤り。**

どちらも**元の文書には正しく書いてあった。** 要約する過程で壊した。

> **要約は情報を落とすが、どれを落としてよいかは元の文書を見ないと分からない。**

## C-65. 存在しない決定を引用した（`self`）

### 何が起きたか

`fn Point.norm2 (self)` というメンバ関数の構文は、**決定に存在しない。**

1. 私が 14-構文-型と集合体.md に**提案として**書いた
2. **承認されていない**
3. **C-64 で「宣言側の `var self`（C-20）」と書いた**——存在しない決定の引用
4. プローブに例として載せ、**決定済みのものとして外部に出した**

C-20 が決めたのは「**メンバ関数のレシーバは複製しない**」だけである。
**`self` も `fn T.m` も、レシーバの書き方も、何も決めていない。**

### (3) が一番悪い

番号を付けて引用すれば、**後から読む私自身も「決まっている」と読む。**
提案と決定の区別が、引用によって消えた。

**却下理由を捨てないと決めたのに、決定していないものを決定として記録した。**
記録の目的は「何が決まって、何が決まっていないか」を保つことなのに、
**引用が境界を壊した。**

### 再発を防ぐ

> **`docs/vaak/1x-*.md` は提案である。決定は `decisions.md` にしかない。**
> **`C-n` を引用するときは、その C-n を読んでから引用する。**

C-64 の当該箇所は誤りとして残す（消さない）。

### メンバ関数の構文は未決定に戻す

**プローブから `self` を含む例を外す。** 決めていないものを外部に見せない。

未決定として残るもの:

- メンバ関数を宣言する構文（`fn T.m (self, …)` は**一案にすぎない**）
- レシーバをどう書くか、型注釈を省けるか
- そもそも**メンバ関数を宣言できるのか**——
  C-20 は「メンバ関数のレシーバ」に触れているが、
  **利用者が定義できるとは決めていない。** 標準ライブラリだけが持つ可能性もある

**「まだ決めていないこと」に加える。**

## C-66. `->` は外界面の型である（C-29 からの導出）

### プローブが C-29 を書いていなかった

C-29 は「**すべての型は paradox との直和である**」と決めた。
**プローブはこれを一度も書いていない**——`find(xs, 42) ?? -1` のような例で示すだけだった。

外部の吟味が

```
fn f () { if (c) break 42 fi; };      -> が無いのに 42 を置く
```

を穴として挙げたが、**C-29 を書いていれば穴ではない。**

### 導出

**`->` は「外界面の型」である。** 正常終了時の型ではない——
外界面は paradox にもなりうるので、**`-> i64` は「`i64` または paradox」を意味する。**

したがって:

| | 外界面の型 |
|---|---|
| `-> i64` | **`i64` ⊕ paradox** |
| `->` が無い | **paradox のみ** |

`->` の無い関数は「値を返さない」のではなく、**外界面が paradox しか取らない**と宣言している。

```
fn f () { if (c) break 42 fi; };        エラー。paradox しか取らない外界面に 42 を置いた
fn f () { if (c) break 42 fi; } -> i64; よい。c が偽なら paradox
```

**脱出で置いた値も、正常終了で置いた値も、同じ外界面に置かれる。** 区別しない。

### なぜ「正常終了時の型」ではないのか

そう定義すると **paradox が型から漏れる。**

```
fn find (…) { … } -> i64;
let pos := find(xs, 42) ?? -1;
```

`find` は見つからなければ paradox を返す。「正常終了時の型が `i64`」だと、
**この paradox がどの型に属するのかを別に説明せねばならない。**

**外界面の型と定義すれば、`??` が何を除去しているかがそのまま読める。**
`-> i64` の `??` は直和の paradox 側を落として `i64` にする。C-29 の除去子そのもの。

### `->` の無い関数に `-> paradox` と書かせないのはなぜか

**paradox は型ではなく、すべての型に含まれる腕だから**（C-29）。
「paradox だけの型」は直和の片側だけであり、**基底型の一覧に無い。**

`->` を書かないことが、その状態を表す。**書かないという選択肢が型を一つ表している。**

### 併せて

**`-> T` の関数が `;` で終わっても構文エラーにはならない**——
外界面が paradox になるだけで、`i64 ⊕ paradox` の範囲内である。

```
fn f () { 1; } -> i64;      通る。常に paradox を返す
```

**無意味だが型としては正しい。** 静的検査で警告してよいが、エラーではない。

## C-67. `;` は制御構造の外に書く（C-63 の例が誤っていた）

### 私が書いた例が構文エラーだった

C-63 でループ本体の書き方を直したとき、こう書いた。

```
loop { if (c) break else 2 fi }       エラー。else が値を残す
loop { if (c) break else 2; fi }      通る                      ← 誤り
```

**二つ目は構文エラーである。** `else` の分岐も `parse(6)`（C-63 で自分が決めた）なので、
`2` で止まり、`;` が `fi` の位置に来る。

正しくは:

```
loop { if (c) break else 2 fi; }      ; は fi の後
```

**`;` は `if` の値を潰す。`if` の値は分岐が置いたものである。**
だから `;` は `fi` の後に来る——**分岐の中ではない。**

### 同じ誤りを外部も犯した

外部の吟味が「値を捨てたいなら `if (c) (a;) fi` と書く必要がある」とした。
**これも誤り**である——`( a; )` は分岐を paradox にするだけで、`if` の値は消費されない。

```
if (c) ( a; ) fi       エラー。paradox が残る
if (c) ( a; ) fi;      通る。ただし if (c) a fi; と結果は同じ
if (c) a fi;           これが普通の書き方
```

**括弧は「捨てるための道具」ではない。「一つの分岐に二つ書くための道具」である。**

```
if (c) ( a; b ) fi     a を潰して b を残す。これが本来の用途
```

### なぜ二者が同じ誤りをしたか

**`;` を「文の終わり」として読んだから。** C 系の言語では `;` が文に付くので、
`if (c) a; fi` を「`a` という文」と読む。

Vaak では `;` は**値を潰す後置演算子**であり、**潰す対象は左の式の値**である。
`if` の中に書けば分岐の値を潰し、`fi` の後に書けば `if` の値を潰す。**別の操作になる。**

`parse(6)` は前者を**構文エラーにする**（C-62 / C-63）——
黙って paradox になるより書けない方がよい、という決定である。
**その決定が正しく働いた**が、**決定した本人が例を間違えた。**

### 記録

**規則を決めた直後に、その規則に反する例を書いた**のは C-63 (2) に続いて二度目である。

> **例は規則から導いて書く。覚えている形をそのまま書かない。**

## C-68. 分岐と腕を `parse(0)` に戻す。`E@6` は `:=` の右辺だけ

### `parse(6)` は `$return i; fi;` を壊していた

C-62 は `switch` の腕を、C-63 は `if` の分岐を `parse(6)` にした。
理由は「`;` を吸うと分岐が黙って paradox になるから」。

しかし**それはこの言語で普通に起きることである。**

```
( a; )      内面が空 → 外界面は paradox
{ a; }      同上
```

**分岐だけを特別扱いする理由が無い。** そして実害があった:

```
if (a[i] == x) $return i; fi;
```

**`find` の中身が構文エラーになっていた。** C-43（`break` は領域を閉じてから脱出するので
`;` が要る）と 21-検証 の「`;` が二重に見えるが、どちらも要る」を、**構文が禁じていた。**

### 戻す

> **`if` / `elif` / `else` の分岐と `switch` の腕は `parse(0)` で読む。**

```
if (c) a; fi        分岐が paradox になる。( a; ) と同じ
if (c) a; fi;       ; が if の paradox を潰す
if (c) a fi;        同じ結果。どちらでもよい
```

**「黙って paradox になる」ことを受け入れる。** それがこの言語の一貫した振る舞いだからである。

### 規則が単純になった

`E@6` が残るのは**二箇所だけ**である。

```
binding   := IDENT [':' valuetype] ':=' E@6
fielddecl := (…) IDENT ':' valuetype [':=' E@6]
```

そして **6 は代入演算子 `:=` の右束縛力そのもの**である（C-62 の表）。

つまり**特別な規則ではない。**

> **`:=` の右辺は `parse(6)`。** 宣言の `:=` も、演算子の `:=` も同じ。
> **それ以外はすべて `parse(0)`。**

`var x := 5;` が `var x := (5;)` にならないのは、
**`:=` の右束縛力が `;` より高いから**——表がそのまま効いている。

C-63 の「閉じる記号があるなら 0、無いなら 6」という説明も**要らなくなった。**
あれは**私が作った規則**であり、表から出ていなかった。

### 記録

C-61 → C-62 → C-63 → C-68 は同じ主題の四回目である。

| | |
|---|---|
| C-61 | BNF を束縛力表に従属させた |
| C-62 | 代入演算子を表に載せた |
| C-63 | `E` の略記を廃し、各箇所に束縛力を書いた |
| **C-68** | **表から出ない束縛力（分岐の 6）を捨てた** |

**三回は「表に書いていなかった」誤りだったが、今回は「表に無いものを書いた」誤りである。**
一次仕様を決めたあと、**そこから出ないものを足していないか**も見なければならない。

## C-69. 値は書かれた位置で評価される。`+` と `-` は左を要求しない

### (1) 🔴 「作用素式なら外界面で実行される」が値を運べなかった

これまでこう書いていた。

> 被演算子が**値なら、ここで評価されて置かれる**。
> **作用素式なら、外界面で実行される。**

愚直に読むと:

```
{{ let x := 2; break break x }}
```

内側の `break x` が**外界面で実行される**なら、その被演算子 `x` も**外界面で読まれる。**
しかし外界面は内側のブロックを出た後であり、**`x` のスコープは消えている。**

**値を持ち出せない。**

### 直す

> **値はすべて、書かれた位置で評価される。**
> **外界面で実行されるのは、脱出という作用だけである**——段を一つ進めること。

```
{{ let x := 2; break break x }}
```

1. `x` を**ここで**読む → 2
2. 脱出が 2 を運ぶ
3. 内側のブロックを抜ける
4. 外界面で `break 2` が実行され、外側のブロックを抜ける
5. **2 が置かれる**

**脱出は評価済みの値を運ぶ。** 入れ子は**段を足すだけ**である。

これで `break break x` も `break y` も同じ規則で説明できる——
**前は二つの規則を書いていた。**

### (2) 🟢 `;` の連続は有効（確認）

```
1;;
```

1. `1;` → 内面が空になる
2. 二つ目の `;` は**左辺に領域を要求する**。その領域は空なので**値は paradox**
3. `;` が paradox を潰す

**通る。** 規則から出るだけで、特例は要らない。

そして `{ ; }` は**構文エラー**である——`;` は後置演算子であり、左辺の式が無い。
**「左辺の領域が空」と「左辺の式が無い」は別である。**

### (3) 🔴 `+` と `-` は左被演算子を要求しない演算子である

(2) から導かれる。`;` は**左辺に領域を要求する**演算子だった。
では**要求しない**演算子はあるか——**`+` と `-` がそれである。**

> **`+` と `-` は左被演算子を要求しない。**
> **左に値があればそれを取り（加算・減算）、無ければ取らない（符号）。**

```
a - b        左に値がある → 減算
- b          左に値が無い → 符号反転
{ -1 }       領域の先頭に書ける
a; -b        `a;` で空になった後なので符号
```

**二つの演算子ではなく、一つの演算子である。** 束縛力表は二つの欄を持つが、
それは**左を取ったときと取らなかったときで強さが違う**からにすぎない。

| | 左を取る | 左を取らない |
|---|---|---|
| `+` `-` | 50 / 51 | — / 80 |
| `!` | **取れない** | — / 80 |
| `;` | **必ず取る** | **取れない** |

**`!` と `;` が両端**であり、**`+` `-` がその間にいる。**

### なぜこれが「決まる」のか

`;` を「左辺に領域を要求する」と述べた時点で、**要求しないという選択肢が存在する。**
`+` と `-` は前置にも中置にも書けるので、**その選択肢を取っている演算子である。**

前は「前置の `-` と中置の `-` は別の演算子」と暗黙に扱っていた。
**同じ演算子の、左を取った場合と取らなかった場合である。**

### 単項 `+` を表に足す

これまで前置は `- !` だけだった。**`+` も前置に置く。**
何もしない演算子だが、**`-` と対称でなければ「左を要求しない」が `-` だけの特例に見える。**

## C-70. 脱出の鎖を精査する（C-69 の帰結）

C-69 で「値は書かれた位置で評価される。外界面で実行されるのは段送りだけ」とした。
**`continue` / `outward` / `getdepth()` との兼ね合いを追う。**

### (0) まず、段送りの順序を規定していなかった

```
break break break 1
```

は前置演算子の鎖である。外側の `break` が段を一つ進め、
**その外界面で内側が実行される。** したがって:

> **段送りは、書いた順（左から右）に起きる。**
> **値は全部の段送りより前に、書かれた位置で評価される。**

```
break break break 1
  ①    ②    ③   ← 段送りの順
  1 は ① より前に読まれる
```

**「左から右」は読み下しと一致する。** 規定していなかったが、直感どおりでよい。

### (1) 🟢 `continue` は鎖の終端にしかない（確認）

`continue` は被演算子を取らない（C-50）ので、**鎖の最後にしか書けない。**

```
break continue;        ② 段進めて、そこのループを次の周回へ
continue break;        文法エラー
```

`continue` 自身も**一段進めてから**ループを次の周回にする。
したがって `break continue` は**二段**進む。**`continue` 単独は一段。**

**問題なし。**

### (2) 🔴 `outward` は鎖のどの `break` に付くかで意味が変わる

`outward` は「**この段送りがフレームを越えてよい**」という印である。
段送りは左から右なので、**k 番目の `break` に付けた `outward` は k 番目の段送りに掛かる。**

```
fn f () { break outward break 1; }          深さ 1。① がフレームを越える
fn f () { { { break outward break 1; } } }  深さ 3。① はブロックを抜けるだけ。outward は空振り
```

**深さ 3 からフレームを越えるには、三番目に書く。**

```
fn f () { { { break break break outward break 1; } } }
                ①     ②     ③(フレーム)   呼び出し側で
```

**規定していなかった。** そして**空振りの `outward` を許すかを決める必要がある。**

> **フレームを越えない位置の `outward` は静的エラーとする。**

書いた本人が「越える」と思っているのに越えないのは、**黙って別の意味になる**。
段数が静的に分かる鎖（`$repeat` を含まない）では**検査できる。**

### (3) 🔴 `outward` の被演算子は脱出でなければならない

C-55 は「`outward` は被演算子を要求する」とした。**弱すぎた。**

```
fn f () { break outward 42; }
```

を追うと:

1. `break` がフレームの段を進める（＝**関数から返る**）
2. `outward` が越えることを許す
3. `42` が外界面——**呼び出し位置の領域**——に置かれる

**これは `break 42` と同じである。** `outward` が何もしていない。

**`outward` が効くのは、被演算子が脱出のときだけ**である——
越えた先で**さらに段を進める**から。

> **`outward` は被演算子に脱出を要求する。** 値は取れない。

```
break outward break 1;      よい
break outward continue;     よい
break outward 42;           エラー。break 42 と書け
break outward;              エラー
```

**C-55 を訂正する。** 「被演算子を要求する」ではなく「**脱出を要求する**」。

### (4) 🔴 `getdepth()` は `outward` を越えられない

**これが一番深い。**

`getdepth()` は値なので、C-69 により**書かれた位置で評価される**——
つまり**そのフレームの深さ**を返す。

しかし `outward` の後の段送りは**呼び出し側のフレーム**で起きる。

```
break outward $repeat(break, getdepth())
```

`getdepth()` は**呼ばれた側**の深さを返し、その数だけ**呼んだ側**の段を進める。
**別のフレームの深さで段を数えている。**

> **`outward` を越えた後の段数に `getdepth()` を使えない。静的エラー。**

`$return` は `$repeat(break, getdepth())` なので、**`break outward $return` も書けない。**

**呼び出し側の深さは、呼ばれた側から知りようがない。** これは
C-62 (5)「`outward` を含む脱出の段数は静的に検査できない」の裏側である——
**静的に検査できないだけでなく、動的にも数えられない。**

したがって `outward` の後に書けるのは、**定数個の `break` と `continue` だけ**である。

### まとめ

| | |
|---|---|
| 段送りは**左から右** | 規定を追加 |
| 値は**全部の段送りより前**に評価される | C-69 |
| `continue` は鎖の終端。**一段進めてから**次の周回へ | 確認 |
| **`outward` は k 番目の段送りに掛かる。空振りは静的エラー** | 規定を追加 |
| **`outward` の被演算子は脱出に限る** | C-55 を訂正 |
| **`outward` の後に `getdepth()` を使えない** | 規定を追加 |

**`outward` の費用がまた増えた。** C-34 が非推奨としたのは正しかった。

| | `outward` が失うもの |
|---|---|
| C-62 | 段数の静的検査 |
| C-70 | **`getdepth()`、つまり `$return`** |
| C-70 | **値を直接置くこと**（脱出しか書けない） |

## C-71. 脱出は被演算子の種類だけが違う（C-50 と C-70 (1) の訂正）

### C-50 が「`continue` は被演算子を取らない」としたのは誤り

正しくは:

> **`continue` は作用素式か虚無しか取らない。値を取れない。**

`continue continue` も `continue break` も**有効**である。禁じられるのは `continue 1` だけ。

### 三つは同じ形の演算子である

| | 値 | 作用素式 | 虚無 |
|---|:-:|:-:|:-:|
| `break` | ○ | ○ | ○ |
| **`continue`** | **×** | ○ | ○ |
| **`outward`** | **×** | ○ | **×** |

**構文が三つ別々なのではない。一つの形があって、被演算子の種類が違うだけである。**

```
escape   := 'break' ['outward'] [被演算子]
被演算子 := escape | 式
```

そして**被演算子の種類は静的検査である**——`continue 1` は型のエラーであって、
文法のエラーではない。**文法で特別扱いしていたのを、規則に戻す。**

### なぜ `continue` が値を取れないか

**周回を次へ進めることは、値をどこにも置かない。** 置き場所が無い。

`break` は「段を進めて値を置く」ので置き場所がある。
`continue` は「段を進めて、そこを次の周回へ」なので、**進めた先は領域の終わりではない。**

`outward` が虚無すら取れないのは C-70 (3)——値を置くなら `outward` が要らないから。

### 文法を直す

```
escape        := break_esc | continue_esc | flow_esc
break_esc     := 'break' 'outward' escape | 'break' [被演算子]
continue_esc  := 'continue' [escape]
```

`continue` の被演算子が `escape` に限られることは**文法で書ける**（値を排除できるので）。
`break outward` の被演算子も `escape` に限る。

**`break` だけが「値も取れる」ので `被演算子` を使う。**

### 残る問い：`continue continue` と `break continue` は同じか

段送りが左から右で、鎖の**最後の脱出が動作を決める**なら、
**中間の脱出は段を進めるだけ**なので二つは一致する。

```
break continue        二段進めて、そこを次の周回へ
continue continue     同じ
```

**冗長である。** ただし**禁じる理由も無い**——`break break` を許すのと同じ理由で。

**判断を求める。** 一致でよいか、それとも中間の `continue` に別の意味を与えるか。

## C-72. `break` は終結させ、`continue` は再開させる。四種類目のエラー

### 二つは「段を進める」点では同じだが、進めた段をどうするかが違う

> **`break` は段を終結させる。`continue` は段を再開させる。**

したがって:

```
nfor (i, 0, 10) { break continue; }
```

は**エラー**である——`break` がループを終結させた後で、`continue` が再開しようとする。
**終結した段は再開できない。**

**`break continue` と `continue continue` は一致しない。** C-71 の問いへの答え。

### 四種類目のエラー

これまで実行時エラーは二種（未消費の paradox・フレームを越える脱出）だった。

> **終結した段を再開しようとすること。**

`continue` の抜けた先がループでない場合（C-50）も、これに含まれる——
**再開できるものが無い**という一つの形にまとまる。

| | 種類 | |
|---|---|---|
| 1 | 静的 | 複数（領域の値の数、権限、名前解決 …） |
| 2 | 実行時（値） | 消費されなかった paradox |
| 3 | 実行時（制御） | フレームを越える脱出 |
| **4** | **実行時（制御）** | **終結した段の再開** |

3 と 4 はどちらも制御だが、**別の失敗である**——
3 は「進みすぎ」、4 は「もう無いものに作用した」。

### `outward` も作用素式しか取らない（確認）

C-70 (3) のとおり。虚無も値も取らない。

```
break outward break 1;      よい
break outward continue;     よい
break outward 42;           エラー
break outward;              エラー
```

### 🔴 未解決：被演算子の値をいつ読むか（C-69 と衝突）

```
nfor (i, 0, 10) { continue break i; }        値は 1
```

`continue` が段を再開させ、**次の周回の先頭が外界面になる。**
そこで `break i` が実行され、`i` は**その周回の値**——つまり 1。

**これは「値は書かれた位置で評価される」（C-69）と衝突する。**
C-69 なら `i` は最初の周回で読まれて 0 になる。

一方 C-69 は次のために入れた:

```
{{ let x := 2; break break x }}        x を持ち出せるように
```

`break` の外界面は**段の外**なので、そこで `x` を読もうとしてもスコープが無い。

### 二つの読み方

**A. 段を進めてから、被演算子を外界面で処理する**（C-69 以前）

- `continue break i` → 1 ✓（`continue` の外界面は再開した本体の先頭。`i` は生きている）
- `break break x` → **エラー**（`break` の外界面ではスコープが死んでいる）

**B. 値は全部の段送りより前に読む**（C-69）

- `continue break i` → 0 ✗
- `break break x` → 2 ✓

**A なら `continue` の外界面が「再開した本体の先頭」であることが効く。**
`break` と `continue` で外界面の位置が違う、という一貫した説明になる。
代わりに `break break x` が書けない——**値を持ち出したいなら外側で宣言する。**

**B なら `break break x` が書けるが、`continue break i` が 0 になる。**

**判断を求める。** A を採るなら C-69 を取り消す。

## C-73. `break` の被演算子は即時評価。`continue` は遅延（C-69 / C-72 の決着）

### 決定

> **`break` の被演算子は即時評価される。**
> **`continue` の被演算子は即時評価されない**——再開した本体の先頭で処理される。

C-72 の A/B は**どちらでもなく、脱出ごとに違う。** そして**それは導出できる。**

### なぜ違うか

**外界面がスコープを保っているかどうかが違う。**

| | 外界面 | スコープ |
|---|---|---|
| `break` | **段の外** | **死んでいる** |
| `continue` | **再開した本体の先頭** | **生きている** |

`break` の外界面では値を読めない。**だから先に読むしかない。**
`continue` の外界面では読める。**だから先に読む理由が無い。**

### そして `continue` で即時評価してはいけない理由がある

即時に読むと、**前の周回の値を次の周回に持ち込む。**

```
nfor (i, 0, 10) { continue break i; }
```

即時なら `i` は最初の周回の 0。しかし `continue` は**次の周回へ進む**のだから、
**そこで読むべき値は次の周回の `i`**——1 である。

**前の周回の値を運ぶのは、周回の意味を壊す。**

### 適用は再帰的

```
{{ let x := 2; break break x }}          2
```

`break` なので即時——`x` は書かれた位置（内側のブロック）で読まれる。
入れ子でも同じ。**`break` の下にある値はすべて即時に読まれる。**

```
nfor (i, 0, 10) { continue break i; }    1
```

`continue` の被演算子は遅延するので、**`break i` ごと**再開した本体の先頭へ送られる。
そこで `break` が実行され、**そこで `i` が即時に読まれる**——次の周回の 1。

**「`break` は即時、`continue` は遅延」を再帰的に適用するだけ。** 特例は無い。

### C-69 を訂正する

C-69 は「値はすべて書かれた位置で評価される」とした。**`break` についてのみ正しい。**

```
break の被演算子    → 書かれた位置で評価
continue の被演算子 → 再開した本体の先頭で処理
outward の被演算子  → 脱出しか取らないので値の問題が起きない
```

**三つとも、外界面がどこかから決まっている。** C-69 の「外界面で実行されるのは段送りだけ」
という一文が言い過ぎだった——**外界面がどこかで、被演算子の扱いが決まる。**

## C-74. `mod` は常に非負を返す。併せて、承認を経ていない規定の洗い出し

### `mod` の訂正

C-63 (7) で「**`mod` の符号は左被演算子に従う**（`-7 mod 3` は `-1`）」と書いた。
**承認を経ていない。私の勝手な規定である。**

> **`mod` は常に非負整数を返す。**

```
-7 mod 3        2      （-7 = -3 × 3 + 2）
7 mod -3        1      （7 = -2 × -3 + 1）
7 mod 0         paradox
```

**結果は常に `[0, |右辺|)` に入る。** ユークリッド剰余である。

### 🔴 これは `/` の丸めを決めてしまう

`a = (a / b) × b + (a mod b)` を保つなら、**`/` は床で丸めねばならない**（正の除数のとき）。

```
-7 / 3     床なら -3。-7 - (-3 × 3) = 2      ✓ mod と整合
-7 / 3     0方向なら -2。-7 - (-2 × 3) = -1  ✗ mod と矛盾
```

**`/` の丸めは決定に無い。** C-21 は溢れ・0除算・暗黙変換しか決めていない。

**判断を求める。**

- **A. `/` を床で丸める。** `mod` と整合する。Python と同じ
- **B. `/` を 0 方向で丸める。** C・Rust と同じだが、**恒等式が壊れる**
- **C. 恒等式を保証しない。** `/` は 0 方向、`mod` は非負。両者は独立

### 承認を経ていない規定の一覧

`self`（C-65）と `mod`（今回）で二度起きた。**同じ経路のものを全部挙げる。**

これらは**私が導出・提案したもので、承認を経ていない**:

| | 出所 | 内容 |
|---|---|---|
| 1 | C-62 | **反復回数の型は `i64`** |
| 2 | C-62 | **`nfor` の回数が 0 以下なら 0 周** |
| 3 | C-63 | **`1.0 / 0.0` も `0.0 / 0.0` も paradox**（inf も NaN も作らない） |
| 4 | C-64 | **浮動小数の非有限な結果はすべて paradox**（溢れも含む） |
| 5 | C-64 | **`$repeat(op, n)` の `n` が 0 以下なら作用素を重ねない** |
| 6 | C-64 | **`str` は独立した基底型**（`u8 array` と相互に代入できない） |
| 7 | C-63 | **`i64` の最小値 ÷ −1 は折り返す** |
| 8 | C-62 | **`&&` / `||` は短絡する** |
| 9 | C-63 | **評価順序は左から右** |
| 10 | C-62 | **比較の結果は `u1`**（これは C-21 にあるので承認済み） |

**10 以外は承認を経ていない。** プローブに載せているので、**外部には決定として見えている。**

### なぜ起きるか

外部の吟味が「ここが未定義だ」と指摘する。私はそれに答えを書く。
**答えを書くことと、決めることを区別していなかった。**

未定義の指摘に対する正しい応答は二つある。

- **導出できるなら導出を示す**（C-66 の `->` がこれ）
- **導出できないなら「まだ決めていないこと」に入れる**

**私は三つ目——その場で決める——をやっていた。**

### 規則

> **導出できないものを決定として書かない。**
> **「まだ決めていないこと」に入れて、判断を仰ぐ。**

上の 1〜9 を**保留に戻す**。プローブでは「まだ決めていないこと」に移す。

## C-75. C-74 の裁定

### 承認された（1・2・3・5・7・8・9）

保留から決定に移す。

| | |
|---|---|
| 1 | **反復回数の型は `i64`** |
| 2 | **`nfor` の回数が 0 以下なら 0 周** |
| 3 | **`1.0 / 0.0` も `0.0 / 0.0` も paradox** |
| 5 | **`$repeat(op, n)` の `n` が 0 以下なら作用素を重ねない** |
| 7 | **`i64` の最小値 ÷ −1 は折り返す** |
| 8 | **`&&` / `||` は短絡する** |
| 9 | **評価順序は左から右** |

### 6 は C-7 に反していた（取り消す）

C-64 (6) で「**`str` は独立した基底型**」と書いた。
**C-7 が「`str` は `u8 array` の別名。言語は文字を知らない」と決めている。**

**取り消す。** `str` は `u8 array` の別名であり、相互に代入できる。

```
var a : str := …;
var b : u8 array &= a;      よい。同じ型である
str array                   ≡ (u8 array) array
```

**承認済みの決定に反する規定を書いた**のは初めてである。
`self`（C-65）と `mod`（C-74）は「決めていないものを決めた」だったが、
**これは「決まっているものを違う形で決め直した」。**

**より重い。** 引用せずに書いたので、決定と衝突していることに気づかなかった。

> **その領域に既に決定があるかを確認してから書く。**

### 4 は 3 から導かれる（決定とする）

**問い**：浮動小数の仕様はどうなるか。

IEEE-754 は、有限でない結果を二種類作る。

| | いつ | |
|---|---|---|
| **inf** | 0 除算、溢れ | `1.0 / 0.0`、`1e308 * 1e308` |
| **NaN** | 不定形 | `0.0 / 0.0`、`inf - inf` |

**NaN は paradox に潰す**（承認）。

**inf も潰さねばならない**——3 で `1.0 / 0.0` を paradox と決めたからである。
`1.0 / 0.0` は IEEE では inf であり、これを paradox にするなら、
**溢れで出る inf だけを値として許す理由が無い。**

> **浮動小数の非有限な結果はすべて paradox。**
> **inf も NaN も、この言語には存在しない。**

検査は `is_finite()` 一つで済む。

### この決定の効き方

**NaN が存在しないので、比較が全順序になる。**

```
a < b       NaN が無いので、三分律が成り立つ
a == a      常に真
```

IEEE の「NaN はどれとも等しくない」という穴が塞がる。
**`==` が同値関係になり、`<` が全順序になる。**

これは paradox が既に「値が無い」を表しているからできることである——
**IEEE は値の中に「値でない」を紛れ込ませたが、この言語には外に置く場所がある。**

## C-76. 除算はユークリッド除算

**決定**：`/` と `mod` は**ユークリッド除算**である。

> **余りが `[0, |右辺|)` に入るように商を丸める。**

```
 7 /  3   2      7 mod  3   1
-7 /  3  -3     -7 mod  3   2
 7 / -3  -2      7 mod -3   1
-7 / -3   3     -7 mod -3   2
```

**恒等式 `a = (a / b) × b + (a mod b)` が常に成り立つ。**

### 丸めの向きは一つの規則で決まる

| | |
|---|---|
| 右辺が正 | **床**（floor） |
| 右辺が負 | **天井**（ceil） |

向きが変わるように見えるが、**規則は一つである**——「余りが非負になるように」。
**符号による場合分けをしていない。**

### なぜ 0 方向でも床でもないか

**0 方向（C・Rust）**は、**丸めの向きが被演算子の符号で変わる。**
`7/3` は下へ、`-7/3` は上へ丸まる。**一貫性が無い。**

**床（Python）**は丸めの向きこそ一定だが、**余りが除数の符号に従う。**
`7 mod -3` が `-2` になる。**「余り」が負であることに意味が無い。**

**ユークリッドは「余り」の側を一定にする。** 余りは常に「割り切れなかった量」であり、
量が負になることは無い。**丸めは余りに従属する。**

### 効き方

**配列の添字に直接使える。**

```
a[i mod a.len()]
```

`i` が負でも**必ず範囲内に入る。** 0 方向や床では、負の `i` で範囲外になるか、
`((i mod n) + n) mod n` と書く必要がある。**この言語では要らない。**

### 端の場合

- **右辺が 0 なら paradox**（`/` も `mod` も、C-21）
- **`i64` の最小値 ÷ −1 は溢れて折り返す**（C-75 の 7）
- 符号なし型では通常の除算と一致する

## C-77. `str` は `u8 array` をラップした型（C-7 の改定）

**決定**：`str` は `u8 array` の**別名ではなく、それをラップした型**である。

C-7 は「別名」とした。**改定する。** C-64 (6) の「独立した基底型」も違う——
**表現は `u8 array` であり、そこは変わらない。**

| | 表現 | `u8 array` と代入し合えるか |
|---|---|---|
| C-7（別名） | `u8 array` | **できる**（同じ型） |
| C-64（独立）✗ | 不明 | できない |
| **C-77（ラップ）** | **`u8 array`** | **できない**（別の型） |

### C-7 のうち残るもの

- **言語は文字を知らない**
- **添字はバイトを返す。長さはバイト数**
- **UTF-8 の解釈は標準ライブラリのメソッド**
- **NUL 終端を持たない**
- **文字列リテラルは型が決まるまでソースの表現を保持する**

**変わるのは型の同一性だけ**である。「文字を知らない」という核は動かない。

### なぜラップが要るか

別名だと、**`u8 array` を受け取る関数に `str` がそのまま入る。**
逆も入る——**バイト列と文字列が区別できない。**

暗黙変換が無い（C-21）以上、**別名は「区別しない」という選択**になる。
ラップすれば、**区別したうえで、剥がす操作を明示できる。**

二層構造（§2.4）とも合う——**抽象を使う自由と、剥がす自由の双方を残す。**
別名には「剥がす」という段階が無い。

### 🔴 決まっていないこと

**ここで決めない**（C-74 の規則）。

1. **`str` と `u8 array` の間をどう行き来するか。**
   構築（`new str ( bytes )`）か、メソッド（`.bytes()`）か、両方か
2. **利用者がラップ型を宣言できるか。** できるならどう書くか。
   `str` だけが特別なら、それは言語が持つ唯一のラップ型になる
3. **`str` に配列のメソッドが直接効くか。** `s.len()` は要るが、`s.push(byte)` はどうか
4. **文字列リテラルの型。** `str` であろうが、明記していない

**「まだ決めていないこと」に入れる。**

## C-78. ラップ型の裁定

### 承認された

| | |
|---|---|
| **2** | **利用者もラップ型を宣言できる。** `str` は特例ではない |
| **3** | **配列のメソッドは `str` に直接効く**（`.len()` `.push()` `[]`）|
| **4** | **文字列リテラルの型は `str`** |

### 1 は委任された：`new` で包み、`new` で剥がす

```
let s := new str ( bytes );          u8 array から str を作る
let b := new u8 array ( s );         str から u8 array を作る
```

**構築なので、どちらも深く複製する**（C-33）。**費用が字面に出る**（C-6）。

**別の構文を足さない理由**：`new 型 ( 引数 )` が既に「その型の値を作る」形である。
包むことも剥がすことも、**その型の値を作ること**である。**新しい概念が要らない。**

そして **3 により、剥がす機会がほとんど無い**——`s.len()` も `s[i]` も `s.push(b)` も
`str` のまま書ける。**剥がすのは `u8 array` を要求する関数に渡すときだけ**であり、
そこで複製が起きるのは**そういう関数を呼んだ帰結**として正しい。

### 🔴 ラップ型を宣言する構文は決めていない

2 は「できるようにする」までであり、**どう書くかは決まっていない。**

`struct` は名前つきの欄を並べる形なので、そのままでは使えない。
新しい鍵語を足すか、`struct` を拡張するか、別の形か——**未決定。**

**「まだ決めていないこと」に残す。**

### この決定が呼ぶ問い

**ラップ型が言語の機構になるなら、`str` の位置づけが変わる。**

これまで `str` は基底型の一覧（`u1 u8 … str`）に載っていた。
しかし**利用者が同じものを作れるなら、`str` は標準ライブラリの型である。**

**基底型から外すべきかもしれない。** ただしそれは
「無名標準ライブラリがどこまで持つか」という保留中の問いに属する。**ここでは動かさない。**

## C-79. `continue` の被演算子が見る名前と、`switch` が `;` を吸うこと

### (1) 🔴 `continue` の被演算子から本体の局所変数が見えてはならない

```
nfor (i, 0, 10) {
    let temp := i * 10;
    if (i == 0) continue break temp; fi;
}
```

`continue` の被演算子は**次の周回の本体の先頭**で処理される（C-73）。
**そこに `temp` は無い。** まだ宣言されていない。

外部の吟味は「サンク（クロージャ）が要る、GC 無しと矛盾する」と指摘した。
**サンクは要らない。名前解決の規則で閉じる。**

> **`continue` の被演算子から見えるのは、本体の先頭で見えている名前だけである。**
> **ループ変数と、外側のスコープの名前。本体で宣言された名前は見えない。**

```
nfor (i, 0, 10) { continue break i; }              よい。i は周回の先頭で束縛されている
nfor (i, 0, 10) { let t := i; continue break t; }  エラー。t は先頭では見えない
let y := 5;
nfor (i, 0, 10) { continue break y; }              よい。y は外側のセル
```

**外側の名前は捕獲ではない**——外側のセルはそのまま生きている。
**捕獲が必要な名前を、そもそも見えなくする。** だからクロージャが要らない。

**静的検査で閉じる。** 被演算子の名前解決を、本体の先頭のスコープで行うだけ。

### (2) 🔴 `switch` の腕が宣言を終える `;` を吸う

```
let x := switch (a) case 1 => 10;
let y := 20;
```

腕は `E@0` なので **`;` を吸う**（C-68）。したがって:

1. 腕の値は `10;` → paradox
2. `switch` は `let` が来た時点で終わる
3. **`let x := …` の `;` が無い**ので、宣言の paradox が残る
4. `let y := 20;` は自分の paradox を潰す
5. **領域に paradox が一つ残る → エラー**

**曖昧ではない**（外部の吟味は「決定不能」としたが、一意に決まる）。
しかし**書き手の意図と違う。** `;` は宣言を終えるつもりで書いたのに、腕に食われた。

```
let x := (switch (a) case 1 => 10);      括弧で閉じれば通る
```

**これは C-68（腕は `E@0`）と「`switch` は閉じる語を持たない」の積である。**
どちらも決定済みなので、**積をどう扱うかを決める必要がある。**

- **A. 受け入れる。** 括弧を書く規約にする。`switch` を値として使うなら括弧、という規則は覚えやすい
- **B. `switch` に閉じる語を与える**（`hctiws` / `esac` / `end`）。`if`〜`fi` と対称になる
- **C. 腕を `E@6` に戻す。** C-68 で捨てた道。`$return i; fi;` が書けなくなるので**採れない**

**判断を求める。**

### (3) 🟢 整数の恒等式は 2^N を法として成り立つ（導出）

外部の吟味が「`i64` の最小値 ÷ −1 で商が表現できず、恒等式が壊れる」とした。

C-21（溢れは折り返す）と C-75 の 7（最小値 ÷ −1 は折り返す）から導ける。

> **すべての整数演算は 2^N を法として行う。恒等式もその法の上で成り立つ。**

**数学的整数を求めてから表現可能性を検査するのではない。** 折り返しは
言語の意味論であって、失敗ではない。**paradox にはならない。**

### (4) 🟢 別名の同一性は保守的に判定する

```
var b &= a; var c &= d;
if (cond) b &= d; fi;
f(b, c)
```

`cond` 次第で `b` と `c` が同じセルに届く。**静的には決定できない。**

> **異なることを静的に証明できなければ、エラーとする。**

`&=` の対象が名前に限られている（C-53）ので、**別名の指す先は名前の集合として追える。**
分岐で合流したら**和集合を取る。** 交わればエラー。

**保守的な検査で足りる。** 停止性の問題には落ちない。

### (5) 🟡 「巻き戻し機構は無い」の語義

外部の吟味が「`outward` はスタック巻き戻しそのものであり、矛盾する」とした。

**指しているものが違う。**

> **「巻き戻し機構は無い」は所有の巻き戻し——デストラクタ・RAII・解放処理を指す。**
> **制御の転送は最初から在る**（`break` が段を進めるのがそれ）。

所有が完全に字句的で、**スコープを抜けるときに走る処理が無い**ので、
段を何段進めても、フレームを越えても、**片付けるものが無い。**
**だから制御転送が安い。** 矛盾ではなく、同じ設計の両面である。

**プローブの書き方を直す**——「所有の巻き戻し」と明示する。

### (6) 🟡 `{ a -b }` は `a - b` になる

`+` と `-` が左被演算子を要求しない（C-69）ので、
**`a` と `-b` を並べたつもりでも減算になる。**

```
{ a -b }        a - b。値は一つ
{ a; -b }       a を潰して -b。値は一つ
{ a (-b) }      値が二つ → 静的エラー
```

**C-69 の帰落である。** 避けられない——「改行に意味は無い」と組み合わさっている。
**落とし穴として書く。**

## C-80. `{ ; }` は通る（C-69 (2) の訂正）

C-69 (2) で「`{ ; }` は構文エラーである——`;` は後置演算子であり、左辺の式が無い」と書いた。
**承認を経ていない。そして誤りである。**

> **左辺に式が無いことと、左辺の領域がアーカーシャであることは区別されない。**

```
{ ; }       左辺は空の領域 → 値は paradox → ; が潰す → 内面は空 → 外界面は paradox
{ ;; }      同じ
1;;         同じ（一つ目の ; で空になり、二つ目が空の領域を受ける）
( ; )       ( ) と同じ。paradox
```

**`;` は常に左辺に領域を要求する。その領域が空でもよい。**
`1;;` を認めて `{ ; }` を落とすのは、**同じものを二通りに扱っていた。**

### 解析器の扱い

`;` に**前置位置の規則**を与える——一次式の位置に `;` が来たら、
**空の領域を左辺として置く。** 後置の規則はそのまま。

**特例ではない。** 「左辺の領域」という一つの概念に、空の場合が含まれるだけである。

### 記録

これも「決めていないものを決めた」（C-74 の型）である。
**`1;;` を導出したその場で、`{ ; }` を落とす規則を足していた。**
導出は片方だけで、もう片方は私が付け足した。

## C-81. `continue` の被演算子のスコープは設計どおり（C-79 (1) の位置づけ)

C-79 (1) を「修正」として書いたが、**そうではない。設計どおりである。**

> **`continue` の被演算子から見えるのは、本体の先頭で見えている名前だけ。**
> **ループ変数と外側の名前。本体で宣言された名前は見えない。**

これは C-73（`continue` の外界面は再開した本体の先頭）から**そのまま出る。**
外界面がそこなら、**そこで見えている名前しか見えない。** 追加の規定ではない。

**捕獲もクロージャもサンクも要らない**のは、この帰結である——
**捕獲が必要になる名前が、そもそも見えない。**

外部の吟味は「サンクが要る、GC 無しと矛盾する」としたが、
**外界面の位置を読み違えている。** 次の周回の**先頭**であって、
書かれた場所ではない。

## C-82. `switch` の腕は `E@6`。閉じ語は与えない

**決定**：C を採る。

```
arm := 'case' E@0 '=>' E@6
```

**腕の値は `;`（左束縛力 5）を吸わない。**

```
let x := switch (a) case 1 => 10;        通る。; は宣言に効く
switch (a) case 1 => f() case 2 => g();  通る。; は switch に効く
case 1 => f();                           構文エラー。腕は ; を吸わない
case 1 => ( f(); )                       腕の中で値を捨てるなら括弧
```

**`if` の分岐は `E@0` のまま**（C-68）。`if (a[i] == x) $return i; fi;` が要るので変えられない。

### 却下したもの

**B（閉じ語 `esac` を与える）を却下した。**

**A（規約だけ）も却下した**——`;` の問題が残るので。

### 残る規約

> **腕に閉じ記号の無い `switch` を直接書かない。囲む。**

```
case 1 => ( switch (y) case 2 => 10 )      よい
case 1 => { switch (y) case 2 => 10 }      よい
case 1 => switch (y) case 2 => 10          内側が後続の case を食う
```

`arm+` は**区切りも終端も持たない唯一の繰り返し**なので、貪欲さを止めるものが無い。
**貪欲でなくすと普通の `switch` が壊れる**（`arm+` が最小個数で止まり、残りの `case` が浮く）。

### 費用：C-68 の原則を腕にだけ破る

C-68 は「**表から出ない束縛力を書かない**」と決めた。`E@6` が残るのは
`:=` の右辺だけであり、**6 は `:=` の右束縛力そのもの**だった。

**腕の 6 は表から出ない。** 「`;` より上」というだけの規定である。

| 箇所 | | どこから来るか |
|---|---:|---|
| `:=` の右辺 | 6 | **`:=` の右束縛力**（表） |
| **腕の値** | **6** | **表から出ない。`;` を吸わせないための規定** |
| 脱出の被演算子 | 8 | **脱出の右束縛力**（表） |

**C-68 で捨てたものを、腕にだけ戻した。** 記録する。

B を採れば表の穴（区切りも終端も持たない繰り返し）が埋まり、
この規定も入れ子の規約も要らなくなった。**鍵語一つと引き換えに、
規定一つと規約一つを持つことを選んだ。**

## C-83. `esac` の却下理由と、`case` が必要な理由

### B（`esac`）を却下した理由

> **機械の都合で煩雑な構文を持たせないため。**
> **`( )` の方が簡潔な上、新しい機能を覚える必要がない。導出可能性が高い。**

閉じ語は**解析器の都合**である。書き手にとっては、
**既にある `( )` で囲めば済むものに、新しい鍵語を覚えさせる。**

`( )` は既に領域を作る記法として知っている。**「囲めば閉じる」は導出できる。**
`esac` は「`switch` を閉じる語がある」という**追加の知識**を要求する。

**規則の数は増えるが、覚えることは増えない方を採った。**

### 却下した案：`;` を `switch` の終端にする

```
switch case(a)
  1 => switch case(b)
    1 => 2
    2 => 4
    4 => 1;
  2 => …;;
```

`;` が内側の `switch` を閉じ、`;;` が外側を閉じる、という案。

**却下。`;` は終端であると同時に消去である。**
内側の `switch` を `;` で閉じると、**その値も潰れる。**
腕の値が paradox になり、**内側の `switch` が値を返せなくなる。**

**終端と消去に同じ記号を使えない。** これは `;` の意味論（C-14）から出る。

### `case` は外せない

「`=>` の左右がそれぞれ一つの値を取るので `case` は要らないのでは」という問い。

**外すと、腕の終わりが一トークンで決まらなくなる。**

現在:

```
… 腕の値を読み終える。次が case なら腕がもう一つ、そうでなければ switch が終わる
```

**一トークンの先読み。**

`case` を外すと:

```
switch (a) 1 => 10 foo()
```

`foo()` が**次の腕の照合値**（`=>` を待っている）なのか、**`switch` の外の式**なのかは、
**`=>` が現れるまで読まないと分からない。** そして `switch` には閉じ記号が無いので、
**走査を止めるものが無い**——最悪ファイル末尾まで読む。

`paren` / `maplit` の `=>` 先読みは**閉じ括弧で止まる**（既知の先読み）。
**腕の先読みは止まらない。** 同じ種類ではない。

> **`case` は飾りではない。腕の境界を一トークンで決めるための印である。**

### 区切り記号で代用する案

```
arm (',' arm)*
```

**一トークンで決まる。鍵語も増えない。** しかし:

```
case 1 => var x := 1, y := 2
```

`,` が**宣言の区切り**（C-35 の複数束縛）と衝突する。
貪欲に読めば宣言が取るが、**同じ記号が二つの役割を持つ。**

`case` は衝突しない。**そして「これは腕である」と字面に出る。**

**却下。**

## C-84. 浮動小数は A（非有限を paradox に潰す）を維持

**却下したもの：B（IEEE のまま＋変換関数を提供）**

**却下理由は性能ではなく意味論である。**

- `==` が同値関係でなくなり、`<` が全順序でなくなる（`a == a` が偽になりうる）
- 写像の鍵に浮動小数を使えば壊れる
- **NaN は「ここに実在する値が無い」を表す値**であり、**paradox とまったく同じ意味を、
  型の内側に二つ目の表現として持つ**ことになる

C-75 の「IEEE は値の中に『値でない』を紛れ込ませたが、この言語には外に置く場所がある」が
そのまま失われる。**paradox の存在理由の一部が消える。**

**却下したもの：束縛と比較のときだけ検査する中間案**

inf が「存在するが観測できない値」になる。**paradox とは別の二つ目の「値でないもの」**が増え、
B より悪い。

| | |
|---|---|
| 木を辿るインタプリタ | ほぼゼロ |

| **AOT / JIT** | **ベクトル化が効かない。ここが本当の費用** |

**JIT/AOT コンパイラビリティは優先度の低い設計基準だが、基準ではある。**
それを承知で中核の一貫性を採った。

### 逃げ道は既にある

**ホスト方言は基底型を足せる**（C-2）。生の IEEE が要るホストは `f64ieee` のような型を足す。

## C-85. 外部の吟味の収穫（第八回）

### (1) 🔴 私のプローブが `break 5 ?? 42` を間違えていた

```
break 5 ?? 42       脱出。?? は届かない        ← 誤り
```

**脱出の被演算子は `parse(8)`。`??` の左束縛力は 60 ≥ 8 なので吸われる。**

```
break 5 ?? 42   →  break (5 ?? 42)
```

同じ行の少し上に `break x + y → break (x + y)`（`+` は 50 ≥ 8）と書いてあり、
**自分の例どうしが矛盾していた。**

**「脱出は値位置を突き抜ける」が効くのは `( break 5 ) ?? 42` の側**である。
括弧で脱出を閉じた場合にだけ、`??` が脱出に出会う。

### (2) 🔴 セルは paradox を保持しない

```
let pos := find(xs, 42);     そのまま。pos は i64 か paradox     ← 誤り
```

**`let x := 1 / 0;` がエラーなのだから、これもエラーである。**

> **paradox は領域の外界面にしか現れない。セルには入らない。**
> **「すべての型は paradox との直和」は、領域の外界面の話である。**

**式の型は `T ⊕ paradox`。セルの型は `T` だけ。**
束縛は外界面の値をセルに書くので、**paradox なら書けずにエラーになる。**

`??` が「除去子」と呼べるのは、**セルに入れる前に落とさねばならない**からである。
この区別を書いていなかった。

### (3) 🔴 スコープを作らない領域に宣言を置けてしまう

```
if (c) var x := 1 fi;
x
```

`if` の分岐は**領域だがスコープではない**（C-20 の表）。
したがって `x` は**外側のスコープに属する**が、`c` が偽なら**束縛が起きない。**

**「宣言されたが束縛されていない名前」が条件付きで生じる。** エラーの分類に無い。

同じことが `switch` の腕、`&&` / `||` / `??` の右辺（短絡するので）にも起きる。

**導出**：宣言は名前をスコープに入れる操作である。**スコープの無い領域には入れる先が無い。**

> **宣言は、スコープを作る領域にしか置けない。**
> ブロック `{ }`、ループ本体、関数本体、最上位。

`( var x := 1; x + 1 )` も書けなくなる（`( )` はスコープを作らない）。
**代わりに `{ }` を書く**——スコープが欲しいから宣言するのだから、素直である。

**判断を求める。**

### (4) 🔴 解析器は「左辺に値があるか」を持たねばならない

```
a; -b
```

現在の擬似コードでは、`a` を読み `;` を後置適用した後も**左辺は在る**ので、
`-`（左束縛力 50）が中置として適用され `(a;) - b` になる。**意図と違う。**

**`;` は左辺の領域を空にする**（C-14）。`-` は「**左辺に値があれば取る**」（C-69）。
`a;` の後、内面はアーカーシャで**値が無い**ので、`-` は前置として働く。

> **解析器は `min_bp` のほかに「左辺に値があるか」を持つ。**
> **`;` はそれを偽にする。**

`;` が「必ず取る」のは**領域**であり、`+` `-` が「取れば取る」のは**値**である。
**空の領域から `;` は paradox を得るが、`-` は何も得ない。**

**擬似コードに書いていなかった。** C-69 で表には書いたが、解析の規則に反映していない。

### (5) 🟡 その他

- **paradox を受け付ける演算子は `??` と `;` の二つ。** 「`??` 以外は受け付けない」は不正確
- **`const` の凍結は集合で持つ。** 同じセルに `const` 別名が複数あれば、
  **すべてのスコープを抜けるまで解けない**。静的なので計数は要らない——
  **「この地点で生きている `const` 別名があるか」を見るだけ**
- **非 alias 引数は深く複製する。** `fn f (var a : i64)` の `a` は呼び出し側と別のセル
- **`nfor` の `count` は `i64`、`i` は開始値の型**
- **比較の連鎖の禁止は混在にも及ぶ**（`a < b == c` も禁じる）
- **`fn f () { break; } -> i64;` は通る。** 値の無い脱出は何も置かないので外界面は paradox

## C-86. 宣言はスコープを作る領域にしか置けない

**決定**：C-85 (3) を採る。

> **宣言（`var` / `let` / `const` / `fn` / `struct` / `flow`）は、**
> **スコープを作る領域にしか置けない。**

| | スコープ | 宣言 |
|---|---|---|
| ブロック `{ }` | ○ | **置ける** |
| ループ本体 | ○ | **置ける** |
| 関数本体 | ○ | **置ける** |
| 最上位 | ○ | **置ける** |
| `( )` | × | **置けない** |
| `if` の分岐 | × | **置けない** |
| `switch` の腕 | × | **置けない** |
| 演算子の被演算子位置 | × | **置けない** |

```
if (c) var x := 1 fi;       エラー。分岐はスコープを作らない
if (c) { var x := 1; } fi;  よい。ただし x はブロックの中だけ
( var x := 1; x + 1 )       エラー
{ var x := 1; x + 1 }       よい
f(var x := 1)               エラー
a && (var x := 1)           エラー
```

### 導出

**宣言は名前をスコープに入れる操作である。スコープの無い領域には入れる先が無い。**

置ければ**外側のスコープに入る**が、その領域は**条件付きで実行される**ことがある——
`if` の分岐、`switch` の腕、短絡する `&&` `||` `??` の右辺。
すると「**宣言されたが束縛されていない名前**」が生じ、**エラーの分類に無い状態**になる。

`( )` は条件付きではないが、**同じ規則で落とす**——
「スコープを作るか」の一点で決まる方が、**条件付きかどうかを列挙するより単純である。**

### 代償

`( var x := 1; x + 1 )` が書けない。**`{ }` を書く。**
**スコープが欲しいから宣言するのだから、素直である。**

### 効き方

**「この名前はどこに入るか」が、スコープの表だけで答えられる。**
領域とスコープを分けた甲斐がここに出る——
**領域は値の単位、スコープは名前の単位**（C-2 の三分法）であり、
**宣言は名前の操作なのでスコープに従う。**

## C-87. 別名の同一性は根の名前で判定する。レシーバも数える

### 問い（外部から）

> 「`alias` 引数に渡せるのは名前だけ」により `arr[i]` を渡せない。
> **意図的にデータ構造の局所的な書き換えを禁じているのか。**

### 答え：禁じてはいない。判定を決定可能にするためである

同じ吟味の中で、こうも指摘されている。

> `f(arr[i], arr[j])` で `i != j` を静的に証明するのは、定理証明器でも積まない限り不可能。

**この二つは同じことの表と裏である。**

経路を渡せるようにすると、**「同じセルに届くか」の判定が添字の比較になり、決定不能になる。**
名前に限れば、**名前の集合の比較**になる。

> **制限は表現力を削るためではなく、判定を有限にするためである。**

### 局所的な書き換えは書ける

```
f(arr, i)                  配列と添字を渡す。中で arr[i] を触る
arr[0].push(3)             レシーバは経路でよい
```

**渡す先で `arr[i]` と書けばよい**——経路によるアクセスは禁じていない（C-20）。
禁じているのは**別名の束縛**だけである。

### 🔴 ただし穴があった：レシーバが判定に入っていない

```
arr[0].merge(arr)
```

- レシーバは `arr[0]`——**`arr` の中を指す**
- 引数 `arr`——**同じ配列**

**同じセルに二つの別名が届いている。** しかし現在の規則は
「`alias` **引数**に渡せるのは名前だけ」としか書いておらず、**レシーバを数えていない。**

C-64 でレシーバを経路に開いたとき、**その経路が判定に参加することを書かなかった。**

> **レシーバも別名の一つとして数える。**

### 判定の方法：根の名前を比べる

> **別名の同一性は、経路の根（最初の識別子）で判定する。**

```
arr[0]   根は arr
arr      根は arr        → 衝突
arr[i]   根は arr
arr[j]   根は arr        → 衝突（保守的）
p.x      根は p
q        根は q          → 衝突しない
```

**`i != j` を証明しない。根が同じなら衝突とみなす。** 保守的だが**決定可能**である。

そして**別名を指し直せる**（C-62）ので、根は追跡が要る——
`var b &= a;` なら `b` の根は `a`。分岐で合流したら**根の集合の和**を取る。
**交われば衝突。**

### 🟡 制限は緩められるかもしれない

根で判定するなら、**経路を渡しても判定できる。**

```
f(arr[0], other)      根が arr と other。衝突しない → 許してよい？
f(arr[0], arr)        根が両方 arr → 拒否
```

**「名前だけ」は、根で判定すると決めた今、必要より強い**かもしれない。

寿命の心配も無い——**別名引数は呼び出しより長く生きず**、
呼び出しの間に配列を伸ばせるのは `arr` に届く別のもの**だけで、それは根の判定で弾かれる。**

**判断を求める。** 緩めるか、名前だけのまま残すか。

## C-88. その他の収穫（第九回）

### (1) 🔴 「領域が paradox を持って終結したらエラー」は強すぎた

```
fn f () { } ;
```

関数の外界面は paradox だが、`;` が消費するので通る。
**「終結したらエラー」では、これが説明できない。**

> **正しくは：paradox が `;` にも `??` にも消費されず、値を要求する境界に到達したときにエラーになる。**

「終結」ではなく「**消費されずに値の要求に出会うこと**」がエラーである。
`f(1/0)` は引数が値を要求するのでエラー、`f();` は `;` が消費するので通る。**同じ規則で出る。**

### (2) 🔴 メモリの解放戦略を決めていない

**「所有は完全に字句的」「解放処理は走らない」「GC も参照カウントも無い」**を並べたが、
`new` は割り当てる。

```
loop { new i64 array (1000, 0); };
```

**何もしなければ増え続ける。**

候補:

- **A. 領域ごとのアリーナ。** 領域を抜けたらまとめて捨てる
- **B. 実行ごとのアリーナ。** 一回の実行が終わったら全部捨てる
- **C. 字句的な解放。** 領域を抜けるときに解放する——**「解放処理は走らない」に反する**

**B は「一回の実行は数ミリ秒から数秒」という前提に合う**が、
長く回るループが割り当て続けると持たない。

**未決定として残す。** 意味論ではなく実装戦略だが、**言語の性格を決める。**

### (3) 🟡 `outward` は一度に一フレームだけ越える

規定していなかった。**`outward` は書いた `break` の段送りに掛かる**（C-70）ので、
**一つの段送り＝一つのフレーム。** 二フレーム越えるには `outward` を二つ書く。

### (4) 🟡 検査を通していないプログラムの安全性

「標準実装は検査を通したプログラムを受け取る前提」としたが、
**信頼できないスクリプトを受け取るホストでは、メモリ安全性が保証されない。**

**配列の範囲外は paradox**（C-21）なので**その一点は実行時に守られる**が、
別名の権限や凍結は検査に委ねている。

**ホスト界面の契約**（未決定）に属する問題として残す——
「検査器を通す責任は誰にあるか」を契約に書く。

### (5) 🟢 `;` の解析は通る（外部の誤り）

外部の吟味が「`a; b; c` を一回の `parse(0)` で読めないので破綻」としたが、
**`block := '{' E@0* '}'` が繰り返すので通る。**

`parse(0)` は `a;` で止まり（`has_value` が偽で `b` は演算子でない）、
**`E@0*` が次の `E@0` を始める。** `a; -b` も同じ——
`-` は左の値を要求するので `has_value` が偽なら止まり、次の `E@0` が前置として読む。

**C-85 (4) の `has_value` がこれを解いている。**

## C-89. 別名の判定をどこまで精密にするか（三段階）

### 問い（外部から）

> 配列の添字が決定不可能なのは明白だが、**構造体の欄は静的に区別できる。**
> それでも `f(p.x)` を一律で禁じているのは、仕様を単純に保つためか。

### 答え：そのとおり。欄は区別できる。禁じているのは単純さのためである

C-87 で「経路の根で判定する」としたが、**根より細かく見られる。**

```
p.x  と  p.y      欄名が違う → 区別できる
p.x  と  p        一方が他方を含む → 衝突
p.a.x と p.a.y    区別できる
arr[i] と arr[j]  添字は比較できない → 衝突（保守的）
arr[0] と arr[0]  同上（値が同じでも比較しない）
```

> **経路を成分ごとに比べればよい。欄名は比較でき、添字は比較できない。**

### 三段階ある

| | 渡せるもの | 判定 | 費用 |
|---|---|---|---|
| **1. 名前だけ**（現行） | 名前 | **記号の比較** | 最小 |
| **2. 根で判定** | 経路も | **根の比較** | 小。`p.x` と `p.y` も衝突扱い |
| **3. 成分で判定** | 経路も | **成分ごと。** 欄は比較、添字は衝突 | 中。前置包含の扱いが要る |

**3 なら `swap(p.x, p.y)` が書ける。** 2 では書けない（根が同じ `p` なので衝突）。

### 決定：1 のまま始める

**緩めるのは後方互換だが、締めるのは違う。**

| | |
|---|---|
| 1 → 3 に緩める | **既存のプログラムは全部通る。** 書けなかったものが書けるようになるだけ |
| 3 → 1 に締める | **既存のプログラムが壊れる** |

**保守的な側から始めるのが正しい。** イディオム（`f(arr, i)` / 構造体ごと渡す）で
実際に痛むかを見てから緩める。

**「まだ決めていないこと」ではなく「後で緩めうる決定」として記録する。**

### 緩めるときに要るもの

- 経路を**成分の列**として持つ（`p . a . [?]` のように、添字は不明の印を置く）
- **前置包含**を衝突とする（`p.x` と `p` は衝突、`p.x` と `p.x.y` も衝突）
- 別名の指し直し（C-62）があるので、**経路の集合**を分岐で合流させる

**判定は決定可能なまま。** 定理証明器は要らない——**添字を比較しないと決めているから。**

### 記録

C-87 で「名前だけは必要より強いかもしれない」と書いたが、
**「強い側から始める」という理由を書いていなかった。** ここで書く。

## C-90. 記憶は領域ごとのアリーナ。明示解放は持たない

**決定**：**領域ごとのアリーナ。** 領域を抜けたらまとめて捨てる。

### 明示解放を却下した理由

**割り当ては `new` だけではない。**

```
var xs := [ 3, 1, 4 ];      配列リテラル
var b := a;                 深い複製
f(big_array)                非 alias 引数も深い複製
```

そして `fn sum (a : i64 array)` の `a` は**呼び出し側から見えず、返る時に死ぬ。**
**誰も `delete` を書けない。**

C で明示解放が成り立つのは**暗黙の複製がスタックへ行くから**である。
Vaak は `:=` が深い複製なので、**暗黙の割り当てに名前が付かない。**

### 字句的解放が正確であることは既に決まっていた

| | |
|---|---|
| 値は自己完結（C-48） | 参照を追う必要が無い |
| 別名は外へ返せない（C-19） | 内側を指したまま外へ出ない |
| 再帰的データ構造は作れない（C-63） | 循環しない |
| 返り値は複製（実装は移動してよい） | 呼び出し側の領域へ移る |

> **スコープを越えて生き残るものが無い。だから、抜けた時点での解放は正確である。**

### 「解放処理は走らない」と両立する

**個々の値を辿らない。アリーナのポインタを一つ戻すだけ。**
デストラクタも RAII も無い。**C のスタックと同じ規律である。**

### 私の誤り

「`loop { new i64 array (1000, 0); };` は増え続ける」と書いたが、**誤り。**
**ループ本体はスコープである**（領域・スコープ・脱出段の表）ので、**周回ごとに解放される。**

**自分で決めた表を読まずに問題を作っていた。**

### ホストのメモリだけが自己管理の対象

言語の側に「自分で管理する」対象は無い。`&=` で張るホストのメモリだけであり、
それは**ホストの責任**（ホスト界面の契約、未決定）。

## C-91. 実装で見つかった解析器の穴（三件）

**P2（パーサ）を書いて、プローブの解析例をテストにしたら三つ落ちた。**

### (1) 🔴 写像リテラルの先読みが `switch` の腕を誤認する

```
( switch (y) case 2 => 10 )
```

「括弧の中の**最上位**に `=>` が現れるか」で写像かを決めていた（C-59 の先読み表）。
しかし **`case … =>` の `=>` も最上位に現れる。** 括弧が写像リテラルだと誤認された。

**修正**：走査中に `case` を数え、**その分の `=>` は数えない。**

```
( a => b )                    case が無い → 最初の => で写像と決まる
( switch (y) case 2 => 10 )   case が一つ → その => を消費 → 写像ではない
```

**先読みの規則を書いたときに、`=>` が二箇所に現れることを見落としていた**——
「`=>` は演算子ではない。写像リテラルと `switch` の腕にしか現れない」と
**自分で二箇所と書いていた。**

### (2) 🟡 「文法で書けない」が正確でなかった

```
var e &= a[0];
continue 1;
```

**どちらも「文法エラー」と書いていたが、実際には別の木として解析が通る。**

- `var e &= a[0]` → `(var e &= a)` の後に `[0]` が後置の添字として付く
- `continue 1` → `continue`（被演算子なし）と `1` の**二つの式**

**書けないのは「その意味の木」であって、「そのトークン列」ではない。**
トークン列は別の木になるだけで、構文解析は止まらない。

**修正**：どちらも**その位置で止めて、意図を言う。**

```
`&=` の対象は名前だけ。経路には張れない
`continue` は値を取れない。脱出か、何も書かないか
```

**文法に無いことと、解析器が拒むことは別である。**
前者は「導けない」、後者は「そこで止める」。**プローブの「文法エラー」という語が、
両者を同じものとして扱っていた。**

### 記録

**三件とも、プローブに書いた例をテストにしたら出てきた。**
書いた本人が読み返しても気づかず、**機械に照合させて初めて出た。**
