# Vaak で最小テープ言語を解釈する

Brainfuck 相当の八命令を持つ小さなテープ言語を Vaak で実装し、木を辿る参照実装、VM、
STEEL native の三経路で動かした記録です。実装は
[tape_language.vaak](../../examples/experiments/tape_language.vaak)、測定器と日本語名の回帰試験は
[tape-language-bench](../../examples/experiments/tape-language-bench/) にあります。

この枝は書き味と性能を確かめる実験です。Vaak の構文・意味論・標準ライブラリには何も足して
いません。

## 実装した言語

| 命令 | 意味 |
|---|---|
| `>` / `<` | ヘッドを右／左へ動かす。右端ではテープを伸ばし、左端越えは失敗 |
| `+` / `-` | 現在の `u8` セルを折り返し加減算 |
| `[` / `]` | 現在セルが 0 かどうかで反復 |
| `,` | 入力列から次のバイトを読む。入力を使い切った後は 0 |
| `.` | 現在セルを出力列へ送る |

他のバイトは読み飛ばします。ホスト出力を前提にしないため、`.` の結果は
`checksum = (checksum * 131 + byte) mod 251`、最後のバイト、出力数として返します。
無限ループでホストを止めないよう、実行には命令数の上限も渡します。

自己検査に使う台本は次です。

```brainfuck
,>,<[->+<]>.
```

入力の二バイトは 32 と 33 です。最初のセルを二番目へ移して加えるので、出力は 65 (`A`)。
167 命令で終わり、テープ長は 2 になります。最上位ではこれらを全部照合し、成功なら 42 を
返します。

## 配列だけでテープとスタックを表せた

実行テープは `u8 array`、角括弧の対応表と開き括弧のスタックは `i64 array` です。

```vaak
var tape := new u8 array(1, 0);
var opens := new i64 array(0, 0);

opens.push(i);
let begin := opens.pop() ?? 0;
tape[head] += 1;
```

専用の stack 型が無くても、LIFO の意図は `.push()` / `.pop()` で十分直接に書けました。
この規模では、stack を別の型として足す根拠は見つかりません。

角括弧は実行前に一度だけ走査し、各括弧から相手の位置へ飛ぶ配列を作ります。実行時の
`[` / `]` は `jumps.positions[pc]` という動的添字一回なので O(1) です。括弧を毎回前後へ
走査する素朴な実装は採りませんでした。

## 書いて分かったこと

### 書きやすかったところ

- `str` がバイト列なので、一バイト命令の字句処理に変換が要らない。
- 動的配列の `.push()` が右端でのテープ伸長にそのまま使える。容量増加も処理系側に隠せる。
- `u8` の折り返し演算がセルの意味と一致し、明示的なマスクが要らない。
- `while` と `if` だけで命令ポインタ式のインタープリターを素直に書ける。
- 結果を構造体にまとめると、参照実装・VM・STEEL で同じ自己検査を共有できる。

### 手間が掛かったところ

- 動的添字の読みは失敗しうるので、範囲が直前の条件から明らかでも `code[pc] ?? 0` のように
  毎回処理を書く。安全性は見えるが、熱いループでは字面が増える。
- `opens.len() > 0` を確かめても、その事実を型検査器は `.pop()` へ渡さない。
  したがって `opens.pop() ?? 0` のフォールバックは残る。
- 複数文を持つ八つの命令を `switch` の腕へ置くより、現在の構文では `if` / `elif` の方が
  短かった。命令種類が増える処理系なら、先に小さな opcode へ変換する方が読みやすい。
- 標準出力のホスト関数を仮定できないので、出力の観測には checksum という試験用の界面が要る。

## 前処理を分けた効果

`run_tape` は括弧表の構築と実行を両方行います。測定器の `prepared` モードでは
`JumpTable` を一度だけ作り、`execute_tape` へ共有してから同じ台本を繰り返します。

12 バイトしかない今回の台本では、前処理を外へ出した差は小さく、ある測定では参照実装が
約 3.8%、VM が約 4.1% 速くなりました。これは「配列スタックが遅い」という結果ではなく、
実行する167命令に対して括弧の走査が短すぎるためです。長い台本や、短い台本を何度も走らせる
用途では分離の価値が増えます。

## 性能

2026-08-22、Windows、Rust 1.98.0 release、clang 22.1.8 `-O3`。同じ台本と入力を使い、
中央値を取りました。解析・静的検査、VM の組み立て、LLVM IR 生成、clang の時間は測定外です。

| 経路 | source（括弧表も毎回） | prepared（括弧表を共有） |
|---|---:|---:|
| 木を辿る参照実装 | 約 **385 µs/run** | 約 **370 µs/run** |
| VM | 約 **235 µs/run** | 約 **225 µs/run** |
| STEEL native | 約 **0.35〜0.45 µs/run** | 同じ範囲（差は起動揺らぎ以下） |

参照実装と VM は 100 回を一標本、STEEL はプロセス起動を薄めるため 50,000〜100,000 回を
一標本にしました。STEEL は素の `return 42` の実行時間を別に測って引いています。
50,000 回と 100,000 回の総時間の傾きも、おおむね **0.43 µs/run** でした。

したがってこの小さな二重インタープリターでは、STEEL native は VM より概ね数百倍速い結果です。
ただしこれは「Vaak の一命令」の比較ではありません。参照実装と VM は、テープ言語の一命令を
実行するたびに Vaak 側の名前・領域・値・動的添字を何命令も処理します。STEEL はそれらを LLVM
へ下ろし、固定した型と分岐の多くを最適化できます。差の大半はこの**インタープリター上の
インタープリター**という構造から出ます。

native 値は短命な Windows プロセスの起動揺らぎを差し引いた推定です。厳密な桁より、参照実装・
VM が数百 µs、STEEL が 1 µs 未満という桁の違いを見る測定です。測定中に別のビルドを走らせると
参照実装と VM の値は大きく揺れるため、再現時は他の負荷を止めます。

## ボトルネックと次の調整点

この実装で熱いのは stack ではなく、次の三つです。

1. 一バイトごとの `if` / `elif` 命令分配。
2. `code[pc]`、`tape[head]`、`jumps.positions[pc]` の動的添字と範囲検査。
3. 参照実装・VMでは、一命令ごとに走る Vaak 自身の評価・分配。

次に効く最適化は新しいデータ構造ではなく、前処理です。連続する `+`、`-`、`>`、`<` を
「opcode と回数」の二本の配列へ畳めば、命令分配と動的添字をまとめて減らせます。再帰的な値も
専用 stack 型も不要です。さらに大きい言語へ進むなら、opcode・operand・jump target の平行配列が
Vaak の非再帰的な値模型に合います。

テープが外部の巨大なホスト配列である場合は事情が別です。C-95 の写しを通る動的添字は S-15 の
測定どおり高くなりうるため、`read_at` / `write_at` が効きます。今回の局所 `u8 array` はその
ホスト界面を通らず、この費用は含みません。

## 再現

```powershell
cargo run --release --bin vaak -- examples/experiments/tape_language.vaak
# 42

cargo test --release --manifest-path examples/experiments/tape-language-bench/Cargo.toml
# 日本語名の試験 3 本。clang があれば STEEL native の終了コード 42 まで確認

# 引数: managed の反復数、標本数、native の反復数、source|prepared
cargo run --release --manifest-path examples/experiments/tape-language-bench/Cargo.toml -- 100 9 50000 source
cargo run --release --manifest-path examples/experiments/tape-language-bench/Cargo.toml -- 100 9 50000 prepared
```

測定器は clang が PATH に無くても、Windows の標準配置
`%ProgramFiles%\LLVM\bin\clang.exe` を探します。clang が無い環境では LLVM IR の生成までを
確認して終了します。
