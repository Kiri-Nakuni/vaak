# pure Vaak文字列探索の費用

2026-08-22にWindows x86-64、`rustc 1.98.0`、release buildで測った。
再現には次を使う。

```console
cargo run --release --example bench_string
```

これは仕様試験ではない。速度の閾値を通常試験へ置かず、比較する実装を選ぶための
観測だけを残す。

## 測り方

- 構文解析とVMの組み立ては計時外。
- 各計測前に一度予熱し、その後の複数回の最小値を採る。
- 入力は末尾だけを`z`にした`a`列で、`str_find_byte(source, 122, 0)`と
  `str_find(source, "z")`に同じ全体走査をさせる。
- 結果のバイト位置が等しいことを毎回検査する。
- `source`はどちらも`str alias`で渡す。

連続した二回の実行では次の範囲だった。値は一検索あたりである。

| 実行器 | 入力 | `str_find_byte` | `str_find("z")` |
|---|---:|---:|---:|
| 参照実装 | 4 KiB | 1.82--2.39 ms | 40.60--45.84 ms |
| 参照実装 | 32 KiB | 19.63--20.26 ms | 298.30--306.40 ms |
| VM | 4 KiB | 1.12--1.25 ms | 6.94--7.72 ms |
| VM | 32 KiB | 8.67--9.48 ms | 57.63--70.91 ms |

32 KiBでは、一バイト専用経路は一般経路より参照実装で約15倍、VMで約6--8倍
速い。候補一個あたりで引くと、一般経路に残る余分な費用は参照実装で
約8.5--8.7 us、VMで約1.5--1.9 usだった。この差には一バイトneedleの照合も
含まれるが、一般経路だけが候補ごとに`str__match_at`の名前付き関数frameを作る。
一バイトの比較そのものでは説明できない大きさなので、frameが主因と見てよい。

これを切り分けるため、needleを文字列で一度受けて一バイトを取り出し、候補の
loopだけを呼出し元のframeへ展開した`inline`対照も測った。低外乱だった一回の
32 KiB測定は次のとおりである。

| 実行器 | `inline` | 現行`str_find("z")` | 差/候補 |
|---|---:|---:|---:|
| 参照実装 | 12.42 ms | 262.58 ms | 7.63 us |
| VM | 9.24 ms | 64.33 ms | 1.68 us |

`inline`は同じ回の`str_find_byte`（参照12.90 ms、VM8.49 ms）と同じ桁だった。
needleを文字列で渡す費用ではなく、候補ごとの`str__match_at` frameが支配している
という切り分けである。

## 反復する接頭辞

4 KiBの`a`列から、`a`を31個並べた後に`z`を置く32バイトneedleを探した。
一致は無く、各候補でneedle末尾近くまで調べる。

| 実行器 | 一検索 |
|---|---:|
| 参照実装 | 108--123 ms |
| VM | 50.8--53.9 ms |

現行の素朴な探索は最悪`O(source * needle)`である。短いneedleの通常入力には
前処理の要らない利点があるが、外部入力や長い反復接頭辞を何度も探す用途には、
予測可能な`O(source + needle)`のKMPなどを別経路として用意する価値がある。

## `alias`は深い複製を避ける

32 KiB文字列の長さだけを返す関数を512回呼び、引数を`str alias`と`str`で
比較した。

| 実行器 | `alias` | 値引数 |
|---|---:|---:|
| 参照実装 | 1.89--2.19 us/call | 3.18--3.27 us/call |
| VM | 0.47--0.52 us/call | 17.26--18.18 us/call |

これは実装上の規則とも一致する。参照実装とVMはいずれも非`alias`引数を深く
複製し、`alias`引数は元セルを束縛する。したがって、検索対象を`source : str
alias`にしたAPIは大入力を走査前に複製しない。needleを値引数にしてリテラルを
直接渡せるようにした現在の折衷も、小さいneedleを想定する限り妥当である。

## 判断

1. CSV/JSONの区切りや引用符には`str_find_byte`を使う。このspecial caseは必要。
2. `str__find_from`、`str_split`、`str_replace_all`は候補照合を同じframe内へ展開
   すると、参照実装とVMの双方で大きく改善する可能性が高い。STEELでは小さい
   内部関数のinlineでも同じ表面を保てる。
3. KMPをすべての検索の既定にはしない。短いneedleではprefix表の構築と配列操作
   の費用が増える。長いneedle、敵対的入力、同じneedleの反復利用向けに、将来の
   `string/matcher`のような細分化したモジュールで前処理済みmatcherを提供する。
4. 埋め込み用途でさらに頻繁な単純走査が必要なら、pure Vaak APIと同じ契約を持つ
   ホスト組み込みを差し替え可能にする。ただしpure Vaak版は意味論の参照として残す。
