# Vaak で小さな Forth 系言語を作る

Vaak の動的配列が処理系のデータスタックとして十分かを確かめるため、整数だけを扱う
小さな Forth 系インタープリターを書きました。実装は
[examples/vaak/07-Forth.vaak](../../examples/vaak/07-Forth.vaak) にあります。

これは ANS Forth の実装ではありません。語を空白で区切る連結型の小言語です。それでも、
データスタック、スタック操作、算術、利用者定義の語、辞書探索、誤りの伝播を含みます。

## 評価できるもの

| 語 | 意味 |
|---|---|
| `42`, `-7` | `i64` をスタックへ積む |
| `+`, `-`, `*`, `/` | 上の二値を取り、結果を積む |
| `dup` | 最上段を複製する |
| `swap` | 上の二値を入れ替える |
| `drop` | 最上段を捨てる |
| `: name ... ;` | 語を定義する |

主例は次の一行です。

```forth
: twice dup + ; 21 twice
```

`twice` は最上段を二つにして足すため、答えは 42 です。組み込み語の名前は再定義できません。
同じ利用者定義名が複数あれば、後の定義が前の定義を隠します。

## `i64 array` がそのままスタックになる

データスタックは特別な型ではなく、空の可変配列です。

```vaak
var stack : i64 array := new i64 array(0, 0);
stack.push(21);
let value := stack.pop() ?? $return false;
```

スタックを変更する関数は、署名でも変更可能な別名として受けます。

```vaak
fn apply_primitive (kind : i64, var stack : i64 array alias) { ... } -> u1;
```

`var` は変更権限、`alias` は呼び出し元と同じセルを使うことを示します。値で受けると配列を
深く複製するので、ここでは意味も費用も署名に現れます。`dup`、`swap`、`drop` は
`pop` と `push` の組み合わせだけで書けました。

下段不足や零除算が起きると、内部の実行関数は `false` を返します。公開境界の
`run_forth` はそれを値の無い `$return` に変え、利用者には paradox として見せます。
Vaak 自身は状態を巻き戻さないため、誤りまでに行った `pop` も戻りません。しかし実行は
その場で打ち切られるので、この処理系は壊れたスタックを再利用しません。

## コロン定義は元のトークン列を指す

入力はまず `str array` へ分割します。定義本体を別の配列へ複製せず、次の平行配列に置きます。

```text
definition_names   : str array
definition_starts  : i64 array
definition_ends    : i64 array
```

開始位置と終了位置は、元のトークン列に対する半開区間です。最初の走査ですべての定義を集め、
二度目の走査で最上位の語を実行します。このため、後ろに書いた定義も前の定義本体から呼べます。
利用者定義語を呼ぶと、`execute_range` が同じデータスタックを `alias` で受けて、その区間を
再帰的に実行します。

再帰的な構文木やリスト型は要りませんでした。「平らな列＋整数の位置」は LISP 実験と同じく、
現在の Vaak で小さな処理系を書くときに扱いやすい形です。大きな処理系なら、辞書を線形探索する
この三配列より、文字列の intern 表と写像の方が先に欲しくなります。

## 実装中に見つかった性能穴

可変配列をセル上で直接変更する修正を入れた後にも、木を辿る参照実装だけ `push` が配列長に
比例していました。組み込みメソッドへ進む前に、利用者定義メソッドを探すため
`need_value(base)` が名前レシーバを評価し、配列全体を複製していたためです。

名前レシーバではセルを借りて型だけを見るようにすると、増加率は線形へ戻りました。VM は既に
名前の可変メソッドを専用命令へ落としていたため、この二次増加はありませんでした。

2026-08-22、Windows x86-64、Rust 1.98.0 release build で、解析・翻訳を除き7回の中央値を
取った代表値です。小さい値なので絶対時間より増加率を見ます。

| `push` 回数 | 参照・修正前 | 参照・修正後 | VM |
|---:|---:|---:|---:|
| 1,000 | 5.825 ms | 0.532 ms | 0.188 ms |
| 2,000 | 21.507 ms | 1.120 ms | 0.489 ms |
| 4,000 | 80.189 ms | 2.532 ms | 1.054 ms |

4,000回の `push` と4,000回の `pop` を一往復させる現在の実装は、参照実装 3.996 ms、
VM 3.481 ms でした。再現用の小ベンチは
[examples/bench_stack.rs](../../examples/bench_stack.rs) です。

```bash
cargo run --release --example bench_stack -- 4000 push
cargo run --release --example bench_stack -- 4000 roundtrip
```

Forth の主例全体を1,000回走らせた中央値は、参照実装 3,067.214 ms
（3,067.2 us/run）、VM 588.615 ms（588.6 us/run）でした。こちらは各回でForth入力の字句分割も
やり直します。再現用は [examples/bench_forth.rs](../../examples/bench_forth.rs) です。

### STEEL native で初めて見えた意味差

LLVM 22.1.8 の `clang` を導入して主例をネイティブ実行すると、リンクには成功しましたが、
終了コードは期待する42ではなく **0** でした。IR生成成功だけでは、意味の一致を確認したことには
なりませんでした。

次まで縮めても再現します。

```vaak
fn push_one (var stack : i64 array alias) { stack.push(42); };
var stack : i64 array := new i64 array(0, 0);
push_one(stack);
stack.pop() ?? 0
```

| 実行経路 | 答え |
|---|---:|
| 木を辿る参照実装 | 42 |
| VM | 42 |
| STEEL native | **0** |

STEEL は `alias` 引数にも集合体の記述子を値で渡していました。要素を上書きするだけなら、記述子が
指すバッファは同じなので問題が隠れます。しかし `push` は長さ・容量・場合によってはバッファの
アドレスを変えます。呼び出された関数の記述子だけが変わり、呼び出し元の空の記述子は変わりません。

さらに、単に記述子の枠をポインタで渡すだけでは不十分です。関数内の `grow` が確保したバッファは
関数入口のアリーナ印より上にあり、現在のSTEELは関数退出時にその印まで戻します。呼び出し元へ
記述子を返すなら、伸びたバッファも印を越えて生存させなければなりません。

この問題はstack型の不足ではなく、実装済みであるはずの `alias` 意味論とSTEELの食い違いです。
誤った実行結果を速く測っても性能比較にはならないため、**STEEL native のForthベンチ値は記録しません。**
最小再現は `tests/forth.rs` の ignored 試験に残しました。

## 書いて分かったこと

### 書きやすかったところ

- 可変配列の `push`、`pop`、`len` がForthのスタック操作にそのまま対応する。
- `var ... alias` により、どの関数が同じスタックを変更するか署名だけで分かる。
- コロン定義をトークン区間で表せるため、再帰的な値型もGCも要らない。
- スタック不足、未知語、閉じない定義、零除算を公開境界で一つの paradox に畳める。
- 同じソースを参照実装、VM、STEEL のLLVM IR生成まで通せる。

### 手間が掛かったところ

- `str` はバイト列なので、`:` や数字を `58`、`48` のような値で判定する。
- `split_whitespace` や整数解析が無いため、字句分割と十進変換を処理系側で書く。
- 辞書を平行配列で持つので、利用者定義語の探索は定義数に対して線形である。
- `execute_range` はトークン列、辞書三配列、データスタックを別々の `alias` 引数で受ける。
  共有は明確だが、署名は長い。
- `let token := tokens[pos]` は文字列を複製する。高性能版は元の `source` と開始・終了位置だけを
  持つトークン表に変えた方がよい。
- コロン定義の呼び出しは Vaak の関数再帰を使う。深い処理系では、戻り位置を積む第二の
  `i64 array` を明示した方が、ホストの呼び出し深さに依存しない。

## stack 型を追加するべきか

この実験の範囲では、**追加しない方がよい**という結論です。

必要だった操作はすべて `array` に既にあり、直接更新の実装穴を塞いだ後は `push/pop` が
償却定数時間として振る舞いました。`stack T` を新しい型にしても、要素列、長さ、末尾への追加、
末尾からの除去という表現は同じです。意味の異なる型を増やす根拠がまだありません。

今後、測定から次が必要になれば、まず配列の標準メソッドとして検討できます。

- `.last()`：最上段を除去せず読む意図を短く書く。
- `.reserve(n)`：大きさが予測できる処理系で再確保を避ける。
- `.capacity()`：確保方針を測る。

Forthの「戻りスタック」も別の `i64 array` で表せます。固定容量、オーバーフロー時の固有動作、
ホストが提供する連続領域との無変換共有など、配列と異なる契約が実際に必要になった時点が
専用stack型を再検討する境目です。

性能上の次の壁はstackではありません。現在の実装では、文字列トークンの複製と辞書の線形探索が
先に効きます。Vaak-on-Vaakを進めるなら、安定した整数IDを持つarena表現、文字列intern、STEELでも
使える写像の順に調べる方が効果的です。

## 動作確認

```bash
cargo run --release --bin vaak -- examples/vaak/07-Forth.vaak
# 42

cargo test --release --test forth
# 参照実装 = 42、VM = 42、誤りはparadox、STEELのLLVM IR生成成功

# clang が使える環境で、既知のSTEEL native差を再現する。修正前は 0 != 42 で失敗する
cargo test --release --test forth -- --ignored --nocapture
```

Windows環境で一度は `clang` 22.1.8 によるリンクと実行まで確認できました。その後の新しいshellでは
MSVCの `libcmt.lib` と `oldnames.lib` が探索できず、同じリンクを再現できませんでした。成功した際に
明示した環境設定はLLVMの `bin` を `PATH` の先頭へ加えただけで、`LIB` と `INCLUDE` は設定して
いません。このため、上の終了コード0は実測として残しつつ、Windows上の再現にはVisual C++の
Developer環境も必要です。

未実装の言語機能を足さずに、小さな連結型言語とコロン定義まで書けました。専用stack型よりも、
既存の配列操作が隠れた複製をしないことの方が、処理系を書く上では決定的でした。
