# Vaak で S 式を評価する

Vaak 自身で小さな S 式インタープリターを書き、木を辿る参照実装、VM、STEEL の三経路へ
同じソースを通した記録です。実装は
[examples/vaak/06-LISP.vaak](../../examples/vaak/06-LISP.vaak) にあります。

これは Common Lisp や Scheme の実装ではありません。整数を値に持つ、小さな式言語です。
それでも、字句分割、入れ子になった式、名前の探索、字句的な束縛、遅延する条件分岐までを含みます。

## 評価できるもの

| 形 | 意味 |
|---|---|
| `42`, `-7` | `i64` の整数 |
| `name` | 最も内側の `let` から名前を探す |
| `(+ ...)`, `(* ...)` | 零個以上の引数を左から畳む |
| `(- ...)`, `(/ ...)` | 一個以上の引数を左から畳む。`(- 3)` は `-3` |
| `(= a b)`, `(< a b)` | 真なら 1、偽なら 0 |
| `(if condition yes no)` | 選んだ腕だけを評価する |
| `(let name value body)` | `body` の中だけで見える名前を作る |
| `(do ...)` | 順に評価し、最後の値を返す。空なら 0 |

例の末尾では、次の式を評価しています。

```lisp
(let x 6
  (do
    (let x 40 (+ x 2))
    (if (= (* x 7) 42)
        (+ x 36)
        (/ 1 0))))
```

内側の `x` は 40、外側の `x` は 6 のままです。条件は真なので、零除算を含む腕は
評価されません。答えは 42 です。

## 構文木を作らずに読む

普通の Lisp 処理系なら、`cons` や再帰的な列で構文木を表したくなります。しかし Vaak の
値型は循環しないことが前提で、次のような自己参照構造体は作れません。

```text
struct Node { var children : Node array; };  // 型依存が循環する
```

そこで、この実装は入力を `str array` に分け、構文木を作らずに直接評価します。`eval` は
読み始める位置を受け取り、次の三つを `Step` で返します。

```vaak
struct Step {
    let ok : u1 := false;
    let value : i64 := 0;
    let next : i64 := 0;
};
```

`(+ 1 (* 2 3))` を読むとき、内側の `eval` が値 6 と `)` の直後を返し、外側がそこから
読み続けます。再帰するのは制御だけで、値の形は再帰しません。この「平らな列＋位置」は、
現在の Vaak で再帰下降パーサを書くときの扱いやすい形です。

## 環境は二本の配列

名前と値は、同じ長さの二本の配列に置きます。

```vaak
names  : str array
values : i64 array
```

名前は末尾から探すので、内側の束縛が外側を隠します。最初の版を書いた時点では STEEL が
`map` を扱わなかったため、三経路に通る二本の配列を選びました。現在の STEEL 第四段には
`map` と `hash` があり、大きな識別子表は `hash` で intern する方が自然です。

最初の版では、`let` ごとに環境を複製してから一組を追加しました。

```vaak
var scoped_names := names;
var scoped_values := values;
scoped_names.push(name);
scoped_values.push(bound.value);
```

Vaak の `:=` は深い複製なので、これは安全側の短い実装です。一方、束縛のたびに環境全体を
写すため、深い入力では複製量が二次的に育ちます。調整版は `names` と `values` を可変の
`alias` 引数で受け、一組を `push` して本体を評価し、戻ったあとに `pop` します。

```vaak
names.push(name);
values.push(bound.value);
let body := eval(tokens, bound.next, names, values, false);
names.pop();
values.pop();
```

二方式は `copy_environment` 引数で切り替えられ、同じ試験を通します。専用 stack 型は
使っていません。測定と Safe Rust 版との比較は
[小 LISP の別名調整と Safe Rust 比較](lisp-performance.md)にあります。

読み取り専用で共有する大きな値は、関数の署名に `alias` を書いて渡しています。

```vaak
fn eval (tokens : str array alias, pos : i64,
         names : str array alias, values : i64 array alias) { ... } -> Step;
```

共有する箇所と複製する箇所がソースから分かるのは、処理系を書くときにも有用でした。

## 選ばない式を飛ばす

構文木を先に作らないため、`if` の実装には一工夫要ります。真の腕を評価したあと、偽の腕を
普通に `eval` すると、副作用や零除算まで実行してしまいます。`skip` は括弧の深さだけを数え、
式を評価せずに直後まで進みます。これにより `if` は選んだ腕だけを評価します。

この方式は特殊形式を追加するたびに「評価する部分」と「構文だけ読む部分」を明示する必要が
あります。小さな処理系では分かりやすい一方、`quote`、マクロ、関数定義まで増やすなら、
平らな構文木を別の配列群として作る方が拡張しやすくなります。

## 書いて分かったこと

### 書きやすかったところ

- `str` に `.len()`、`.push()`、`.clear()`、`[]` がそのまま使えるので、字句分割は短く書ける。
- 動的配列だけでトークン列と環境を作れる。確保器を処理系側で用意しなくてよい。
- 再帰関数は参照実装、VM、STEEL のすべてで使える。
- `alias` が署名に出るため、大きな列をどこで共有しているか読み取りやすい。
- 深い複製が既定なので、環境の枝分かれを安全側に書くのは簡単。
- 最外部では、解釈できない入力を paradox に畳める。例外用の値を整数から取り除かなくてよい。

### 手間が掛かったところ

- `str` はバイト列なので、括弧や数字を `40`、`41`、`48` のような `u8` で判定する。
  標準の文字分類や字句分割があれば、意図をもっと直接書ける。
- 三経路の当初の共通部分だけで書いたため、名前探索は線形になった。
- 再帰的な値型を作れないため、Lisp のリストや構文木をそのまま型にできない。
- Vaak の `fn` は局所変数を捕捉しない。`lambda` を足すなら、関数本体の位置と環境を
  データとして持ち、呼び出しを自分でディスパッチする必要がある。
- `let` ごとの深い環境複製は簡単だが、時間も場も束縛数に比例して増える。

### STEEL で見つかった実装差（修正済み）

参照実装と VM は無名標準ライブラリの `$return` を自動で用意しますが、現在の STEEL は
まだ注入しません。そのため、三経路で共有するこの例では同じ `flow` 定義をソース冒頭にも
明示しています。

最初の版は、内部の失敗も paradox で運び、次のように書いていました。

```vaak
let part := eval(tokens, cursor, names, values) ?? $return;
total += part.value;
```

参照実装と VM では動きましたが、修正前の STEEL は `part` を `Step` ではなく `i64` として扱い、
欄アクセスで「欄を持つのは構造体だけ」と報告していました。脱出式に付けた仮の `i64 paradox`
から `??` 全体の型を取っていたためです。C-29 の `E ?? D : T` に合わせて左辺の型を保つように
直し、現在はこの形も三経路で動きます。

例は測定対象を変えないため `Step.ok` を明示し、`eval` 自体は必ず `Step` を返す形のままです。公開する
`run_lisp` の境界では `ok == false` を値なしの `$return` に変え、利用者には paradox として
見せています。これは言語仕様や STEEL の制限から必要な `ok` ではありません。

## 動作確認

```bash
cargo run --release --bin vaak -- examples/vaak/06-LISP.vaak
# 42

cargo test --release --test lisp
# 参照実装 = 42、VM = 42、STEEL の LLVM IR 生成成功
```

`tests/lisp.rs` は `clang` が見つかる環境では、LLVM IR から実行ファイルも作り、終了コード
42 まで照合します。今回の Windows 環境では LLVM 22.1.8 の `clang` で、実行ファイルの生成と
終了コード 42 まで確認しました。次でも手動確認できます。

```bash
cargo run --release --bin steel -- examples/vaak/06-LISP.vaak -o target/vaak-lisp
./target/vaak-lisp
echo $?  # 42
```

STEEL の最上位整数はプロセスの終了コードになるので、例の答えは 0〜255 に収めています。

## 次に広げるなら

この実験を処理系らしく育てる順番は、次のようになります。

1. トークンに開始位置を添え、誤りを入力上の位置まで戻す。
2. 構文木を「種類・値・最初の子・次の兄弟」の平行配列として作る。
3. `lambda` を、本体のノード番号と環境の組として表す。
4. 名前を `hash` で intern し、三経路で整数 ID の探索費用を測る。
5. `Step ?? $return` の STEEL 側の型保持を直し、内部の `ok` を paradox へ戻す。

未実装の言語機能を足さなくても、整数を扱う S 式評価器までは書けました。一方で、
再帰的なデータ、捕捉する関数、効率のよい文字列操作の三点が、より本格的な Lisp へ進む際の
境目です。
